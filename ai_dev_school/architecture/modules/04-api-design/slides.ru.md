## Ресурсы и URL

| Плохо | Хорошо |
|---|---|
| `POST /createBooking` | `POST /api/bookings` |
| `GET /getSlotsForMaster?id=7` | `GET /api/masters/7/slots` |
| `POST /api/bookings/1017/cancel` | `PATCH /api/bookings/1017` с `{"status": "cancelled"}` — или явное действие, если это отдельный бизнес-процесс |
| `GET /api/Booking_List` | `GET /api/bookings` |

- URL — **существительные**, коллекции — во множественном числе
- Вложенность — максимум один уровень: `/masters/7/slots`, а не `/masters/7/services/3/slots/42/bookings`
- Действие — это метод HTTP, а не глагол в пути

<!-- Slide 6 -->
## Методы: безопасные и идемпотентные

| Метод | Что делает | Безопасный | Идемпотентный |
|---|---|---|---|
| `GET` | Прочитать | Да | Да |
| `PUT` | Заменить целиком | Нет | Да |
| `DELETE` | Удалить | Нет | Да |
| `PATCH` | Изменить часть | Нет | Не обязательно |
| `POST` | Создать / действие | Нет | **Нет** |

- **Безопасный** — ничего не меняет на сервере
- **Идемпотентный** — повтор запроса даёт тот же результат, что и один запрос
- Сеть ненадёжна: клиенты, прокси и SDK **повторяют** запросы. Повтор `POST` — это вторая запись.

<!-- Slide 7 -->
## Коды ответов, которые действительно нужны

| Код | Когда |
|---|---|
| `200 OK` / `201 Created` / `204 No Content` | Успех: прочитали / создали / удалили |
| `400 Bad Request` | Запрос нельзя разобрать |
| `401 Unauthorized` | Не знаем, кто вы |
| `403 Forbidden` | Знаем, но нельзя |
| `404 Not Found` | Ресурса нет (или вам не положено знать, что он есть) |
| `409 Conflict` | Конфликт состояния: слот уже занят |
| `422 Unprocessable Content` | Данные не прошли валидацию |
| `429 Too Many Requests` | Превышен лимит |
| `500` / `503` | Ошибка сервера / сервис временно недоступен |

Правило: `4xx` — клиент может исправить запрос; `5xx` — клиент не виноват, можно повторить позже.

## Единый формат ошибок: Problem Details (RFC 9457)

```
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://slot.example/errors/slot-taken",
  "title": "Слот уже занят",
  "status": 409,
  "detail": "Слот 42 заняли в 14:03",
  "instance": "/api/bookings",
  "nearest_free_slots": [43, 47]
}
```

- Один формат на весь API — фронтенд и агент разбирают ошибки одним кодом
- `type` — стабильный идентификатор, по нему клиент решает, что делать
- Дополнительные поля (`nearest_free_slots`) — разрешены стандартом

## Валидация на границе

```
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://slot.example/errors/validation",
  "title": "Данные не прошли проверку",
  "status": 422,
  "errors": [
    {"field": "phone", "message": "Ожидается номер в формате +7XXXXXXXXXX"},
    {"field": "slot_id", "message": "Слот в прошлом"}
  ]
}
```

- Проверяем **всё**, что пришло от клиента: типы, форматы, диапазоны, права
- Ошибки — **по полям**, чтобы форма подсветила нужное место
- Pydantic / FastAPI делают базовую валидацию из типов; бизнес-правила — ваш код

## Пагинация

| | Offset: `?page=3&size=20` | Cursor: `?cursor=…&limit=20` |
|---|---|---|
| Как работает | Пропустить N строк | Продолжить после последнего элемента |
| Прыгнуть на страницу 50 | Можно | Нельзя |
| Новые записи во время листания | Дубли и пропуски | Стабильно |
| Скорость на больших таблицах | Падает: БД всё равно читает N строк | Постоянная (по индексу) |

```json
{ "items": [ ... ], "next_cursor": "eyJzdGFydHNfYXQiOiIyMDI2LTEwLTA5VDE1OjAwIiwiaWQiOjQ3fQ" }
```

Курсор — непрозрачная для клиента строка (внутри — ключ последнего элемента). Списки всегда с лимитом.

## Фильтры, сортировка, соглашения о данных

- Фильтры и сортировка — параметрами: `GET /api/slots?master_id=7&from=2026-10-09&sort=starts_at`
- Один стиль имён во всём API: `snake_case` **или** `camelCase`, не вперемешку
- Даты и время — **ISO 8601 с часовым поясом**: `2026-10-09T15:00:00+03:00`
- Деньги — **целым числом в минимальных единицах** + валюта: `{"amount": 90000, "currency": "RUB"}` = 900 ₽
- ID — строки или числа, но одинаково везде
- `null` и отсутствующее поле — договоритесь, что означает каждое

## Идемпотентность: проблема

Клиент нажал «Записаться» → запрос дошёл, запись создана → ответ потерялся (плохая сеть) → клиент или SDK **повторяет** запрос.

Без защиты — **две записи** или, если слот уже занят первым запросом, клиент видит «Слот занят» на свою же запись.

Решение — **ключ идемпотентности**:

```
POST /api/bookings
Idempotency-Key: 9b2f6c1e-4d7a-4f0e-9a51-3c8e2b7d1a44
```

Клиент генерирует ключ (UUID) **один раз на действие** и повторяет его при ретраях. Сервер на повтор с тем же ключом возвращает **сохранённый** ответ.

---

<!-- Slide 13 -->
## Идемпотентность: реализация

```python
@app.post("/api/bookings", status_code=201)
async def create_booking(data: BookingCreate, idempotency_key: str = Header()):
    saved = await repo.get_idempotent(idempotency_key)
    if saved:
        if saved.request_hash != hash_of(data):
            raise HTTPException(422, "Ключ уже использован с другим телом запроса")
        return saved.response                     # повтор: тот же ответ
    booking = await book_slot(data)
    await repo.save_idempotent(idempotency_key, hash_of(data), booking)
    return booking
```

- Ключ хранится **в той же транзакции**, что и запись, с уникальным индексом — два одновременных повтора не пройдут оба
- Ключи хранят ограниченное время (например, 24 часа)
- Тот же ключ с **другим** телом — ошибка клиента

## Одновременные правки: ETag и If-Match

Мастер и администратор одновременно редактируют одну запись — побеждает последний, правка первого молча теряется.

```
GET /api/bookings/1017          →  200, ETag: "v7"
PATCH /api/bookings/1017
If-Match: "v7"                  →  200, ETag: "v8"
PATCH /api/bookings/1017
If-Match: "v7"                  →  412 Precondition Failed (запись уже изменили)
```

- Это **оптимистичная блокировка**: не держим замок, а проверяем версию при записи
- Внутри — колонка `version`: `UPDATE ... SET version = version + 1 WHERE id = 1017 AND version = 7`

## Версионирование и развитие

**Добавлять можно** (не ломает клиентов):
- новые эндпоинты, новые необязательные поля в запросе, новые поля в ответе

**Ломающие изменения** (нужна новая версия):
- удалить или переименовать поле, сменить тип, сделать поле обязательным, изменить смысл кода ответа

Способы: в пути `/api/v1/...` (проще всего), в заголовке, по дате версии.

Вывод из эксплуатации: объявить заранее, заголовки `Deprecation` и `Sunset`, следить по логам, кто ещё вызывает старую версию.

## Авторизация и лимиты

- Пользователи — сессия или токен; партнёры — **API-ключи** с правами (scopes): `bookings:read`, `bookings:write`
- Права проверяются на **каждом** запросе, на сервере — не только «залогинен ли», но и «его ли это запись»
- **Лимиты запросов** защищают от перебора и случайных циклов:

```
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

- Лимиты — на пользователя, ключ, IP; на дорогие операции (запись, вызов LLM) — строже

## Вебхуки: API наоборот

Сервер сам сообщает партнёру о событии: «создана запись» → POST на URL партнёра.

```python
import hashlib, hmac

def verify(body: bytes, timestamp: str, signature: str, secret: bytes) -> bool:
    signed = timestamp.encode() + b"." + body
    expected = hmac.new(secret, signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```

- **Подпись** (HMAC) — получатель проверяет, что вебхук от вас; метка времени — защита от повторной отправки старых сообщений
- **Повторы** с растущей паузой, если получатель не ответил `2xx`
- Получатель **идемпотентен**: одно событие может прийти дважды — храните `event_id`

## REST, GraphQL, gRPC, WebSocket / SSE

| | Сильная сторона | Когда |
|---|---|---|
| **REST** | Просто, кэшируется, понятно всем | По умолчанию, публичные API |
| **GraphQL** | Клиент сам выбирает поля, один запрос вместо пяти | Сложный фронтенд, много связанных данных, разные клиенты |
| **gRPC** | Бинарный, быстрый, строгая схема, стриминг | Общение сервисов внутри системы |
| **WebSocket / SSE** | Сервер сам присылает обновления | Чаты, живые статусы, стриминг ответов LLM (Модуль 7) |

Для «Slot»: REST наружу. SSE — для живого обновления свободных слотов.

## Contract-first: OpenAPI как источник правды

1. Сначала меняем `openapi.yaml`, ревьюим в PR
2. **Spectral** — линтер спецификации: имена, коды ответов, описания
3. **Prism** — мок-сервер для фронтенда до готового бэкенда
4. **Генерация клиентов** — типизированный клиент для фронтенда вместо ручных `fetch`
5. **Schemathesis** — генерирует тысячи запросов по спецификации и ищет, где реализация с ней расходится

Если контракт и код расходятся — контракт врёт, и его копируют все клиенты.

## API для ИИ-агентов

- Агент читает **описания** в OpenAPI буквально: пишите, что делает эндпоинт и когда его вызывать
- **Примеры** запросов и ответов в спецификации — лучшая подсказка
- **Предсказуемые ошибки**: по `type` и `detail` агент понимает, что исправить
- Агенты **повторяют** запросы чаще людей → идемпотентность обязательна
- Опасные действия — отдельными эндпоинтами с отдельными правами
- Поверх API легко сделать **MCP-сервер** — и «Slot» станет инструментом для любого агента
