  • Старые версии приложения живут у пользователей годами — опубликованный API нельзя «просто переписать»
  • Хороший API скучный и предсказуемый: увидев один эндпоинт, можно угадать остальные

Плохо

Хорошо

  • URL — существительные, коллекции — во множественном числе
  • Вложенность — максимум один уровень; действие — это метод HTTP, а не глагол в пути

Безопасный — ничего не меняет. Идемпотентный — повтор даёт тот же результат, что и один запрос.

Клиенты, прокси и SDK повторяют запросы. Повтор POST — это вторая запись.

Единый формат ошибок: Problem Details (RFC 9457)

HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://slot.example/errors/slot-taken",
  "title": "Слот уже занят",
  "status": 409,
  "detail": "Слот 42 заняли в 14:03",
  "instance": "/api/bookings",
  "nearest_free_slots": [43, 47]
}
  • Один формат на весь API — фронтенд и агент разбирают ошибки одним кодом
  • type — стабильный идентификатор, по нему клиент решает, что делать; свои поля разрешены

Валидация на границе

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://slot.example/errors/validation",
  "title": "Данные не прошли проверку",
  "status": 422,
  "errors": [
    {"field": "phone", "message": "Ожидается номер в формате +7XXXXXXXXXX"},
    {"field": "slot_id", "message": "Слот в прошлом"}
  ]
}
  • Проверяем всё, что пришло от клиента; ошибки — по полям, чтобы форма подсветила нужное место
  • Pydantic / FastAPI проверяют типы; бизнес-правила — ваш код

Идемпотентность: проблема

Решение — ключ идемпотентности: клиент генерирует UUID один раз на действие и повторяет его при ретраях.

POST /api/bookings
Idempotency-Key: 9b2f6c1e-4d7a-4f0e-9a51-3c8e2b7d1a44

Идемпотентность: реализация

@app.post("/api/bookings", status_code=201)
async def create_booking(data: BookingCreate, idempotency_key: str = Header()):
    saved = await repo.get_idempotent(idempotency_key)
    if saved:
        if saved.request_hash != hash_of(data):
            raise HTTPException(422, "Ключ уже использован с другим телом запроса")
        return saved.response                     # повтор: тот же ответ
    booking = await book_slot(data)
    await repo.save_idempotent(idempotency_key, hash_of(data), booking)
    return booking
  • Ключ хранится в той же транзакции, что и запись, с уникальным индексом — два одновременных повтора не пройдут оба
  • Ключи хранят ограниченное время (например, 24 часа); тот же ключ с другим телом — ошибка клиента

Одновременные правки: ETag и If-Match

Мастер и администратор правят одну запись — побеждает последний, правка первого молча теряется.

  1. GET /api/bookings/1017 → 200, ETag: "v7"
  2. PATCH If-Match: "v7" → 200, ETag: "v8"
  3. PATCH If-Match: "v7" → 412 Precondition Failed — запись уже изменили
  • Оптимистичная блокировка: не держим замок, а проверяем версию при записи
  • Внутри: UPDATE ... SET version = version + 1 WHERE id = 1017 AND version = 7

Версионирование и развитие

Добавлять можно

  • Новые эндпоинты
  • Новые необязательные поля в запросе
  • Новые поля в ответе

Ломает клиентов → новая версия

  • Удалить или переименовать поле
  • Сменить тип, сделать поле обязательным
  • Изменить смысл кода ответа
  • Способы: в пути /api/v1/... (проще всего), в заголовке, по дате версии
  • Вывод из эксплуатации: объявить заранее, заголовки Deprecation и Sunset, смотреть в логах, кто ещё вызывает старую версию

Авторизация и лимиты

  • Пользователи — сессия или токен; партнёры — API-ключи с правами: bookings:read, bookings:write
  • Права — на каждом запросе, на сервере: не только «залогинен ли», но и «его ли это запись»
  • Лимиты — на пользователя, ключ, IP; на дорогие операции (запись, вызов LLM) — строже
HTTP/1.1 429 Too Many Requests
Retry-After: 30

Вебхуки: API наоборот

import hashlib, hmac

def verify(body: bytes, timestamp: str,
           signature: str, secret: bytes) -> bool:
    signed = timestamp.encode() + b"." + body
    expected = hmac.new(secret, signed,
                        hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
  1. Событие создана запись → POST на URL партнёра
  2. Подпись HMAC + метка времени: от вас и не старое
  3. Повторы с растущей паузой, пока нет 2xx
  4. Дубли получатель хранит event_id

API для ИИ-агентов

Агенту помогает

  • Описания в OpenAPI: что делает и когда вызывать
  • Примеры запросов и ответов
  • Предсказуемые ошибки с type и detail

Агент усиливает риски

  • Повторяет запросы чаще людей → идемпотентность обязательна
  • Опасные действия — отдельные эндпоинты с отдельными правами

Поверх API легко сделать MCP-сервер — и «Slot» станет инструментом для любого агента.

Лабораторная работа

  1. Доработайте OpenAPI «Slot»: Problem Details, cursor-пагинация, Idempotency-Key на POST /bookings, ETag на изменение записи
  2. Реализуйте изменения в API
  3. Подписанный вебхук booking.created и получатель, который проверяет подпись
  4. Проверьте спецификацию Spectral, прогоните Schemathesis
  5. С агентом: поиск несогласованности в OpenAPI и запуск Schemathesis; каждую находку сверьте со спецификацией сами
