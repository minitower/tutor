## Почему БД — сердце приложения

- Код переписывают каждые пару лет; данные живут **десятилетиями** и переживают несколько версий приложения
- Баг в коде чинится деплоем; испорченные данные — иногда **никак**
- К одной БД ходят API, воркеры, админка, аналитика, скрипты — правило в коде одного из них не защищает от остальных
- Большинство проблем производительности — в БД (Модуль 6)

> База данных — последняя линия обороны. Что она не запрещает, однажды случится.

## Моделирование данных

- **Сущности → таблицы**, связи → внешние ключи (по ER-диаграмме из Модуля 1)
- **Ключи:** суррогатный (`id bigint`) — по умолчанию; естественный (телефон, email) — меняется, не делайте его первичным
- **Нормализация:** каждый факт хранится в одном месте — нет противоречий при обновлении
- **Денормализация** — осознанно, ради скорости чтения, с понятным способом поддерживать копию в актуальном виде
- Время — всегда `timestamptz`; деньги — `numeric` или целое в копейках, никогда `float`

## Схема «Slot»

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE masters (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name      text NOT NULL,
  timezone  text NOT NULL DEFAULT 'Europe/Moscow'
);

CREATE TABLE slots (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  master_id  bigint NOT NULL REFERENCES masters(id),
  starts_at  timestamptz NOT NULL,
  ends_at    timestamptz NOT NULL CHECK (ends_at > starts_at),
  booked     boolean NOT NULL DEFAULT false,
  EXCLUDE USING gist (master_id WITH =, tstzrange(starts_at, ends_at) WITH &&)
);

CREATE TABLE bookings (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  slot_id       bigint NOT NULL REFERENCES slots(id),
  client_phone  text NOT NULL CHECK (client_phone ~ '^\+7[0-9]{10}$'),
  status        text NOT NULL DEFAULT 'confirmed'
                CHECK (status IN ('confirmed', 'cancelled', 'done', 'no_show')),
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX one_active_booking_per_slot
  ON bookings (slot_id) WHERE status <> 'cancelled';
```

<!-- Slide 7 -->
## Ограничения как бизнес-правила

| Правило бизнеса | Ограничение в БД |
|---|---|
| У слота есть мастер | `REFERENCES masters(id)` |
| Слот заканчивается после начала | `CHECK (ends_at > starts_at)` |
| У мастера не пересекаются слоты | `EXCLUDE USING gist (... WITH &&)` |
| Телефон в правильном формате | `CHECK (client_phone ~ ...)` |
| На слот не больше одной активной записи | Частичный `UNIQUE ... WHERE status <> 'cancelled'` |
| Статус — из списка | `CHECK (status IN (...))` |

Частичный индекс важен: обычный `UNIQUE (slot_id)` запретил бы снова записаться на слот после отмены.

## Транзакции и ACID

- **Atomicity** — всё или ничего: запись создана **и** слот помечен занятым, или ни то ни другое
- **Consistency** — после транзакции все ограничения выполняются
- **Isolation** — параллельные транзакции не видят «половинок» друг друга
- **Durability** — подтверждённое не пропадёт при падении сервера (WAL на диске)

```python
async with db.transaction():
    await mark_slot_booked(slot_id)
    booking = await insert_booking(slot_id, phone)
    await enqueue_notification(booking.id)   # outbox-таблица в той же транзакции
```

## Гонка: «проверил, потом вставил»

```python
if not await repo.slot_is_free(slot_id):      # оба клиента видят «свободен»
    raise SlotTaken()
await repo.insert_booking(slot_id, phone)     # оба вставляют → двойная запись
```

| Время | Клиент А | Клиент Б |
|---|---|---|
| 14:03:00.001 | Слот свободен? — да | |
| 14:03:00.002 | | Слот свободен? — да |
| 14:03:00.003 | Вставить запись | |
| 14:03:00.004 | | Вставить запись |

На ноутбуке с одним пользователем этот баг не воспроизвести. На запуске со скидкой — он случится в первый же час.

<!-- Slide 10 -->
## Как закрыть гонку

**1. Ограничение в БД + обработка ошибки** — самый надёжный вариант:

```python
try:
    await repo.insert_booking(slot_id, phone)
except IntegrityError:            # сработал one_active_booking_per_slot
    raise SlotTaken()             # → 409 Conflict
```

**2. Условный UPDATE** — атомарная «проверка и запись» одним запросом:

```sql
UPDATE slots SET booked = true WHERE id = 42 AND NOT booked RETURNING id;
-- 0 строк → слот уже занят
```

**3. Блокировка строки** — `SELECT ... FROM slots WHERE id = 42 FOR UPDATE` внутри транзакции: второй клиент ждёт, пока первый закончит.

## Уровни изоляции в PostgreSQL

| Уровень | Что гарантирует | Цена |
|---|---|---|
| **Read Committed** (по умолчанию) | Видны только подтверждённые данные; каждый запрос видит свежий снимок | Возможны потерянные обновления и гонки «проверил-вставил» |
| **Repeatable Read** | Вся транзакция видит один снимок | Конфликт записи → ошибка, нужен повтор |
| **Serializable** | Как будто транзакции шли строго по очереди | Больше ошибок сериализации → код обязан повторять транзакцию |

Практика: Read Committed + ограничения + условные UPDATE закрывают большинство задач. Serializable — для сложных инвариантов между многими строками, и только с циклом повторов.

## Индексы подробно

- **B-tree** — по умолчанию: равенство, диапазоны, сортировка
- **Составной индекс** `(master_id, starts_at)` работает для `master_id = 7` и для `master_id = 7 AND starts_at > now()`, но **не** для одного `starts_at` — порядок колонок важен
- **Частичный** `WHERE NOT booked` — меньше и быстрее, если ищем только свободные
- **Покрывающий** `INCLUDE (ends_at)` — ответ из индекса без чтения таблицы
- **GIN** — JSONB, полнотекстовый поиск, массивы; **GiST** — интервалы, геоданные
- Каждый индекс **замедляет запись** и занимает место; неиспользуемые ищите в `pg_stat_user_indexes`

## Миграции без простоя: expand → migrate → contract

Переименуем `client_phone` → `phone`, не останавливая сервис:

1. **Expand:** добавить колонку `phone`; новый код пишет в **обе** колонки
2. **Migrate:** перенести старые данные пачками (`UPDATE ... WHERE id BETWEEN ...`)
3. **Switch:** код читает из `phone`
4. **Contract:** код перестаёт писать в `client_phone`; следующим релизом — удалить колонку

Каждый шаг совместим и со старой, и с новой версией кода — во время деплоя работают обе.

<!-- Slide 14 -->
## Опасные операции в миграциях

| Операция | Проблема | Как безопасно |
|---|---|---|
| `CREATE INDEX` | Блокирует запись в таблицу на всё время построения | `CREATE INDEX CONCURRENTLY` |
| `ALTER COLUMN ... TYPE` | Переписывает всю таблицу под блокировкой | Новая колонка + перенос данных |
| `SET NOT NULL` на большой таблице | Полное сканирование под блокировкой | `CHECK (...) NOT VALID`, затем `VALIDATE CONSTRAINT` |
| Любой `ALTER TABLE` | Ждёт блокировку и выстраивает очередь из всех запросов за собой | `SET lock_timeout = '3s'` и повтор |

Правило: миграцию на большой таблице сначала прогоняют на копии продакшен-данных.

## JSONB: гибкость внутри PostgreSQL

```sql
ALTER TABLE masters ADD COLUMN settings jsonb NOT NULL DEFAULT '{}';
SELECT * FROM masters WHERE settings @> '{"reminders": {"sms": true}}';
CREATE INDEX ON masters USING gin (settings);
```

- **Хорошо:** настройки, ответы внешних API, редкие необязательные атрибуты
- **Плохо:** то, по чему вы ищете, сортируете и связываете таблицы — это колонки
- JSONB часто закрывает потребность «нам нужна MongoDB»

## Выбор хранилища

| Данные | Хранилище |
|---|---|
| Бизнес-данные, связи, транзакции | **PostgreSQL** — по умолчанию |
| Кэш, сессии, очереди, счётчики, лимиты | **Redis** / Valkey |
| Документы с сильно разной структурой | MongoDB — или JSONB в PostgreSQL |
| Аналитика, события, логи, миллиарды строк | **ClickHouse** |
| Полнотекстовый поиск с морфологией, фасеты | OpenSearch / Elasticsearch, Meilisearch |
| Файлы, картинки, бэкапы | **Объектное хранилище (S3)** — не БД |
| Векторы для семантического поиска | **pgvector** в PostgreSQL, Qdrant (Модуль 7) |

Каждое новое хранилище — ещё одна система, которую нужно бэкапить, обновлять и мониторить.

## OLTP vs OLAP

| | OLTP | OLAP |
|---|---|---|
| Пример | «Записать клиента на слот» | «Конверсия по мастерам за квартал» |
| Запросы | Много коротких, по ключу | Мало тяжёлых, по всей таблице |
| Хранилище | PostgreSQL | ClickHouse, хранилище данных |
| Хранение | По строкам | По колонкам |

Тяжёлый аналитический запрос к продакшен-БД замедляет запись клиентов. Аналитику — на реплику или в отдельное колоночное хранилище.

## Порядок масштабирования

1. **Запросы и индексы** — `EXPLAIN ANALYZE` (Модуль 6); чаще всего этого хватает
2. **Вертикально** — больше CPU, памяти, быстрые диски
3. **Пул соединений** — PgBouncer
4. **Реплики на чтение** — внимание к **задержке репликации**: клиент записался, а реплика ещё не знает — читайте свежее с основной БД
5. **Кэш** перед БД — Redis
6. **Партиционирование** — большие таблицы по времени (слоты по месяцам)
7. **Шардирование** — данные на нескольких серверах; самое сложное и последнее средство

Каждая следующая ступень дороже в поддержке — не прыгайте через ступени.

## Бэкапы и восстановление на момент времени

- `pg_dump` — логическая копия; просто, но медленно восстанавливается на больших БД
- **Физический бэкап + архив WAL** (pgBackRest, WAL-G) → **PITR**: восстановить состояние на 14:02:59, за секунду до ошибочного `DELETE`
- Управляемые БД в облаке делают это сами — проверьте, на сколько дней назад
- Регулярное **тестовое восстановление** — часть процесса (Модуль 11)

## БД и ИИ-агенты

- Агенту — **роль только на чтение** и копия данных без персональной информации (MCP к БД — в курсе по агентам)
- Миграции, написанные агентом, — через ревью и прогон на копии данных
- Агенты любят «упростить» схему, удалив неудобное ограничение — ограничение и есть защита
- Никогда — права на запись в продакшен-БД

## Лабораторная работа

1. Пересоберите схему «Slot»: внешние ключи, `CHECK`, `EXCLUDE` для пересекающихся слотов, частичный уникальный индекс на активную запись
2. Тест: 50 одновременных записей на один слот → проходит **ровно одна**, остальные получают 409
3. Миграция без простоя (expand → migrate → contract) во время нагрузочного теста — ноль упавших запросов
4. Проверьте индексы через `EXPLAIN ANALYZE`
5. **С агентом:** попросите агента предложить схему по ER-диаграмме и написать тест на конкурентность; каждое ограничение проверьте, попытавшись его нарушить
