Почему БД — сердце приложения

  • Код переписывают каждые пару лет; данные живут десятилетиями
  • Баг в коде чинится деплоем; испорченные данные — иногда никак
База данных — последняя линия обороны. Что она не запрещает, однажды случится.

Моделирование данных

  • Сущности → таблицы, связи → внешние ключи (по ER-диаграмме из Модуля 1)
  • Ключи: суррогатный id bigint — по умолчанию; естественный (телефон, email) меняется — не делайте его первичным
  • Нормализация: каждый факт хранится в одном месте — нет противоречий при обновлении
  • Денормализация — осознанно, ради скорости чтения, с понятным способом держать копию актуальной

Не делайте

Время в timestamp без пояса, деньги во float, статусы «как придётся» строкой.

Делайте

timestamptz, деньги — numeric или целое в копейках, статус — с CHECK.

Схема «Slot»

CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE masters (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name      text NOT NULL,
  timezone  text NOT NULL DEFAULT 'Europe/Moscow'
);

CREATE TABLE slots (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  master_id  bigint NOT NULL REFERENCES masters(id),
  starts_at  timestamptz NOT NULL,
  ends_at    timestamptz NOT NULL
             CHECK (ends_at > starts_at),
  booked     boolean NOT NULL DEFAULT false,
  EXCLUDE USING gist (master_id WITH =,
    tstzrange(starts_at, ends_at) WITH &&)
);
CREATE TABLE bookings (
  id            bigint GENERATED ALWAYS AS IDENTITY
                PRIMARY KEY,
  slot_id       bigint NOT NULL REFERENCES slots(id),
  client_phone  text NOT NULL
    CHECK (client_phone ~ '^\+7[0-9]{10}$'),
  status        text NOT NULL DEFAULT 'confirmed'
    CHECK (status IN ('confirmed', 'cancelled',
                      'done', 'no_show')),
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE UNIQUE INDEX one_active_booking_per_slot
  ON bookings (slot_id)
  WHERE status <> 'cancelled';

Ограничения как бизнес-правила

Правило бизнесаОграничение в БД
У слота есть мастерREFERENCES masters(id)
Слот заканчивается после началаCHECK (ends_at > starts_at)
У мастера не пересекаются слотыEXCLUDE USING gist (... WITH &&)
Телефон в правильном форматеCHECK (client_phone ~ ...)
На слот не больше одной активной записиЧастичный UNIQUE ... WHERE status <> 'cancelled'
Статус — из спискаCHECK (status IN (...))

Частичный индекс важен: обычный UNIQUE (slot_id) запретил бы снова записаться на слот после отмены.

Транзакции и ACID

Atomicity

Всё или ничего: запись создана и слот занят — или ни то ни другое.

Consistency

После транзакции все ограничения выполняются.

Isolation

Параллельные транзакции не видят «половинок» друг друга.

Durability

Подтверждённое не пропадёт при падении сервера (WAL).

async with db.transaction():
    await mark_slot_booked(slot_id)
    booking = await insert_booking(slot_id, phone)
    await enqueue_notification(booking.id)   # outbox-таблица в той же транзакции

Гонка: «проверил, потом вставил»

if not await repo.slot_is_free(slot_id):      # оба клиента видят «свободен»
    raise SlotTaken()
await repo.insert_booking(slot_id, phone)     # оба вставляют → двойная запись

На ноутбуке с одним пользователем этот баг не воспроизвести. На запуске со скидкой он случится в первый же час.

Как закрыть гонку

1 · Ограничение + ошибка

try:
    await repo.insert_booking(
        slot_id, phone)
except IntegrityError:
    raise SlotTaken()  # 409

Самый надёжный: работает для любого кода, который пишет в БД.

2 · Условный UPDATE

UPDATE slots
SET booked = true
WHERE id = 42 AND NOT booked
RETURNING id;
-- 0 строк → занят

«Проверка и запись» одним атомарным запросом.

3 · Блокировка строки

SELECT * FROM slots
WHERE id = 42
FOR UPDATE;

Внутри транзакции: второй клиент ждёт, пока первый закончит.

Уровни изоляции в PostgreSQL

УровеньЧто гарантируетЦена
Read Committed (по умолчанию)Видны только подтверждённые данные; каждый запрос — свежий снимокВозможны потерянные обновления и гонки «проверил-вставил»
Repeatable ReadВся транзакция видит один снимокКонфликт записи → ошибка, нужен повтор
SerializableКак будто транзакции шли строго по очередиОшибки сериализации → код обязан повторять транзакцию
Read Committed + ограничения + условные UPDATE закрывают большинство задач. Serializable — для сложных инвариантов между многими строками и только с циклом повторов.

Индексы подробно

Составной: порядок важен

(master_id, starts_at) работает для master_id = 7 и master_id = 7 AND starts_at > now(), но не для одного starts_at.

Частичный и покрывающий

WHERE NOT booked — меньше и быстрее. INCLUDE (ends_at) — ответ прямо из индекса.

GIN и GiST

GIN — JSONB, полнотекстовый поиск, массивы. GiST — интервалы, геоданные.

Каждый индекс замедляет запись и занимает место; неиспользуемые ищите в pg_stat_user_indexes.

JSONB: гибкость внутри PostgreSQL

ALTER TABLE masters ADD COLUMN settings jsonb NOT NULL DEFAULT '{}';
SELECT * FROM masters WHERE settings @> '{"reminders": {"sms": true}}';
CREATE INDEX ON masters USING gin (settings);

Хорошо

Настройки, ответы внешних API, редкие необязательные атрибуты.

Плохо

То, по чему ищете, сортируете и связываете таблицы, — это колонки.

JSONB часто закрывает потребность «нам нужна MongoDB».

OLTP vs OLAP

OLTP · PostgreSQL

«Записать клиента на слот». Много коротких запросов по ключу. Хранение по строкам.

OLAP · ClickHouse

«Конверсия по мастерам за квартал». Мало тяжёлых запросов по всей таблице. Хранение по колонкам.

Тяжёлый аналитический запрос к продакшен-БД замедляет запись клиентов. Аналитику — на реплику или в колоночное хранилище.

БД и ИИ-агенты

  1. Доступ роль только на чтение и копия данных без персональной информации
  2. Миграции написанные агентом — через ревью и прогон на копии данных
  3. Ловушка агенты «упрощают» схему, удаляя неудобное ограничение — а ограничение и есть защита
  4. Никогда права на запись в продакшен-БД

Лабораторная работа

  1. Пересоберите схему «Slot»: внешние ключи, CHECK, EXCLUDE, частичный уникальный индекс
  2. Тест: 50 одновременных записей на один слот → проходит ровно одна, остальные получают 409
  3. Миграция без простоя во время нагрузочного теста — ноль упавших запросов
  4. Проверьте индексы через EXPLAIN ANALYZE
  5. С агентом: схема по ER-диаграмме и тест на конкурентность; каждое ограничение проверьте, попытавшись его нарушить
