## Выбор проекта

- **По умолчанию:** «Slot» — всё уже частично готово из лабораторных
- **Своя идея** — можно, если она сопоставима по размеру и согласована с преподавателем
- Хорошая своя идея: есть публичная страница, есть данные, есть процесс, есть реальная аудитория, которую вы знаете
- Плохая своя идея: «соцсеть для всех», «маркетплейс», что-то, что нельзя показать за 10 минут

> Маленький, но живой продукт лучше большого, но недоделанного.

## План работ

| Неделя | Фокус | Контрольная точка |
|---|---|---|
| 1 | Документация, модель данных, скелет фронта и бэка | `docs/` согласован, API отвечает |
| 2 | Функциональность, контракт API, тесты, ИИ-функция | Главный сценарий работает end-to-end |
| 3 | Контейнеры, проверка безопасности, деплой, мониторинг | Живой HTTPS-адрес, CI зелёный |
| 4 | Производительность, SEO, аналитика, запуск | Неделя реальных данных, отчёт |

Каждая контрольная точка — короткая демонстрация преподавателю. Проблемы видны рано.

## Работа с агентами на всём проекте

- `AGENTS.md` — с первого дня; обновляйте при каждом архитектурном решении
- Агент работает **от документации**: user story → тест → код
- Каждое изменение агента — через ревью и CI, как изменение человека
- Агенту — только тестовые секреты и staging; продакшен — ваши руки
- Ведите **журнал агента**: что поручили, что получилось, что пришлось исправлять

Журнал — часть защиты: он показывает, что вы управляли агентом, а не наоборот.

## Типичные провалы

| Провал | Как избежать |
|---|---|
| Красивая архитектура, ничего не работает | Сначала главный сценарий end-to-end, потом остальное |
| Деплой в последнюю ночь | Живой адрес к концу 3-й недели |
| Документация расходится с кодом | Обновлять в том же PR, что и код |
| Микросервисы и Kubernetes «потому что модно» | Монолит + Compose, если нет причины |
| Запуск без аналитики | Цели настроены до первого поста |
| Бэкап не проверяли | Восстановление — часть зачёта |

## Вопрос «×10 пользователей»

На защите будет вопрос: **что изменится, если пользователей станет в 10 раз больше?**

Хороший ответ опирается на цифры и называет **первое** узкое место:

- «Нагрузочный тест показал предел ~400 RPS на одном VPS; упрёмся в CPU API → вторая копия за балансировщиком, сессии уже в Redis»
- «Следующим станет БД: вынесем на управляемый PostgreSQL с репликой на чтение»
- «Kubernetes пока не нужен: два сервера спокойно обслуживает Compose»

Плохой ответ: «перепишем на микросервисы и Rust».

## Критерии оценки

| Критерий | Вес |
|---|---|
| Продукт работает на продакшене, главный сценарий без ошибок | 25% |
| Документация полная и соответствует коду | 15% |
| Архитектурные решения обоснованы (ADR, цифры) | 15% |
| Код, контракт API, целостность данных и тесты | 15% |
| Инфраструктура и безопасность: CI, HTTPS, бэкап, мониторинг, чек-лист OWASP | 15% |
| Запуск: аналитика, канал, честный разбор результатов | 15% |

Бонус: Kubernetes-манифесты, второй язык в бэкенде, сильный набор для eval ИИ-функции, интересный журнал агента.

## Итоги курса

- Приложение = фронтенд + бэкенд + инфраструктура + люди, которые о нём узнали
- Документация — контракт для людей и агентов
- Выбор технологий — по аргументам и цифрам, а не по моде
- Простое решение, которое работает, лучше сложного, которое «на вырост»
- Измеряйте всё: скорость, надёжность, воронку
