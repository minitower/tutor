Проблема: синхронизировать данные и экран

Вручную (jQuery-стиль)

slots = slots.filter(s => s.id !== id);
$('#slot-' + id).remove();
$('#free-count').text(slots.length);
if (slots.length === 0)
  $('#empty').show();
// забыли строку — экран врёт

Декларативно (фреймворк)

// описали, как экран зависит от данных
<p>Свободно: {slots.length}</p>
{slots.length === 0
  ? <Empty />
  : slots.map(s => <Slot slot={s} />)}
// DOM обновит фреймворк
Вы описываете, как экран зависит от данных, — фреймворк сам обновляет DOM.

Компоненты, props, состояние

function SlotList({ slots, onBook }) {            // props — вход
  const [selected, setSelected] = useState(null); // состояние
  if (slots.length === 0) return <p>Свободных слотов нет</p>;
  return (
    <ul>
      {slots.map(s => (
        <SlotItem key={s.id} slot={s}
          active={s.id === selected}
          onClick={() => setSelected(s.id)} />
      ))}
    </ul>
  );
}

UI = функция(состояние). Компонент — переиспользуемый кусок интерфейса.

Модели реактивности

Virtual DOM · React

Перерисовывает дерево в памяти и сравнивает со старым (diff), потом правит только разницу.

Сигналы · Vue, Solid, Angular

Запоминает, кто читал значение, и при изменении обновляет только их.

Компилятор · Svelte

Ещё на сборке превращает компонент в точечные обновления DOM. Почти нет рантайма.

Для пользователя разница обычно невидима; для размера бандла и скорости на слабых телефонах — заметна.

SPA vs SSR: что видит поисковик

SPA — пустая страница

<body>
  <div id="root"></div>
  <script src="app.js"></script>
</body>

Контент появится только после загрузки и выполнения JS.

SSR / SSG — готовый HTML

<body>
  <h1>Барбершоп «Борода»</h1>
  <li>Пт 15:00 — свободно</li>
</body>

JS потом «оживляет» страницу — это гидратация.

Поисковики умеют исполнять JS, но медленнее и не всегда. Для публичных страниц — SSR/SSG.

React Server Components

Серверные компоненты

Выполняются только на сервере: ходят в БД, не попадают в бандл браузера.

Клиентские ("use client")

Только там, где нужна интерактивность: кнопки, формы, календарь.

  • Плюс: меньше JS в браузере, данные без отдельного API-слоя
  • Цена: сложнее ментальная модель, нужен мета-фреймворк (Next.js)

Инструменты

  • Node.js — запускает инструменты сборки и серверный код
  • npm / pnpm — пакеты; package.json + lock-файл
  • Vite — дев-сервер с мгновенной перезагрузкой и сборка для продакшена
  • TypeScript — типы ловят ошибки до запуска; для агентов тоже подсказка
  • ESLint, Prettier — единый стиль
npm create vite@latest slot-admin -- --template react-ts

Стилизация

CSS-модули

Обычный CSS, имена классов изолированы. Просто и надёжно.

Tailwind

Утилитарные классы прямо в разметке. Быстро, однородно; популярно у агентов.

Библиотеки компонентов

shadcn/ui, MUI, Vuetify, Ant Design. Для админок: таблицы, формы, модалки готовы.

Для агентов важно одно: единые токены дизайна (цвета, отступы), иначе каждый экран будет в своём стиле.

Производительность фронтенда

LCP

Largest Contentful Paint — когда загрузилось главное. Цель: < 2,5 с.

INP

Interaction to Next Paint — отклик на действие. Цель: < 200 мс.

CLS

Cumulative Layout Shift — «прыжки» вёрстки. Цель: < 0,1.

  • Главный враг — размер JS: скачать, разобрать, выполнить
  • Приёмы: разбиение кода, ленивая загрузка, оптимизация картинок, меньше зависимостей
  • Lighthouse в DevTools — бесплатный аудит за минуту

Лабораторная работа

  1. Поднимите mock API по OpenAPI из Модуля 1 (например, Prism)
  2. Публичная страница «Slot»: SSR/SSG, услуги и свободные слоты, форма записи
  3. Админка: SPA, список записей, отмена записи
  4. Прогоните Lighthouse по обеим
  5. С агентом: дайте агенту user stories и токены дизайна, попросите собрать экраны админки; проверьте результат по критериям приёмки

Результат

  • Два фронтенда, работающих с mock API

  • ADR на одну страницу: «почему этот фреймворк»
