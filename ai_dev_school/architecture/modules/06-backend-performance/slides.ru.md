## Главное правило

> Не оптимизируйте то, что не измерили.

1. **Измерить** — нагрузочный тест, профиль
2. **Найти** узкое место — одно, самое большое
3. **Исправить** его
4. **Измерить снова** — подтвердить цифрами

Агент тоже должен следовать этому циклу: сначала гипотеза и данные, потом код.

## Задержка и пропускная способность

- **Задержка (latency)** — сколько ждёт один пользователь: мс на запрос
- **Пропускная способность (throughput)** — сколько запросов в секунду (RPS) выдерживает система
- Связаны, но не одно и то же: можно обслуживать 10 000 RPS, но каждый за 2 секунды
- Под нагрузкой задержка растёт: запросы начинают стоять в очереди

<!-- Slide 6 -->
## Почему среднее врёт

100 запросов: 98 по 50 мс, 2 по 5 000 мс

- **Среднее:** 149 мс — «всё хорошо»
- **p50 (медиана):** 50 мс — половина быстрее
- **p95:** 50 мс
- **p99:** 5 000 мс — каждый сотый ждёт 5 секунд

Смотрим **p95 и p99**: это опыт ваших самых недовольных пользователей. А у активного пользователя за сессию — десятки запросов, и он почти наверняка попадёт в хвост.

## I/O-bound vs CPU-bound

| | I/O-bound | CPU-bound |
|---|---|---|
| Где время | Ждём БД, сеть, диск | Считаем: картинки, отчёты, шифрование, ML |
| Доля веб-API | Подавляющее большинство | Редкие эндпоинты |
| Что помогает | Async, кэш, индексы, очереди | Другой алгоритм, процессы, Go/Rust, GPU |

Сначала определите, какой у вас случай, — решения противоположные.

## БД: индексы и EXPLAIN

```sql
EXPLAIN ANALYZE
SELECT * FROM slots WHERE master_id = 7 AND starts_at > now() AND NOT booked;

-- без индекса:
Seq Scan on slots  (actual time=0.02..182.4 rows=12)
  Rows Removed by Filter: 1999988

-- после CREATE INDEX ON slots (master_id, starts_at) WHERE NOT booked:
Index Scan using slots_master_starts_idx  (actual time=0.03..0.09 rows=12)
```

Seq Scan по большой таблице в горячем запросе — первый подозреваемый.

## Проблема N+1

```python
masters = session.query(Master).all()          # 1 запрос
for m in masters:
    print(m.name, len(m.slots))                # + N запросов, по одному на мастера
```

100 мастеров = 101 запрос. Каждый быстрый, вместе — секунда.

```python
masters = session.query(Master).options(selectinload(Master.slots)).all()  # 2 запроса
```

ORM скрывает запросы — включайте логирование SQL в разработке.

## Пул соединений и реплики

- Открыть соединение с PostgreSQL — дорого (десятки мс, память на сервере)
- **Пул соединений** переиспользует открытые соединения (встроен в SQLAlchemy, pgx; снаружи — PgBouncer)
- Слишком много соединений — БД тратит память на них вместо данных
- **Реплики на чтение** — копии БД для SELECT-запросов, когда основная не справляется

<!-- Slide 14 -->
## Кэш в приложении: cache-aside

```python
async def free_slots(master_id: int):
    key = f"free_slots:{master_id}"
    if cached := await redis.get(key):
        return json.loads(cached)
    slots = await repo.free_slots(master_id)
    await redis.set(key, json.dumps(slots), ex=30)   # TTL 30 секунд
    return slots

# при записи на слот:
await redis.delete(f"free_slots:{master_id}")        # инвалидация
```

Две сложности: **инвалидация** (когда данные устарели) и **TTL** (сколько можно показывать старое).

## Масштабирование

| | Вертикальное | Горизонтальное |
|---|---|---|
| Как | Больше CPU и памяти на одном сервере | Больше копий приложения за балансировщиком |
| Просто? | Очень — сменить тариф | Нужен stateless-код |
| Предел | Самый большой сервер | Почти нет (кроме БД) |

**Stateless:** приложение не хранит ничего между запросами в памяти процесса. Сессии, файлы, кэш — в Redis, S3, БД.

## Когда язык действительно важен

- CPU-задачи: обработка изображений и видео, криптография, парсинг больших файлов, симуляции
- Огромный RPS при тонкой логике: прокси, шлюзы, биржи
- Жёсткие требования к памяти и задержке: p99 < 5 мс
- Решения: вынести горячий участок в сервис на Go/Rust, расширение на Rust для Python (PyO3), готовые нативные библиотеки (NumPy, Polars)

Переписывают **горячий участок**, а не всё приложение.

## Честные бенчмарки

- **Прогрев:** первые запросы медленнее (кэши, JIT, пул соединений)
- **Реалистичные данные:** 10 строк в БД быстрые всегда, проверяйте на миллионах
- **Одинаковое железо** и одинаковые настройки
- **Реалистичный сценарий:** не только GET одной страницы
- **Генератор нагрузки** не на том же сервере, что и приложение
- Сравниваем p95/p99, а не среднее

## Лабораторная работа

1. Заполните БД «Slot» реалистичными данными: 1 000 мастеров, 2 млн слотов
2. Нагрузочный тест k6 или Locust: запишите p95 и RPS

5. Измерьте снова
6. **С агентом:** дайте агенту отчёт теста и вывод `EXPLAIN`; попросите сначала гипотезу, потом код; подтвердите исправление цифрами
