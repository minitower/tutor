Задержка и пропускная способность

Задержка (latency)

Сколько ждёт один пользователь: миллисекунды на запрос.

Пропускная способность (throughput)

Сколько запросов в секунду (RPS) выдерживает система.

  • Связаны, но не одно и то же: можно обслуживать 10 000 RPS, но каждый за 2 секунды
  • Под нагрузкой задержка растёт: запросы начинают стоять в очереди

Почему среднее врёт

100 запросов: 98 по 50 мс и 2 по 5 000 мс

Смотрим p95 и p99. У активного пользователя за сессию десятки запросов — он почти наверняка попадёт в хвост.

Куда на самом деле уходит время

Типичный запрос к API «Slot», 482 мс:

  • Язык — 1,7 мс. БД и сеть — 480 мс
  • Переписывание на Rust сэкономит ~1 мс; индекс и очередь — почти всё остальное

БД: индексы и EXPLAIN

EXPLAIN ANALYZE
SELECT * FROM slots WHERE master_id = 7 AND starts_at > now() AND NOT booked;

-- без индекса:
Seq Scan on slots  (actual time=0.02..182.4 rows=12)
  Rows Removed by Filter: 1999988

-- после CREATE INDEX ON slots (master_id, starts_at) WHERE NOT booked:
Index Scan using slots_master_starts_idx  (actual time=0.03..0.09 rows=12)

Seq Scan по большой таблице в горячем запросе — первый подозреваемый. 182 мс → 0,09 мс.

Каждый запрос быстрый, вместе — секунда. ORM скрывает запросы — включайте логирование SQL в разработке.

Кэш в приложении: cache-aside

async def free_slots(master_id: int):
    key = f"free_slots:{master_id}"
    if cached := await redis.get(key):                 # попали в кэш
        return json.loads(cached)
    slots = await repo.free_slots(master_id)           # промах → БД
    await redis.set(key, json.dumps(slots), ex=30)     # TTL 30 секунд
    return slots

# при записи на слот:
await redis.delete(f"free_slots:{master_id}")          # инвалидация

Две сложности: инвалидация (когда данные устарели) и TTL (сколько можно показывать старое).

Масштабирование

Вертикальное

Больше CPU и памяти на одном сервере. Очень просто — сменить тариф. Предел — самый большой сервер.

Горизонтальное

Больше копий приложения за балансировщиком. Почти без предела (кроме БД). Требует stateless-кода.

Stateless: приложение не хранит ничего между запросами в памяти процесса. Сессии, файлы, кэш — в Redis, S3, БД.

Когда язык действительно важен

  • CPU-задачи: изображения и видео, криптография, парсинг больших файлов, симуляции
  • Огромный RPS при тонкой логике: прокси, шлюзы, биржи
  • Жёсткие требования к памяти и задержке: p99 < 5 мс

Честные бенчмарки

  1. Прогрев первые запросы медленнее: кэши, JIT, пул соединений
  2. Данные 10 строк в БД быстрые всегда — проверяйте на миллионах
  3. Железо одинаковое железо и одинаковые настройки
  4. Сценарий реалистичный, не только GET одной страницы
  5. Ловушка генератор нагрузки на том же сервере, что и приложение
  6. Метрики сравниваем p95/p99, а не среднее

Лабораторная работа

  1. Заполните БД «Slot» реалистичными данными: 1 000 мастеров, 2 млн слотов
  2. Нагрузочный тест k6 или Locust: запишите p95 и RPS
  3. Найдите узкое место: EXPLAIN ANALYZE, профайлер, логи SQL
  4. Исправьте: индекс, кэш свободных слотов, уведомления в очередь; измерьте снова
  5. С агентом: дайте агенту отчёт теста и вывод EXPLAIN; попросите сначала гипотезу, потом код; подтвердите исправление цифрами
