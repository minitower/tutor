Три слоя приложения

Фронтенд · зал ресторана

Интерфейс и реакция на действия пользователя. Работает в браузере или на телефоне.

Бэкенд · кухня

Бизнес-логика, данные, права доступа. Работает на сервере, пользователь его не видит.

Инфраструктура · здание

Серверы, сеть, базы данных, деплой, мониторинг. Без неё нет ни зала, ни кухни.

Гость видит только зал — но без кухни и здания ресторана нет.

Модель клиент–сервер

  • Клиенту нельзя доверять: всё пришедшее сервер проверяет заново
  • Данные живут на сервере — клиент получает только копию для показа

Жизнь запроса: https://slot.example/booking

Синие шаги — сеть, розовые — входная точка инфраструктуры, зелёные — ваше приложение.

Шаг 3: TCP + TLS

TCP

Надёжная доставка байтов: рукопожатие, порядок пакетов, повторная отправка потерянных.

TLS

Шифрование и проверка, что сервер — тот, за кого себя выдаёт. Замок в адресной строке = валидный сертификат.

HTTP/2 и HTTP/3 (QUIC) сокращают число рукопожатий и ускоряют загрузку.

Шаги 4–5: CDN и reverse proxy

  • CDN — кэширует статику близко к пользователю
  • Reverse proxy (Nginx, Caddy) — единая входная точка; балансировщик раздаёт запросы копиям приложения

Почему фронтенд — это JavaScript

  • Браузер умеет исполнять только HTML, CSS, JavaScript (+ WebAssembly)
  • TypeScript — JavaScript с типами; компилируется в обычный JS
  • React, Vue, Svelte — всё это в итоге JS в браузере
  • WebAssembly запускает в браузере Rust, C++, Go — для тяжёлых задач (Figma, видео, игры)

Почему бэкенд — это любой язык

Сервер — это ваш компьютер, на нём можно запустить что угодно. Выбор определяют экосистема, скорость, команда, рынок найма.

GoПростота, производительность, один бинарник
JavaScript / TypeScriptОдин язык на фронте и бэке
RustМаксимум скорости и безопасности памяти
Java / Kotlin, C#Энтерпрайз, большие команды

Инфраструктура и её языки

Где запускать

VPS, облако, Kubernetes, PaaS.

Как упаковывать

Docker: Dockerfile → образ → контейнер.

Как описывать

YAML (Compose, Kubernetes, CI), HCL (Terraform), Bash.

Инфраструктура описана в файлах в репозитории, а не «настроена руками когда-то».

Архитектурные стили

СтильСутьПлюсыМинусы
МонолитОдно приложение, один деплойПросто, быстроРастёт в «большой ком»
Модульный монолитОдин деплой, чёткие модули внутриПростота + порядокНужна дисциплина
МикросервисыМного сервисов, у каждого свой деплойНезависимые команды и масштабСеть, сложность, дорого
ServerlessФункции, которые запускает облакоНет серверов, оплата за вызовХолодный старт, привязка к вендору
Сначала монолит. Резать — когда больно, а не когда модно.

Микросервисы решают организационную проблему — много команд мешают друг другу. У стартапа из 1–5 человек её нет.

Модульный монолит

Легко разрезать потом по готовым границам модулей.

Ранние микросервисы

Каждый сетевой вызов — новая точка отказа; склеить обратно трудно.

Где в этой картине ИИ

LLM как зависимость

Claude, GPT и др. — внешний API, как платёжный шлюз. Медленно и дорого → очереди, кэш, лимиты, таймауты.

Агент как клиент

Читает ваш API и документацию, вызывает инструменты через MCP.

Агент как разработчик

Пишет код по вашей документации. Поэтому в каждой лабораторной курса есть шаг «С агентом».

Проект курса: «Slot»

Онлайн-запись для маленького бизнеса — барбершоп, репетитор, переговорка.

Каждый модуль добавляет к «Slot» один слой — к концу курса он работает на вашем домене.

Лабораторная работа

  1. Откройте DevTools → вкладка Network на реальном сайте (маркетплейс, новости)
  2. Обновите страницу, сохраните трассу (HAR)
  3. Найдите: HTML-документ, статику с CDN, API-запросы, самый медленный запрос
  4. Нарисуйте архитектуру, которую можно восстановить снаружи
  5. С агентом: дайте агенту HAR-файл, попросите объяснить каждый запрос; найдите, где он ошибся

Результат

  • Размеченная трасса запросов с комментариями
  • Схема архитектуры изученного сайта
  • Первая блок-схема «Slot»: клиент → API → БД, уведомления
  • Список ошибок агента и почему он их сделал

Далее: Документация проекта
