## Три слоя приложения

| Слой | Что делает | Где работает | Аналогия |
|---|---|---|---|
| **Фронтенд** | Показывает интерфейс, реагирует на клики | Браузер, телефон | Зал ресторана |
| **Бэкенд** | Бизнес-логика, данные, права доступа | Сервер | Кухня |
| **Инфраструктура** | Серверы, сеть, БД, деплой, мониторинг | Дата-центр / облако | Здание, электричество, водопровод |

Гость видит только зал — но без кухни и здания ресторана нет.

<!-- Slide 5 -->
## Модель клиент–сервер

- **Клиент** спрашивает: браузер, мобильное приложение, другой сервис, ИИ-агент
- **Сервер** отвечает: проверяет права, выполняет логику, читает и пишет данные
- Клиенту **нельзя доверять**: всё, что пришло от клиента, сервер проверяет заново
- Данные живут на сервере — клиент получает только копию для показа

---

<!-- Slide 6 -->
## Жизнь запроса: https://slot.example/booking

1. **URL** → браузер разбирает схему, домен, путь
2. **DNS** → домен превращается в IP-адрес
3. **TCP + TLS** → соединение и шифрование
4. **CDN** → статика отдаётся с ближайшего узла
5. **Балансировщик / reverse proxy** → выбирает сервер приложения
6. **API** → проверка прав, бизнес-логика
7. **БД / кэш / очередь** → данные
8. **Ответ** → JSON или HTML обратно
9. **Рендеринг** → браузер рисует пиксели

---

<!-- Slide 7 -->
## Шаг 2: DNS — телефонная книга интернета

- `slot.example` → `203.0.113.10`
- Резолвер спрашивает по цепочке: корневые серверы → `.example` → NS-серверы домена
- Ответ кэшируется на время **TTL**
- Поэтому смена DNS «доезжает» не сразу

Подробно разберём в Модуле 11, когда будем подключать свой домен.

---

<!-- Slide 8 -->
## Шаг 3: TCP + TLS

- **TCP** — надёжная доставка байтов: рукопожатие, порядок, повторная отправка
- **TLS** — шифрование и проверка, что сервер действительно тот, за кого себя выдаёт
- Замок в адресной строке = валидный TLS-сертификат
- HTTP/2 и HTTP/3 (QUIC) сокращают число рукопожатий и ускоряют загрузку

---

<!-- Slide 9 -->
## Шаги 4–5: CDN и reverse proxy

- **CDN** — сеть серверов по миру, кэширует картинки, JS, CSS близко к пользователю
- **Reverse proxy** (Nginx, Caddy) — единая входная точка: TLS, маршрутизация, сжатие
- **Балансировщик** распределяет запросы между несколькими копиями приложения
- Пользователь видит один адрес — за ним может быть десяток серверов

---

<!-- Slide 10 -->
## Шаги 6–7: API и данные

- **API** — контракт: какие запросы можно делать и что вернётся
- Внутри: роутинг → валидация → авторизация → бизнес-логика → доступ к данным
- **БД** хранит состояние (PostgreSQL, MySQL, MongoDB)
- **Кэш** (Redis) — быстрые ответы на частые вопросы
- **Очередь** — долгие задачи в фоне: письма, уведомления, отчёты

## HTTP за одну минуту

```
POST /api/bookings HTTP/1.1
Host: slot.example
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...

{"slot_id": 42, "client_name": "Анна"}
```

```
HTTP/1.1 201 Created
Content-Type: application/json

{"id": 1017, "status": "confirmed"}
```

Методы: GET, POST, PUT/PATCH, DELETE · Коды: 2xx успех, 3xx редирект, 4xx ошибка клиента, 5xx ошибка сервера

## Способы общения клиента и сервера

| Протокол | Как работает | Когда использовать |
|---|---|---|
| **REST** | HTTP + JSON, ресурсы и методы | По умолчанию для публичных API |
| **GraphQL** | Клиент сам описывает, какие поля нужны | Сложный фронтенд, много связанных данных |
| **WebSocket** | Постоянное двустороннее соединение | Чаты, уведомления в реальном времени |
| **gRPC** | Бинарный протокол, строгая схема (protobuf) | Общение сервисов между собой |

<!-- Slide 13 -->
## Почему фронтенд — это JavaScript

- Браузер умеет исполнять только **HTML, CSS, JavaScript** (+ **WebAssembly**)
- **TypeScript** — JavaScript с типами; компилируется в обычный JS
- React, Vue, Svelte — всё это в итоге JS в браузере
- WebAssembly позволяет запускать в браузере Rust, C++, Go — для тяжёлых задач (Figma, видео, игры)
- Мобильные клиенты: Swift (iOS), Kotlin (Android) или кроссплатформенно — React Native, Flutter

---

<!-- Slide 14 -->
## Почему бэкенд — это любой язык

Сервер — это ваш компьютер, на нём можно запустить что угодно. Выбор определяют:

| Язык | Сильная сторона |
|---|---|
| Python | Скорость разработки, ИИ/ML-экосистема |
| Go | Простота, производительность, один бинарник |
| JavaScript/TypeScript | Один язык на фронте и бэке |
| Rust | Максимум скорости и безопасности памяти |
| Java/Kotlin, C# | Энтерпрайз, большие команды |

## Инфраструктура и её языки

- **Где запускать:** VPS, облако, Kubernetes, PaaS
- **Как упаковывать:** Docker (`Dockerfile`)
- **Как описывать:** конфигурация как код — **YAML** (Compose, Kubernetes, CI), **HCL** (Terraform), **Bash**
- **Как следить:** логи, метрики, алерты
- Принцип: инфраструктура описана в файлах в репозитории, а не «настроена руками когда-то»

<!-- Slide 16 -->
## Архитектурные стили

| Стиль | Суть | Плюсы | Минусы |
|---|---|---|---|
| **Монолит** | Одно приложение, один деплой | Просто, быстро | Растёт в «большой ком» |
| **Модульный монолит** | Один деплой, чёткие модули внутри | Простота + порядок | Нужна дисциплина |
| **Микросервисы** | Много сервисов, каждый со своим деплоем | Независимые команды и масштаб | Сеть, сложность, дорого |
| **Serverless** | Функции, которые запускает облако | Нет серверов, платишь за вызов | Холодный старт, привязка к вендору |

---

<!-- Slide 17 -->
## Почему начинать с монолита

- Микросервисы решают **организационную** проблему: много команд мешают друг другу
- У стартапа из 1–5 человек такой проблемы нет
- Каждый сетевой вызов между сервисами — новая точка отказа
- Хороший модульный монолит легко разрезать потом; плохие микросервисы трудно склеить обратно

> Сначала монолит. Резать — когда больно, а не когда модно.

## Где в этой картине ИИ

- **LLM API** (Claude, GPT и др.) — ещё одна внешняя зависимость бэкенда, как платёжный шлюз
- Вызовы LLM медленные и дорогие → очереди, кэш, лимиты, таймауты
- **ИИ-агенты как клиенты**: читают ваш API, документацию, вызывают инструменты (MCP)
- **ИИ-агенты как разработчики**: пишут код по вашей документации — поэтому в этом курсе у каждой лабораторной есть шаг «С агентом»

<!-- Slide 19 -->
## Проект курса: «Slot»

Онлайн-запись для маленького бизнеса — барбершоп, репетитор, переговорка.

- Публичная страница: услуги и свободные слоты (нужно SEO)
- Клиент бронирует слот
- Админ-панель для владельца
- Уведомления о записи

Каждый модуль добавляет к «Slot» один слой — к концу курса он работает на вашем домене.

## Лабораторная работа

1. Откройте DevTools → вкладка **Network** на реальном сайте (маркетплейс, новости)
2. Обновите страницу, сохраните трассу (**HAR**)
3. Найдите: HTML-документ, статику с CDN, API-запросы, самый медленный запрос
4. Нарисуйте архитектуру, которую можно восстановить снаружи
5. **С агентом:** дайте агенту HAR-файл, попросите объяснить каждый запрос; найдите, где он ошибся
