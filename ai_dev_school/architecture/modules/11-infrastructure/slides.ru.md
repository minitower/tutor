## Варианты хостинга

| Вариант | Что вы получаете | Контроль | Ваша работа | Цена старта |
|---|---|---|---|---|
| Виртуальный хостинг | Папка для PHP-сайта | Минимум | Почти нет | Копейки |
| **VPS** | Виртуальный сервер с root | Полный | ОС, безопасность, обновления | ~5–10 $/мес |
| **PaaS** | «Дай код — запущу» | Средний | Только код | Бесплатно–20 $ |
| **IaaS-облако** | Конструктор: сети, ВМ, БД, хранилища | Полный | Много | От единиц $ |
| **Serverless** | Функции по вызову | Минимум | Код функций | Платите за вызовы |

## Что выбрать для первого проекта

- **Фронтенд-статика / Next.js** → PaaS (Vercel, Netlify, Cloudflare Pages) — бесплатно и быстро
- **Всё приложение в Compose** → один VPS — дёшево, понятно, всему научит
- **Не хотите администрировать** → PaaS для контейнеров (Render, Fly.io, Railway)
- **Растёте, нужны управляемые сервисы** → облако (Yandex Cloud, Selectel, AWS, GCP)

Для «Slot» в курсе: **VPS + Docker Compose** — чтобы увидеть каждый слой своими руками.

## Сервер с нуля: первые 15 минут

```bash
# 1. Вход по SSH-ключу, а не паролю
ssh-copy-id root@203.0.113.10

# 2. Отдельный пользователь
adduser deploy && usermod -aG sudo,docker deploy

# 3. Запретить вход root и по паролю (/etc/ssh/sshd_config)
PermitRootLogin no
PasswordAuthentication no

# 4. Файрвол: только SSH, HTTP, HTTPS
ufw allow OpenSSH && ufw allow 80,443/tcp && ufw enable

# 5. Автоматические обновления безопасности
apt install unattended-upgrades fail2ban
```

## Домены и DNS

- Покупаете домен у **регистратора** (Reg.ru, Namecheap, Cloudflare)
- **NS-записи** говорят, какие DNS-серверы отвечают за домен
- На этих серверах — ваши записи:

| Запись | Пример | Зачем |
|---|---|---|
| **A / AAAA** | `slot.example → 203.0.113.10` | Домен → IPv4 / IPv6 |
| **CNAME** | `www → slot.example` | Псевдоним другого имени |
| **MX** | `→ mx.yandex.net` | Куда доставлять почту |
| **TXT** | `v=spf1 …`, верификация | SPF/DKIM, подтверждение владения |

**TTL** — сколько секунд ответ кэшируется. Перед переездом уменьшите TTL заранее.

<!-- Slide 8 -->
## Как работает разрешение имени

1. Браузер спрашивает **рекурсивный резолвер** (провайдер, 1.1.1.1, 8.8.8.8, 77.88.8.8)
2. Резолвер → **корневой сервер**: «кто отвечает за `.example`?»
3. → **сервер зоны `.example`**: «кто отвечает за `slot.example`?» → NS-записи
4. → **ваш DNS-сервер**: «A-запись `slot.example`?» → `203.0.113.10`
5. Резолвер кэширует ответ на TTL и отдаёт браузеру

Проверка: `dig slot.example` или `nslookup slot.example`

## HTTPS: почему обязателен

- Без TLS любой в сети (Wi-Fi в кафе, провайдер) видит и может подменить трафик
- Браузеры помечают HTTP-сайты как «Не защищено»
- Поисковики понижают HTTP-сайты
- Современные API браузера (геолокация, PWA, service workers) работают только по HTTPS

**Let's Encrypt** — бесплатные сертификаты на 90 дней, продление автоматически (certbot, Caddy, cert-manager).

## Reverse proxy: один вход, много сервисов

```
# Caddyfile — HTTPS-сертификат выпустится сам
slot.example {
    handle /api/* {
        reverse_proxy api:8000
    }
    handle {
        reverse_proxy web:3000
    }
}
```

| Прокси | Чем хорош |
|---|---|
| **Caddy** | Автоматический HTTPS, короткий конфиг |
| **Nginx** | Классика, максимум возможностей и примеров |
| **Traefik** | Сам находит контейнеры по меткам Docker |

## Строительные блоки облака

| Блок | Что это | Примеры |
|---|---|---|
| **VPC, подсети** | Ваша изолированная сеть | Все облака |
| **ВМ** | Виртуальные серверы | Compute Cloud, EC2 |
| **Управляемая БД** | PostgreSQL с бэкапами и репликами «под ключ» | Managed PostgreSQL, RDS |
| **Объектное хранилище** | Файлы по HTTP, S3-совместимое API | Object Storage, S3 |
| **CDN** | Кэш статики по миру | Cloud CDN, CloudFront |
| **Балансировщик** | Распределение трафика | ALB, Network LB |
| **IAM** | Кто и что может делать в облаке | Сервисные аккаунты, роли |

## Схема «Slot», когда проект вырос

```
Пользователь → DNS → CDN (статика)
                   → Балансировщик → 2+ ВМ с API (в приватной подсети)
                                       → Managed PostgreSQL
                                       → Managed Redis
                                       → Object Storage (файлы, бэкапы)
```

- API-серверы без публичных IP — снаружи только балансировщик
- БД доступна только из приватной подсети
- Всё описано в Terraform

## CI/CD: от push до продакшена

```yaml
# .github/workflows/deploy.yml
on: { push: { branches: [main] } }
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker compose run --rm api pytest
      - run: |
          echo "${{ secrets.GHCR_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin
          docker build -t ghcr.io/school/slot-api:${{ github.sha }} ./api
          docker push ghcr.io/school/slot-api:${{ github.sha }}
      - run: ssh deploy@slot.example "cd slot && TAG=${{ github.sha }} docker compose up -d"
```

**CI** — проверить каждое изменение. **CD** — автоматически доставить проверенное.

## Окружения

| Окружение | Для чего | Данные |
|---|---|---|
| **local** | Разработка | Тестовые |
| **staging** | Проверка перед релизом, копия продакшена | Обезличенные |
| **production** | Реальные пользователи | Настоящие |

Правило: один и тот же **образ** проходит staging → production; отличаются только переменные окружения.

## Секреты

- **Никогда в git** — даже в приватном репозитории; бот найдёт ключ за минуты после утечки
- `.env` в `.gitignore`, в репозитории — `.env.example` без значений
- В CI — **секреты CI** (GitHub Actions secrets)
- В облаке — **менеджер секретов** (Lockbox, Secrets Manager, Vault)
- Утёк ключ → **отозвать и выпустить новый**, а не просто удалить коммит
- Агенту — только тестовые ключи, никогда продакшен

<!-- Slide 16 -->
## Бэкапы

- **Что:** БД (обязательно), загруженные файлы, конфиги
- **Как:** `pg_dump` по расписанию или встроенные бэкапы управляемой БД
- **Куда:** в **другое место** — объектное хранилище, другой регион
- **Правило 3-2-1:** 3 копии, 2 разных носителя, 1 — в другом месте

> Бэкап, который ни разу не восстанавливали, не существует.

Раз в месяц: поднять копию из бэкапа и проверить, что данные на месте.

## Инфраструктура как код

```hcl
resource "yandex_compute_instance" "app" {
  name        = "slot-app"
  platform_id = "standard-v3"
  resources {
    cores  = 2
    memory = 4
  }
  boot_disk { initialize_params { image_id = "fd8…ubuntu-24-04" } }
  network_interface { subnet_id = yandex_vpc_subnet.private.id }
}
```

- **Terraform / OpenTofu** — описать ресурсы облака: `plan` показывает изменения, `apply` применяет
- **Ansible** — настроить серверы: пакеты, пользователи, конфиги
- Инфраструктура воспроизводима, ревьюится в PR, не «настроена руками когда-то»

## Деньги

- Включите **бюджетные алерты** в облаке в первый же день
- Типичные утечки: забытые ВМ и диски, исходящий трафик, NAT-шлюзы, логи без срока хранения
- Начинайте с маленького и масштабируйте по метрикам, а не «на вырост»
- Бесплатные уровни (free tier) имеют лимиты — читайте условия

## Лабораторная работа

1. Арендуйте VPS, настройте SSH-ключи, пользователя, файрвол
2. Купите домен (или возьмите поддомен), направьте A-запись на VPS
3. Разверните «Slot» через Compose за Caddy с HTTPS
4. Настройте деплой из GitHub Actions при push в `main`
5. Ночной бэкап БД в объектное хранилище — **и восстановите из него**
6. Проверка доступности с уведомлением
7. **С агентом:** попросите агента написать CI-workflow и чек-лист защиты сервера; выполняйте команды сами, продакшен-секреты агенту не давайте
