Сервер с нуля: первые 15 минут

# 1. Вход по SSH-ключу, а не паролю
ssh-copy-id root@203.0.113.10
# 2. Отдельный пользователь
adduser deploy && usermod -aG sudo,docker deploy
# 3. Запретить вход root и по паролю (/etc/ssh/sshd_config)
PermitRootLogin no
PasswordAuthentication no
# 4. Файрвол: только SSH, HTTP, HTTPS
ufw allow OpenSSH && ufw allow 80,443/tcp && ufw enable
# 5. Автоматические обновления безопасности
apt install unattended-upgrades fail2ban

Сервер с открытым SSH по паролю начинают перебирать боты через минуты после создания.

Домены и DNS

Домен покупают у регистратора (Reg.ru, Namecheap, Cloudflare); NS-записи указывают, какие DNS-серверы отвечают за домен.

ЗаписьПримерЗачем
A / AAAAslot.example → 203.0.113.10Домен → IPv4 / IPv6
CNAMEwww → slot.exampleПсевдоним другого имени
MX→ mx.yandex.netКуда доставлять почту
TXTv=spf1 …, верификацияSPF/DKIM, подтверждение владения

TTL — сколько секунд ответ кэшируется. Перед переездом уменьшите TTL заранее.

Как работает разрешение имени

Проверка: dig slot.example или nslookup slot.example

HTTPS: почему обязателен

  1. Безопасность без TLS трафик видит и может подменить любой в сети — Wi-Fi в кафе, провайдер
  2. Доверие браузеры помечают HTTP-сайты как «Не защищено»
  3. SEO поисковики понижают HTTP-сайты
  4. Функции геолокация, PWA, service workers работают только по HTTPS
Let's Encrypt — бесплатные сертификаты на 90 дней с автоматическим продлением (certbot, Caddy, cert-manager).

Reverse proxy: один вход, много сервисов

# Caddyfile — HTTPS выпустится сам
slot.example {
    handle /api/* {
        reverse_proxy api:8000
    }
    handle {
        reverse_proxy web:3000
    }
}

Деплой
on: { push: { branches: [main] } }
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker compose run --rm api pytest
      - run: |
          echo "${{ secrets.GHCR_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin
          docker build -t ghcr.io/school/slot-api:${{ github.sha }} ./api
          docker push ghcr.io/school/slot-api:${{ github.sha }}
      - run: ssh deploy@slot.example "cd slot && TAG=${{ github.sha }} docker compose up -d"

Секреты

  1. Никогда в git — даже в приватном; бот найдёт ключ за минуты после утечки
  2. Локально .env в .gitignore, в репозитории — .env.example без значений
  3. CI секреты CI (GitHub Actions secrets)
  4. Облако менеджер секретов: Lockbox, Secrets Manager, Vault
  5. Утечка отозвать и выпустить новый ключ, а не просто удалить коммит
  6. Агент только тестовые ключи, никогда продакшен

Бэкапы

Что

БД — обязательно; загруженные файлы, конфиги.

Как

pg_dump по расписанию или встроенные бэкапы управляемой БД.

Куда

В другое место: объектное хранилище, другой регион. Правило 3-2-1.

Бэкап, который ни разу не восстанавливали, не существует. Раз в месяц — поднять копию и проверить данные.

Ansible

Настройка серверов: пакеты, пользователи, конфиги.

Деньги

  • Включите бюджетные алерты в облаке в первый же день
  • Типичные утечки: забытые ВМ и диски, исходящий трафик, NAT-шлюзы, логи без срока хранения
  • Начинайте с маленького и масштабируйте по метрикам, а не «на вырост»
  • Бесплатные уровни (free tier) имеют лимиты — читайте условия

Лабораторная работа

  1. Арендуйте VPS, настройте SSH-ключи, пользователя, файрвол
  2. Купите домен (или возьмите поддомен), направьте A-запись на VPS
  3. Разверните «Slot» через Compose за Caddy с HTTPS
  4. Деплой из GitHub Actions при push в main
  5. Ночной бэкап БД в объектное хранилище — и восстановите из него; проверка доступности с уведомлением
  6. С агентом: попросите написать CI-workflow и чек-лист защиты сервера; команды выполняйте сами, продакшен-секреты агенту не давайте

Результат

  • Живой адрес https://… с валидным сертификатом
  • CI-пайплайн: тесты → образ → деплой
  • Доказательство успешного восстановления из бэкапа
  • Скриншот алерта о недоступности (выключите API и дождитесь уведомления)
