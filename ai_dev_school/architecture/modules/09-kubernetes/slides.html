Проблема: серверов 10, контейнеров 200

  1. Размещение на какой сервер поставить новый контейнер?
  2. Сбой сервер упал — кто перезапустит его контейнеры на другом?
  3. Обновление как выкатить версию без простоя?
  4. Поиск как сервисам найти друг друга, если IP меняются?
  5. Нагрузка как масштабировать вверх и обратно?

Оркестратор решает всё это автоматически. Kubernetes (k8s) — стандарт де-факто.

Главная идея: желаемое состояние

  • Не «запусти контейнер», а «должно работать 3 копии API версии 1.4»
  • Kubernetes постоянно сравнивает желаемое с реальным и устраняет разницу
  • Упал под → реальное 2, желаемое 3 → создаётся новый

Декларативно, как SQL: описываем что, а не как.

Архитектура кластера

Что происходит при kubectl apply

  1. kubectl отправляет манифест в API server
  2. API server проверяет и сохраняет его в etcd
  3. Контроллер нужно 3 пода, есть 0 → создаёт 3 объекта Pod
  4. Scheduler видит поды без узла → назначает каждому узел
  5. kubelet видит назначенный под → просит containerd запустить контейнер
  6. kubelet докладывает статус → API server → etcd

Никто никого не вызывает напрямую — все смотрят на состояние в API server.

Deployment

apiVersion: apps/v1
kind: Deployment
metadata: { name: slot-api }
spec:
  replicas: 3                                  # желаемое состояние
  selector: { matchLabels: { app: slot-api } }
  template:
    metadata: { labels: { app: slot-api } }
    spec:
      containers:
        - name: api
          image: ghcr.io/school/slot-api:1.4.0   # не latest
          ports: [{ containerPort: 8000 }]
          envFrom: [{ secretRef: { name: slot-secrets } }]
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { memory: 512Mi }
          readinessProbe: { httpGet: { path: /health, port: 8000 } }

Вход снаружи: Ingress и Gateway API

  • Ingress — правила HTTP-маршрутизации; работает через контроллер (ingress-nginx, Traefik)
  • Gateway API — более новый и гибкий преемник Ingress
  • cert-manager выпускает TLS-сертификаты Let's Encrypt автоматически

Конфигурация и хранилище

ConfigMap

Несекретные настройки: адреса, флаги.

Secret

Пароли, токены. По умолчанию это base64, а не шифрование: нужны шифрование etcd, RBAC, Vault / External Secrets.

PersistentVolume

Кусок диска в кластере.

PersistentVolumeClaim

Запрос пода: «мне нужно 10 ГБ»; облако выдаёт диск само (StorageClass).

Надёжность: пробы

ПробаВопросЕсли провалена
livenessПроцесс жив?Перезапустить контейнер
readinessГотов принимать трафик?Убрать под из Service, не убивать
startupУже запустился?Не проверять остальные пробы, пока не стартовал

Типичная ошибка

liveness проверяет БД → БД моргнула → Kubernetes перезапускает все поды API.

Правильно

liveness — только «процесс отвечает»; зависимость от БД — в readiness.

Надёжность: ресурсы и масштабирование

  • requests — сколько гарантировано; по ним scheduler выбирает узел
  • limits — потолок; превысил память → контейнер убит (OOMKilled)
  • HPA — меняет число реплик по CPU, памяти или своим метрикам
  • Cluster Autoscaler — добавляет и убирает узлы в облаке

Упаковка: Helm, Kustomize, GitOps

Helm

Пакетный менеджер: шаблоны + values.yaml. helm install postgresql bitnami/postgresql

Kustomize

Без шаблонов: база + наложения для staging и production. Встроен в kubectl.

GitOps

Argo CD, Flux: состояние кластера в git, контроллер сам приводит кластер к git.

Тот же принцип желаемого состояния, но источник правды — репозиторий.

Когда Kubernetes не нужен

Признаки, что рано

  • Один-два сервера, одна команда, умеренная нагрузка
  • Некому чинить кластер в 3 ночи
  • Десятки новых понятий, YAML, сеть, обновления кластера

Альтернативы

  • Compose на VPS — MVP и небольшие проекты
  • PaaS (Render, Fly.io, Railway) — без серверов
  • Docker Swarm, Nomad — проще, чем k8s

Kubernetes и ИИ-агенты

  1. Факт агенты хорошо генерируют манифесты — и так же хорошо генерируют опасные
  2. Проверять пробы, requests/limits, runAsNonRoot, секреты, нет latest
  3. В CI kubectl apply --dry-run=server, kubeconform, политики Kyverno
  4. Никогда не давайте агенту kubectl с правами на продакшен-кластер

Лабораторная работа

  1. Поднимите локальный кластер: k3d cluster create slot
  2. Манифесты «Slot»: Deployment + Service для API и фронтенда, StatefulSet или Helm-чарт для PostgreSQL, ConfigMap, Secret, Ingress
  3. Rolling update на новую версию и откат
  4. Удалите под — посмотрите, как он возвращается; масштабируйте API до 5 реплик
  5. С агентом: сгенерируйте манифесты из compose.yaml, затем проверьте вручную: пробы, лимиты, секреты

Результат

  • Манифесты (или Helm-чарт) «Slot» в репозитории
  • Лог самовосстановления и rolling update
  • Список исправлений в манифестах агента
  • ADR «нужен ли Slot'у Kubernetes?» — с честным ответом

Далее: Безопасность

Kubernetes держит желаемое состояние через циклы согласования. Deployment + Service + Ingress — основа веб-приложения. Для маленького проекта Compose на VPS — нормальный выбор.
