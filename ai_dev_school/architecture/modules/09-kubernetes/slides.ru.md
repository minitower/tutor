<!-- Slide 4 -->
## Проблема: Docker на одной машине — это просто

А если серверов 10 и контейнеров 200?

- На какой сервер поставить новый контейнер?
- Сервер упал — кто перезапустит его контейнеры на другом?
- Как обновить версию без простоя?
- Как сервисам найти друг друга, если IP меняются?
- Как масштабировать под нагрузку и обратно?

**Оркестратор** решает всё это автоматически. Kubernetes (k8s) — стандарт де-факто.

---

<!-- Slide 5 -->
## Главная идея: желаемое состояние

- Вы не говорите «запусти контейнер». Вы говорите: **«должно работать 3 копии API версии 1.4»**
- Kubernetes постоянно сравнивает **желаемое** состояние с **реальным** и устраняет разницу
- Упал под → реальное 2, желаемое 3 → создаётся новый
- Это называется **цикл согласования (reconciliation loop)**

```
наблюдать → сравнить с желаемым → действовать → наблюдать → …
```

Декларативно, как SQL: описываем **что**, а не **как**.

## Архитектура кластера

**Control plane** (мозг):
- **API server** — единая точка входа: все команды и все компоненты общаются только через него
- **etcd** — распределённое хранилище ключ-значение: всё состояние кластера
- **Scheduler** — решает, на какой узел поставить под
- **Controller manager** — запускает контроллеры, которые приводят реальность к желаемому

**Узлы (nodes)** (мышцы):
- **kubelet** — агент на узле: запускает поды, докладывает о здоровье
- **kube-proxy** — сетевые правила для Service
- **Container runtime** — containerd, собственно запускает контейнеры

---

<!-- Slide 7 -->
## Что происходит при `kubectl apply`

1. `kubectl` отправляет манифест в **API server**
2. API server проверяет и сохраняет его в **etcd**
3. **Контроллер Deployment** видит: нужно 3 пода, есть 0 → создаёт 3 объекта Pod
4. **Scheduler** видит поды без узла → назначает каждому узел
5. **kubelet** на узле видит назначенный под → просит containerd запустить контейнер
6. kubelet докладывает статус → API server → etcd

Никто никого не вызывает напрямую — все смотрят на состояние в API server.

<!-- Slide 8 -->
## Рабочие нагрузки

| Объект | Что это | Когда |
|---|---|---|
| **Pod** | Один или несколько контейнеров с общей сетью | Минимальная единица; руками почти не создают |
| **ReplicaSet** | Держит N одинаковых подов | Создаётся Deployment-ом |
| **Deployment** | ReplicaSet + плавные обновления и откаты | Stateless-приложения: API, фронтенд |
| **StatefulSet** | Поды со стабильными именами и дисками | БД, очереди |
| **DaemonSet** | По одному поду на каждом узле | Сбор логов, мониторинг |
| **Job / CronJob** | Задача до завершения / по расписанию | Миграции, бэкапы, отчёты |

## Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: slot-api }
spec:
  replicas: 3
  selector: { matchLabels: { app: slot-api } }
  template:
    metadata: { labels: { app: slot-api } }
    spec:
      containers:
        - name: api
          image: ghcr.io/school/slot-api:1.4.0
          ports: [{ containerPort: 8000 }]
          envFrom: [{ secretRef: { name: slot-secrets } }]
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { memory: 512Mi }
          readinessProbe: { httpGet: { path: /health, port: 8000 } }
```

## Сеть: Service

Поды смертны, их IP меняются. **Service** даёт стабильное имя и адрес и балансирует между подами по меткам.

| Тип | Доступен | Когда |
|---|---|---|
| **ClusterIP** | Только внутри кластера | API для фронтенда, БД |
| **NodePort** | Порт на каждом узле | Отладка, редко в продакшене |
| **LoadBalancer** | Внешний IP от облака | Публичный вход без Ingress |

Внутри кластера работает DNS: `http://slot-api.default.svc.cluster.local` или просто `http://slot-api`.

<!-- Slide 11 -->
## Вход снаружи: Ingress и Gateway API

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: slot }
spec:
  tls: [{ hosts: [slot.example], secretName: slot-tls }]
  rules:
    - host: slot.example
      http:
        paths:
          - { path: /api, pathType: Prefix, backend: { service: { name: slot-api, port: { number: 80 } } } }
          - { path: /,    pathType: Prefix, backend: { service: { name: slot-web, port: { number: 80 } } } }
```

- **Ingress** — правила HTTP-маршрутизации; работает через Ingress-контроллер (ingress-nginx, Traefik)
- **Gateway API** — более новый и гибкий преемник Ingress
- **cert-manager** выпускает TLS-сертификаты Let's Encrypt автоматически

<!-- Slide 12 -->
## Конфигурация и хранилище

- **ConfigMap** — несекретные настройки: адреса, флаги
- **Secret** — пароли, токены. Внимание: по умолчанию это **base64, а не шифрование**; нужны шифрование etcd, RBAC, внешние менеджеры секретов (Vault, External Secrets)
- **PersistentVolume (PV)** — кусок диска в кластере
- **PersistentVolumeClaim (PVC)** — запрос пода: «мне нужно 10 ГБ»; облако выдаёт диск автоматически (StorageClass)

<!-- Slide 13 -->
## Надёжность: пробы

| Проба | Вопрос | Если провалена |
|---|---|---|
| **liveness** | Процесс жив? | Перезапустить контейнер |
| **readiness** | Готов принимать трафик? | Убрать под из Service, не убивать |
| **startup** | Уже запустился? | Не проверять остальные пробы, пока не стартовал |

Типичная ошибка: liveness проверяет БД → БД моргнула → Kubernetes перезапускает **все** поды API.

---

<!-- Slide 14 -->
## Надёжность: ресурсы и масштабирование

- **requests** — сколько гарантировано; по ним scheduler выбирает узел
- **limits** — потолок; превысил память → контейнер убит (OOMKilled)
- **HPA (Horizontal Pod Autoscaler)** — меняет число реплик по CPU, памяти или своим метрикам
- **Cluster Autoscaler** — добавляет и убирает узлы в облаке
- **Rolling update** — новые поды поднимаются до того, как старые убраны; `kubectl rollout undo` — откат

---

<!-- Slide 15 -->
## Упаковка: Helm и Kustomize

- **Helm** — пакетный менеджер: шаблоны манифестов + `values.yaml`; `helm install postgresql bitnami/postgresql`
- **Kustomize** — без шаблонов: базовые манифесты + наложения для окружений (staging, production); встроен в `kubectl`
- **GitOps** (Argo CD, Flux) — состояние кластера описано в git; контроллер в кластере сам приводит кластер к git

Тот же принцип желаемого состояния, но источник правды — репозиторий.

## Где запускать

| Вариант | Примеры | Когда |
|---|---|---|
| Локально | k3d, kind, minikube, Docker Desktop | Учёба, тесты |
| Лёгкий кластер на VPS | k3s | Небольшой продакшен, свои серверы |
| Managed | GKE, EKS, AKS, Yandex Managed Kubernetes | Control plane — забота облака |

Managed k8s снимает самую сложную часть — control plane, etcd, обновления.

<!-- Slide 17 -->
## Когда Kubernetes не нужен

- Один-два сервера, одна команда, умеренная нагрузка
- Нет человека, который будет разбираться с кластером, когда он сломается в 3 ночи
- Kubernetes добавляет: десятки новых понятий, YAML, сеть, мониторинг кластера, обновления

| Альтернатива | Когда |
|---|---|
| **Compose на одном VPS** | MVP и небольшие проекты |
| **PaaS** (Render, Fly.io, Railway) | Не хотите заниматься серверами вообще |
| **Docker Swarm, Nomad** | Несколько серверов, но проще, чем k8s |

## Kubernetes и ИИ-агенты

- Агенты хорошо генерируют манифесты и Helm-чарты — и так же хорошо генерируют **опасные** манифесты
- Проверяйте: пробы, requests/limits, `runAsNonRoot`, секреты не в открытом виде, нет `latest`
- Валидация в CI: `kubectl apply --dry-run=server`, kubeconform, политики (Kyverno)
- Не давайте агенту `kubectl` с правами на продакшен-кластер

<!-- Slide 19 -->
## Лабораторная работа

1. Поднимите локальный кластер: `k3d cluster create slot`
2. Манифесты «Slot»: Deployment + Service для API и фронтенда, StatefulSet или Helm-чарт для PostgreSQL, ConfigMap, Secret, Ingress
3. Сделайте rolling update на новую версию и откат
4. Удалите под — посмотрите, как он возвращается
5. Масштабируйте API до 5 реплик
6. **С агентом:** сгенерируйте манифесты из `compose.yaml` с помощью агента, затем проверьте вручную: пробы, лимиты, секреты

## Итоги и следующий модуль

- Kubernetes держит **желаемое состояние** через циклы согласования
- Control plane: API server, etcd, scheduler, контроллеры; узлы: kubelet, kube-proxy, runtime

- Для маленького проекта Compose на VPS — нормальный выбор
