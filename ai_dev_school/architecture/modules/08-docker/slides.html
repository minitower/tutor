Проблема: «у меня работает»

  1. Версии у разработчика Python 3.12, на сервере — 3.9
  2. Системные пакеты библиотеке нужен libpq, которого нет на сервере
  3. Конфликты два проекта на одном сервере требуют разных версий пакета
  4. Онбординг новый сотрудник настраивает окружение два дня
Контейнер упаковывает приложение вместе с окружением: интерпретатор, библиотеки, системные пакеты, конфиги.

Виртуальная машина vs контейнер

Контейнер — не маленькая ВМ, а обычный процесс Linux, которому ограничили обзор и ресурсы.

Под капотом: три механизма Linux

Namespaces

Что процесс видит: свои PID, сеть, файловую систему, hostname, пользователей.

cgroups

Сколько процесс может взять: CPU, память, диск, число процессов.

OverlayFS

Образ из слоёв только для чтения + тонкий слой для записи сверху.

На Windows и macOS Docker Desktop запускает лёгкую Linux-ВМ, и контейнеры живут в ней.

Образ, контейнер, реестр

  • Образ — шаблон (класс), контейнер — запущенный экземпляр (объект)
  • Тег — имя версии (slot-api:1.4.0); digest (sha256:…) — неизменяемый отпечаток

Dockerfile

FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app/ ./app/

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Каждая инструкция (FROM, RUN, COPY) создаёт слой.

Кэш слоёв и порядок инструкций

Плохо

COPY . .
RUN pip install -r requirements.txt

Любая правка кода → переустановка всех зависимостей.

Хорошо

COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

Зависимости меняются редко — их слой берётся из кэша.

Правило: редко меняющееся — выше, часто меняющееся — ниже. Плюс .dockerignore: .git, node_modules, .venv, .env.

Multi-stage сборка

# Этап 1: сборка — со всеми инструментами
FROM node:22 AS build
WORKDIR /src
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Этап 2: запуск — только результат
FROM nginx:alpine
COPY --from=build /src/dist /usr/share/nginx/html

Итоговый образ фронтенда: ~1,2 ГБ → ~50 МБ. Компиляторов и исходников в продакшене нет.

Маленькие и безопасные образы

Базовый образРазмерКогда
python:3.12~1 ГБПочти никогда для продакшена
python:3.12-slim~130 МБПо умолчанию
alpine~5 МБ основаОсторожно: musl вместо glibc, сюрпризы с колёсами Python
distrolessМинимумНет даже shell — меньше поверхность атаки

Плюс: запуск не от root (USER app), никаких секретов в слоях, фиксированные версии.

Запуск: порты, тома, переменные

docker run -d --name slot-api \
  -p 8000:8000 \
  -e DATABASE_URL=postgresql://... \
  -v slot-uploads:/app/uploads \
  --restart unless-stopped \
  --memory 512m --cpus 1 \
  slot-api:1.4.0
  • -p порт хоста : порт контейнера · -e конфигурация через окружение · -v именованный том · --memory/--cpus лимиты (cgroups)
  • Контейнер одноразовый: всё, что записано внутрь без тома, пропадёт при пересоздании

Сети и healthcheck

  • Контейнеры в одной пользовательской сети видят друг друга по имени сервиса: postgres:5432
  • Наружу публикуем только то, что нужно (-p); БД наружу не открываем
  • Healthcheck проверяет, что приложение действительно живо, а не просто запущено
HEALTHCHECK --interval=10s CMD curl -f http://localhost:8000/health || exit 1

Docker Compose: всё приложение в одном файле

services:
  api:
    build: ./api
    environment:
      DATABASE_URL: postgresql://slot:${DB_PASSWORD}@postgres:5432/slot
      REDIS_URL: redis://redis:6379
    depends_on:
      postgres: { condition: service_healthy }
    ports: ["8000:8000"]
  worker:
    build: ./api
    command: arq app.worker.Settings
  postgres:
    image: postgres:17
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck: { test: ["CMD", "pg_isready", "-U", "slot"] }
  redis:
    image: redis:7
volumes:
  pgdata:

Compose: разработка и продакшен

docker compose up -d        # поднять всё
docker compose logs -f api  # смотреть логи
docker compose down         # остановить

Разработка

Bind mount кода + автоперезагрузка; compose.override.yaml подхватывается автоматически.

Продакшен

Только готовые образы из реестра, секреты из окружения, restart: unless-stopped.

Compose на одном VPS — честный вариант для продакшена небольшого проекта (Модуль 11).

Безопасность образов

  1. Сканировать Trivy, Docker Scout, Grype — в CI на каждую сборку
  2. Фиксировать postgres:17.2, а не latest; для точности — digest
  3. Не root внутри контейнера
  4. Секреты не в Dockerfile и не в слоях — только через окружение или secrets
  5. Минимум меньше пакетов в образе — меньше уязвимостей

Docker и ИИ-агенты

Песочница для агента

Агент запускает код и тесты в контейнере, не трогая вашу систему.

Типичные ошибки агента

Копирует всё до установки зависимостей, забывает .dockerignore, оставляет root.

Простая проверка: пересобрать после правки одной строки кода и посмотреть, сколько слоёв взялось из кэша.

Лабораторная работа

  1. Dockerfile для бэкенда «Slot» (FastAPI) и фронтенда (multi-stage)
  2. compose.yaml: api, worker, PostgreSQL, Redis, фронтенд
  3. Healthcheck, том для БД, запуск не от root, .dockerignore
  4. Уменьшите образ бэкенда и просканируйте его Trivy
  5. С агентом: попросите агента проверить Dockerfile на порядок кэша, размер и безопасность; проверьте каждое предложение пересборкой

Результат

  • docker compose up поднимает весь «Slot» локально
  • Размер образов до/после и что дало эффект
  • Отчёт Trivy и что вы исправили
  • Какие советы агента подтвердились пересборкой, а какие нет
