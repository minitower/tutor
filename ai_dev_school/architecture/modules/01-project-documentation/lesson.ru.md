# Модуль 1 — Документация проекта: от идеи до спецификации

## Цели обучения
- Описать продукт так, чтобы разработчик, тестировщик и ИИ-агент построили одно и то же
- Понимать, какой артефакт отвечает на какой вопрос и какие из них маленький проект может пропустить
- Хранить документацию в репозитории в виде, который агент может прочитать и выполнить

## План лекции
1. Зачем документировать: цена недопонимания растёт с каждым этапом
2. Vision / PRD: проблема, аудитория, цели, не-цели, метрики успеха
3. User story («Как… я хочу… чтобы…») + критерии приёмки в формате Given/When/Then; INVEST
4. Use case: акторы, предусловия, основной поток, альтернативные и ошибочные потоки
5. Test case: шаги, данные, ожидаемый результат; как критерии приёмки превращаются в тесты
6. BPMN: события, задачи, шлюзы, пулы и дорожки; моделируем процесс бронирования
7. UML: диаграммы вариантов использования, последовательности, классов, состояний, активностей; ER-диаграмма модели данных
8. Модель C4: context → container → component → code; самая полезная диаграмма для архитектуры
9. ADR (Architecture Decision Record) и контракт API (OpenAPI)
10. Docs-as-code: Mermaid, PlantUML, BPMN XML, всё под версионным контролем в `docs/`
11. Как ИИ-агенты читают документацию: текст лучше картинок, диаграммы как код, `AGENTS.md`/`CLAUDE.md`, связь спецификаций с тестами, как не дать документации устареть

## Лабораторная работа
Напишите спецификацию «Slot»: vision, 8–10 user stories с критериями приёмки, 2 use case, BPMN бронирования, C4-диаграмму контейнеров, ER-диаграмму, черновик OpenAPI, 10 тест-кейсов.
- **С агентом:** дайте агенту только папку `docs/` и попросите найти противоречия и пробелы; затем попросите сгенерировать заготовки тестов по критериям приёмки.

## Результат
Папка `docs/` со всеми артефактами + список пробелов, найденных агентом, и как вы их исправили.
