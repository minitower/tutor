Vision / PRD

Одна страница, которая отвечает на вопросы:

  • Проблема: мастер ведёт запись в мессенджере, клиенты пишут ночью, путаница в слотах
  • Аудитория: малый бизнес с почасовой записью
  • Цели: клиент записывается за 30 секунд без переписки
  • Не-цели: онлайн-оплата, мультифилиальность (не в первой версии)
  • Метрики успеха: доля записей через сайт, число отмен
Не-цели важны так же, как цели: они останавливают и людей, и агентов от лишней работы.

User story

Плохо

«Как пользователь я хочу удобную систему»

Нельзя проверить, нельзя оценить, непонятно, для кого.

Хорошо

«Как клиент барбершопа, я хочу видеть свободные слоты на неделю вперёд, чтобы записаться без переписки с мастером»

Проверка по INVEST: Independent, Negotiable, Valuable, Estimable, Small, Testable

Критерии приёмки: Given / When / Then

Сценарий: запись на свободный слот
  Дано  слот «пт 15:00» свободен
  Когда клиент выбирает его и вводит имя и телефон
  Тогда слот помечается занятым
  И     клиент видит подтверждение, мастер получает уведомление

Сценарий: гонка за один слот
  Дано  два клиента открыли слот «пт 15:00»
  Когда оба нажимают «Записаться»
  Тогда запись получает только первый
  И     второй видит «Слот уже занят» и ближайшие свободные

Второй сценарий — тот, о котором забывают. И агент тоже, если его не написать.

BPMN: язык бизнес-процессов

  • Событие — начало, конец, таймер, сообщение · Задача — действие человека или системы
  • Шлюз — развилка · Дорожка — кто выполняет: клиент, система, мастер
  • BPMN читают и бизнес, и разработчики — хорош для согласования процесса

Sequence-диаграмма как код (Mermaid)

sequenceDiagram
  actor C as Клиент
  participant F as Фронтенд
  participant A as API
  participant D as БД
  participant Q as Очередь
  C->>F: выбрать слот 42
  F->>A: POST /api/bookings
  A->>D: UPDATE slots … AND free
  D-->>A: 1 строка
  A->>Q: notify(master, 1017)
  A-->>F: 201 Created
  F-->>C: «Вы записаны»

Слева — что хранится в репозитории и читает агент. Справа — что рисует GitHub.

State и ER

State: жизнь записи

stateDiagram-v2
  [*] --> pending
  pending --> confirmed: мастер подтвердил
  pending --> cancelled: клиент отменил
  confirmed --> done: визит состоялся
  confirmed --> no_show: не пришёл

ER: данные

erDiagram
  MASTER ||--o{ SERVICE : offers
  MASTER ||--o{ SLOT : has
  SLOT ||--o| BOOKING : "booked by"
  CLIENT ||--o{ BOOKING : makes

||--o| — «у слота не больше одной записи»: это правило потом станет уникальным индексом в БД.

ADR и OpenAPI

ADR — почему так

ADR-0002: PostgreSQL вместо MongoDB
Статус: принято
Контекст: сущности связаны;
  нужна защита от двойной записи
Решение: PostgreSQL, уникальный
  индекс на slot_id в bookings
Последствия: нужны миграции;
  гонку за слот решает БД

OpenAPI — контракт

paths:
  /api/bookings:
    post:
      requestBody:
        $ref: '#/…/BookingCreate'
      responses:
        '201': Запись создана
        '409': Слот уже занят

Из OpenAPI генерируются клиенты, моки и документация — и агенту не нужно угадывать поля.

Как ИИ-агенты читают документацию

Агент ошибается

  • Диаграмма — PNG-картинка
  • Требования — абзацы прозы
  • Одно правило в двух файлах, и они расходятся
  • Не сказано, где что лежит

Агент попадает

  • Mermaid / BPMN XML — читается точно
  • ID, списки, таблицы, Given/When/Then
  • Одно место правды на каждый факт
  • AGENTS.md / CLAUDE.md — входная точка

AGENTS.md для «Slot»

# Slot — правила для агентов
- Требования: docs/stories/; критерии приёмки — единственный источник правды
- API-контракт: docs/api/openapi.yaml — не добавляй поля, которых там нет
- Архитектурные решения: docs/adr/ — читай перед изменением структуры
- Каждый новый эндпоинт → тест со ссылкой на ID истории
- Изменил поведение → обнови историю и диаграмму в том же PR

Коротко, конкретно, с путями к файлам. Агент читает это в начале каждой сессии.

Лабораторная работа

Напишите спецификацию «Slot» в папке docs/:

  1. Vision на одну страницу
  2. 8–10 user stories с критериями Given/When/Then
  3. 2 use case, 10 test case
  4. BPMN бронирования, C4 Container, ER — как код
  5. Черновик OpenAPI, 2 ADR, AGENTS.md
  6. С агентом: дайте агенту только docs/ и попросите найти противоречия и пробелы; затем — сгенерировать заготовки тестов по критериям

Результат

  • Папка docs/ со всеми артефактами
  • Список пробелов, которые нашёл агент, и как вы их исправили
  • Заготовки тестов со ссылками на ID историй
