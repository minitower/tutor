# Модуль 9 — Test-Driven Development с агентами

## Цели обучения
- Использовать тесты как исполняемую, недвусмысленную спецификацию для
  агента
- Понимать, почему падающий тест, написанный *до* исправления, снижает
  галлюцинации агента (у агента есть конкретная, проверяемая цель вместо
  текстового описания, которое он может понять неверно)

## Ключевые концепции
- Red/green/refactor с агентом за рулём: написать падающий тест →
  убедиться, что он падает по правильной причине → реализовать →
  убедиться, что он проходит → рефакторинг
- Тесты на примерах vs. тесты на основе свойств (property-based) как
  спецификации для агента — property-based тесты отлавливают граничные
  случаи, о которых ни агент, ни вы не подумали написать примеры
- Почему это хорошо сочетается с исправлением багов и чётко определённой
  логикой и плохо — с расплывчатой или исследовательской работой над UI,
  где «правильно» ещё не известно

## Лабораторная работа
Дайте агенту только отчёт об ошибке — без подсказок по исправлению.
Потребуйте от него:
1. Написать тест, который воспроизводит баг и падает
2. Убедиться, что падение происходит по правильной причине (не из-за
   опечатки в тесте)
3. Реализовать исправление
4. Убедиться, что тест проходит и ничего другого не сломалось

Держите коммит с падающим тестом и коммит с исправлением раздельно,
чтобы цикл был виден в истории.

## Результат
Два коммита (падающий тест, затем исправление) плюс однострочная
заметка о том, действительно ли первая попытка агента написать тест
воспроизвела баг, или потребовалась коррекция.
