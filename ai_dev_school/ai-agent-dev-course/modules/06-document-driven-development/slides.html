Модуль 6

Document-Driven Development

Спецификации как источник истины

Agentic Software Development: From Specs to Shipped Code

План занятия

  • Почему неоднозначность — главный налог на работу с агентом
  • Анатомия спецификации, по которой агент реально может работать
  • Цикл: спецификация → план → реализация → обновление спецификации
  • Документы для агента на уровне репозитория vs. спецификации фичи
  • Типичные ошибки (и как их избегать)
  • Лабораторная: пишем настоящую спецификацию, отдаём агенту, закрываем пробелы

Цели модуля

По итогам вы сможете:

  • Использовать письменную спецификацию как контракт, по которому агент реализует задачу
  • Отличать спецификацию, которая слишком расплывчата, от той, что переспецифицирована
  • Пройти полный цикл DDD, включая шаг, который команды обычно пропускают
  • Поддерживать спецификацию как живой артефакт, а не разовую передачу
  • Распознавать, когда DDD — не тот инструмент для задачи

Проблема, которую решает DDD

Самый большой источник впустую потраченных ходов агента — неоднозначность.

  • Агент угадывает намерение → строит не то
  • Вы тратите больше времени на исправления, чем потратили бы, один раз записав намерение
  • Разговор, в котором вы «объяснили», не оставляет постоянного следа
DDD переносит эту стоимость заранее — в документ, а не в разговор — и документ остаётся у вас.

Что такое Document-Driven Development

Письменная спецификация — это основной интерфейс между человеком и агентом для работы над задачей.

Агент:

  1. Читает спецификацию
  2. Планирует по ней
  3. Реализует по ней
  4. Помогает обновить её, когда реальность расходится с планом

Последний пункт — то, что команды пропускают. Он же делает это «document-driven», а не «однажды написал документ».

Анатомия спецификации — обзор

  1. Цель (Goal) — один абзац, простым языком
  2. Не-цели (Non-goals) — явно вне рамок
  3. Интерфейсы / контракты — то, что агент не должен придумывать сам
  4. Граничные случаи — те, о которых вы уже знаете
  5. Критерии приёмки — проверяемые, в идеале буквально команды/тесты
  6. Открытые вопросы — оставлены агенту, чтобы он предложил ответ

Сквозной пример на следующих слайдах: экспорт отчётов в CSV.

Цель + Не-цели

## Goal
Let a user export the currently filtered report rows to a CSV file,
matching the date range they've already selected on the dashboard.

## Non-goals
- No new file formats (CSV only, not XLSX/PDF)
- No server-side scheduled/emailed exports — synchronous,
  on-click download only

Не-цели спасают от незаметного расползания объёма задачи — они так же значимы, как и сама цель.

Интерфейсы / контракты

## Interface
- A button labeled "Export CSV" next to the existing date-range picker
- Clicking it downloads a file named `report_<start>_<end>.csv`
- Columns match the currently visible table columns, in the same order

Если это важно, а вы не записали — агент придумает сам, и его выдумка станет фактическим контрактом, который следующему читателю придётся восстанавливать реверс-инжинирингом.

Граничные случаи

## Edge cases
- No rows in the selected range → header-only CSV, not an error
- Date range spans a DST transition → use UTC dates in filename and
  date columns, to avoid off-by-one-day bugs
- User has an active column filter (not just date range) → export
  respects it too, not just the date range

Вы уже знаете эти случаи. Записать их — не стоит времени; не записать — просто переносит стоимость со «спецификации» на «отладку».

Критерии приёмки + Открытые вопросы

## Acceptance criteria
- Exporting a known 3-row range produces exactly those 3 rows + header
- Exporting an empty range produces a header-only CSV, not a 500
- Filename matches `report_<start>_<end>.csv` using UTC dates

## Open questions
- Should the export button be disabled (vs. hidden) when there's no
  data? Leaving this to the agent to propose in the plan step.

Папка спецификаций

  • Одна папка в репозитории — например docs/specs/ — держит по одному файлу на фичу
  • Имя файла = имя фичи/тикета: export-csv.md, cursor-pagination.md
  • Спецификация создаётся до начала работы, обновляется во время работы, и остаётся там, пока фича не выпущена
  • Ссылка на файл — это то, что вы даёте агенту вместо пересказа задачи словами в чате
docs/
└── specs/
    ├── export-csv.md         ← в работе
    ├── cursor-pagination.md  ← выпущено, можно архивировать
    └── rate-limiting.md      ← ещё не начата

Виды спецификаций (1 из 2)

«Спецификация» — не один жанр документа. Формат под задачу:

Feature spec

То, что мы разбирали: Goal, Non-goals, Interface, Edge cases, Acceptance criteria. Один кусок пользовательской функциональности.

Task spec

Меньше и короче — под один рабочий сеанс агента. Ближе к одноразовому плану (Модуль 8), чем к постоянному документу.

Security spec

Модель угроз: границы доверия, что нельзя раскрывать, какие входные данные считать враждебными.

Виды спецификаций (2 из 2)

Code-review spec

Чек-лист критериев, по которым ревьюер — человек или агент — проверяет диф, прежде чем принять его.

Design spec

Токены и визуальные правила вместо расплывчатых прилагательных — подробно в Модуле 7.

Spec-writer

Отдельный шаг (или агент), который превращает расплывчатый запрос из Модуля 5 в структурированную спецификацию, прежде чем строить.

И так далее — под свою команду список стоит держать коротким, а не плодить жанры ради жанров.

Документы уровня репозитория vs. спецификации фичи

Два разных документа — не путайте их:

Репозиторий (CLAUDE.md, AGENTS.md)Спецификация фичи
ОбластьВесь репозиторий, постоянный контекстОдин кусок работы
СодержимоеКонвенции, команды тестов, архитектурные ограниченияЦель, не-цели, интерфейсы, граничные случаи, критерии приёмки
Жизненный циклЧитается каждую сессию, редко меняетсяНаписана под задачу, архивируется/удаляется после выпуска

DDD в этом курсе — про второй тип.

Почему последний шаг — вся суть

  • Спецификация, незаметно расходящаяся с кодом, хуже, чем отсутствие спецификации — она активно вводит в заблуждение следующего читателя
  • «Обновить спецификацию» должно входить в определение «готово», как и тесты
  • Ценность DDD — в том, что план проверяется по спецификации до начала реализации, а не в самом факте существования документа в репозитории
DDD ≠ «я один раз написал документ». DDD = документ остаётся правдивым.

Хорошие документы репозитория делают спецификации короче

Пример правила в CLAUDE.md:

Before any UI/styling work, read `design/tokens.css` and
`design/system.md`. Do not introduce new colors, fonts, or spacing
values outside the tokens file.

Поскольку это правило уже существует на уровне репозитория, спецификации на экспорт CSV вообще не нужно упоминать design-токены — одним пунктом меньше писать, и одним пунктом меньше того, что может устареть.

CLAUDE.md — не файл, который пишут один раз и забывают:

  • Нашли во время задачи устойчивую конвенцию, которой там ещё нет? Добавьте её строкой в CLAUDE.md в том же PR — не «как-нибудь потом»
  • Можно прямо попросить агента в конце задачи: «если нашёл что-то, что стоит запомнить на будущее — предложи правку в CLAUDE.md»
  • Польза копится: каждая следующая спецификация короче, а каждая новая сессия агента стартует уже «в курсе» конвенций команды

Типичные ошибки (1 из 2)

Устаревшие документы

Спецификация говорит одно, код делает другое, никто не замечает, пока это не вызывает баг.

Смягчение

«Обновить спецификацию» — часть «готово», как и тесты.

Переспецификация

Диктовать детали реализации, которые не важны, — дорого писать и дорого поддерживать в актуальном состоянии.

Смягчение

Специфицировать контракты и поведение, а не внутреннее устройство.

Типичные ошибки (2 из 2)

Недоспецификация известных граничных случаев

Если вы о них знаете и не записали — вы не сэкономили время, а перенесли стоимость на отладку.

Смягчение

Пройдитесь по разделу Edge cases явно, а не надейтесь, что «само всплывёт» в реализации.

Спецификация как одностороннее вручение

Ценность DDD — в том, что план агента проверяется по спецификации до начала реализации, а не в том, что вы отдали документ и ушли.

Смягчение

Сначала попросите агента предложить план и сверьте его со спецификацией, прежде чем разрешать реализацию.

Когда DDD — не тот инструмент

МетодологияЛучше всего дляСлабо подходит дляАртефакт

Plan-firstРефакторинги, рискованные измененияБыстрое исследованиеОдноразовый план/ADR
TDD-с-агентомБагфиксы, чёткая логикаИсследовательская UI-работаНабор тестов

Пятистрочный багфикс не нуждается в спецификации. Фича с реальной неоднозначностью — нуждается.

Инструмент: spec-kit

Открытый инструмент от GitHub: слэш-команды /specify, /plan, /tasks прямо в агентном CLI реализуют тот же цикл, что мы прошли на этом занятии.

$ specify init my-project && cd my-project

> /specify Дать пользователю экспортировать отфильтрованные
  строки отчёта в CSV, соответствующий выбранному диапазону дат
> /plan Переиспользовать существующий компонент таблицы,
  без новых зависимостей
> /tasks

Лабораторная: пишем спецификацию, отдаём агенту

  1. Выберите реальную небольшую-среднюю фичу (учебный репозиторий или свой)
  2. Напишите спецификацию на одну страницу по описанной анатомии — засеките время
  3. Дайте агенту только спецификацию как задачу — без устного контекста
  4. Пусть агент сначала предложит план; проверьте его по спецификации, прежде чем разрешать реализацию
  5. После реализации проверьте поведение по критериям приёмки
  6. Обновите спецификацию, чтобы закрыть каждый найденный пробел

Лабораторная: на что обратить внимание

  • Каждое место, где агенту пришлось угадывать → спецификация молчала
  • Каждое место, где план вас удивил → это стоит поймать до того, как появится код
  • Каждый критерий приёмки, который не проходит с первого раза — код неверен, или сам критерий сформулирован нечётко?
  • Честно фиксируйте потраченное время — по этому вы позже оцените, окупился ли DDD

Результат (Deliverable)

  • Документ спецификации
  • План агента (если использовался режим планирования)
  • Получившийся дифф
  • Краткий список: «места, где спецификация была неверной или неполной, и что я изменил»

Именно этот последний список — самый ценный артефакт: он даёт прямое доказательство того, чего стоит спецификация на реальной задаче.

Далее: Deterministic Design Systems

Спецификация — это контракт, а не список пожеланий. Цикл считается DDD, только если спецификация обновляется. Документы уровня репозитория и спецификации фич — разные инструменты, используемые вместе.

Та же идея «запиши, чтобы агент не угадывал», применённая к визуальной консистентности: токены и design-документы вместо расплывчатых прилагательных.
