# Модуль 2 — сценарий лекции: MCP: подключаем агента к внешним системам

*Заметки для преподавателя. Номера слайдов соответствуют `slides.ru.md`.
Тайминги — ориентировочные, для очного занятия на 2–2.5 часа (лекция + лаборатория).*

---

## Вступление (Слайды 1–3) — ~10 мин

### Слайд 1 — Model Context Protocol: руки агента

Добро пожаловать в Модуль 2. В Модуле 1 мы разобрали цикл агента: план, действие, наблюдение. Пока агент работает внутри репозитория: читал файлы, запускал команды, правил код. Но реальные задачи упираются в системы за его пределами: база данных, трекер задач, мониторинг, браузер. Сегодня — как дать агенту доступ к ним через стандарт, а не через одноразовые костыли, и как не превратить этот доступ в дыру.

### Слайд 2 — План занятия

Идём по порядку: проблема и устройство протокола, затем практика — БД, открытые серверы, свой сервер. Потом честный разговор, когда MCP не нужен, и большой блок про безопасность, потому что любой сервер — это код, который выполняется по просьбе модели. Лаба — read-only база данных через MCP. Замечание: в модуле есть ссылки вперёд — на верификацию, CI/CD и хуки; это указатели на темы, которые мы разберём подробно позже.

### Слайд 3 — Цели модуля

Четыре цели. Обратите внимание на последнюю: не «подключить всё, что есть», а уметь оценить сервер и выбрать правильный инструмент — иногда это обычный CLI или skill. Хороший инженер знает, когда MCP не нужен.

## Проблема и устройство протокола (Слайды 4–8) — ~25 мин

### Слайд 4 — Проблема: N × M интеграций

Посмотрите на схему. Слева — мир без стандарта: три приложения и три системы дают девять интеграций, и каждая со своей авторизацией, форматами и багами. Справа — с MCP: каждое приложение реализует клиент один раз, каждая система — сервер один раз, и они совместимы. N умножить на M превращается в N плюс M. Аналогия — Language Server Protocol: раньше каждый редактор поддерживал каждый язык отдельно, теперь языковой сервер пишется один раз.

### Слайд 5 — Что такое MCP

MCP — открытый протокол; сообщения кодируются в JSON-RPC 2.0. Три роли. Host — приложение с моделью: Claude Code, IDE, ваш собственный агент. Client — коннектор внутри host, по одному на каждый сервер. Server — программа, которая отдаёт контекст и возможности. Важная мысль слайда: это слой доступа, отдельный и от модели, и от агента. Поэтому права, аудит и лимиты можно повесить на сервер — об этом дальше.

### Слайд 6 — Архитектура и транспорты

Два стандартных транспорта. Stdio — сервер запускается как дочерний процесс, сообщения идут построчно через стандартные потоки: идеально для локальных инструментов. Streamable HTTP — каждое сообщение это HTTP POST на один endpoint, ответ приходит JSON-ом или потоком SSE: так работают удалённые серверы с OAuth. Прежний SSE-транспорт считается устаревшим. Для преподавателя: свежая ревизия спецификации сделала запросы самодостаточными, без сессии initialize — но клиенты сохраняют совместимость с предыдущими версиями, так что студентам это знать нужно только как «протокол эволюционирует, сверяйтесь со спецификацией».

### Слайд 7 — Что может дать сервер: три примитива

Три примитива, и важно, кто ими управляет. Tools — функции, которые вызывает модель; для агентов это главное. Resources — данные и контекст, которые читает пользователь или модель. Prompts — шаблоны, которые запускает пользователь; в Claude Code это слэш-команды. Со стороны клиента есть elicitation: сервер может попросить пользователя уточнить. Среди расширений — Tasks для долгих операций и Skills over MCP: доставка навыков через MCP — с этим мы встретимся в модуле 4.

### Слайд 8 — Как выглядит вызов инструмента

Вот как выглядит вызов на проводе. Клиент спрашивает tools/list и получает список: имя, описание, JSON-схема аргументов. Дальше tools/call с аргументами и результат. Главное, что нужно унести: модель принимает решение, вызывать ли инструмент, по имени, описанию и схеме. Значит, описание — часть вашего промпта, и его пишет тот, кому вы доверяете… или нет — к этому вернёмся в безопасности. Пример упрощён: служебные поля и рукопожатие опущены.

## Практика: подключение и примеры (Слайды 9–12) — ~30 мин

### Слайд 9 — Подключение в Claude Code

Практика в Claude Code. Локальный сервер: claude mcp add с транспортом stdio, затем двойной дефис и команда запуска — дефисы обязательны, иначе флаги сервера разберёт сам Claude. Удалённый: транспорт http и URL; для OAuth потом открываете /mcp и входите в браузере. claude mcp list показывает статус. Три области: local — личное для проекта, project — файл .mcp.json в git для команды, user — для всех ваших проектов. Запомните имя инструмента mcp двойное подчёркивание сервер двойное подчёркивание инструмент — оно нужно для прав и хуков.

### Слайд 10 — Пример 1: база данных через MCP

Классический первый MCP-кейс — база данных. Агент читает схему, сам пишет запросы, анализирует результат — аналитик на минималках. Но правило номер один: read-only роль. Не полагайтесь на то, что агент «не будет писать» — сделайте так, чтобы не мог. Лучше реплика или staging. DSN — в переменной окружения, файл .mcp.json попадает в git. Добавьте лимиты на стороне БД. И заметка: референс-серверы для PostgreSQL и SQLite сейчас архивированы, берите поддерживаемые — DBHub или серверы вендоров.

### Слайд 11 — Пример 2: открытые MCP-серверы

Открытые серверы. Референсные, из репозитория modelcontextprotocol: Filesystem, Git, Fetch, Memory — граф знаний как память, к нему вернёмся в модуле 3 — плюс Sequential Thinking и Time. Дальше вендорские удалённые серверы: GitHub, Sentry, Notion, Stripe, с OAuth. И Playwright — управление браузером, полезно, чтобы агент сам проверял UI. Прочитайте вслух сноску: Fetch превращает веб-страницу в markdown — это готовый канал для prompt injection. И покажите MCP Registry как место, где искать серверы. Версии и команды меняются быстро, всегда сверяйтесь с README.

### Слайд 12 — Свой MCP-сервер за 10 строк

Свой сервер — десять строк. Функция с декоратором tool, docstring и типы. Обратите внимание: в свежей версии Python SDK FastMCP переименован в MCPServer — в первой мажорной версии импорт другой, это на слайде в комментарии. Запуск по умолчанию по stdio. Отладку делайте в MCP Inspector, без агента: видно список инструментов и результат вызова. Совет по дизайну: мало узких инструментов лучше, чем много общих; docstring — то, что читает модель; ответ должен быть коротким, иначе он съест контекст.

## Когда MCP, а когда нет (Слайд 13) — ~10 мин

### Слайд 13 — MCP, CLI или Skill: что выбрать

Не всё нужно оборачивать в MCP. Если инструмент уже есть в терминале и агент его знает — git, gh, psql — используйте CLI: ноль затрат контекста на описания. MCP выигрывает, когда нужна стандартная авторизация OAuth, типизированные ответы, или один сервер для нескольких клиентов. Повторяемая процедура — skill, правило «всегда» — hook. Помните и про цену: описания инструментов занимают контекст; Claude Code по умолчанию подгружает их по требованию, но всё равно отключайте лишние серверы.

## Безопасность и агентные системы (Слайды 14–16) — ~25 мин

### Слайд 14 — Безопасность MCP: угрозы

Безопасность. Первое — injection через результаты инструментов: страница, тикет, строка в базе могут содержать инструкцию агенту; это модуль 12 в новой обёртке. Второе — tool poisoning: вредоносное описание инструмента. Спецификация прямо говорит, что описания недоверенны, пока сервер не доверенный. Третье — rug pull и supply chain: сервер изменил инструменты после одобрения, или npx с флагом -y тянет непинованную версию. Четвёртое — избыточные права. Пятое — утечки. И цитата из принципов спецификации: инструмент — это выполнение произвольного кода, согласие пользователя обязательно.

### Слайд 15 — Безопасность MCP: контроли

Контроли. Наименьшие права: read-only креды, минимальные scope, allow-список инструментов в permissions — на слайде allow для query и deny для execute. Пин версий и чтение кода сервера до подключения — да, это скучно, но это ровно то же, что вы делаете с зависимостями. Хук-аудит: PreToolUse с matcher mcp точка звёздочка пишет каждый вызов в лог — привет модулю 13. Серверы из .mcp.json требуют одобрения при первом использовании — не жмите «да» не глядя. Для серверов с выходом в интернет — песочница и ограничение исходящей сети.

### Слайд 16 — MCP в агентной системе и в CI

Как это выглядит в автоматизации. Ключевой факт: stdio-сервер в .mcp.json — это команда, которая запускается на машине. Конфиг из чужого PR — недоверенный код, ровно как в модуле 13 про форки. В CI перечисляйте разрешённые инструменты явно, креды — секреты CI с правом только на чтение. И для агентных систем из нескольких ролей полезная мысль: у каждой роли свой набор серверов. Planner читает, implementer пишет в свою ветку, reviewer только комментирует. Политика живёт на сервере, а не в промпте.

## Лабораторная и итоги (Слайды 17–19) — ~10 мин

### Слайд 17 — Лабораторная — БД через MCP

Лаборатория. Поднимите тестовую БД с read-only пользователем, подключите через .mcp.json, задайте три вопроса, сохраните трассу. Потом попросите UPDATE или DROP и покажите, что запись заблокирована — и правами БД, и deny. Это главный момент: защита работает не потому, что агент послушный. Затем мини-сервер с одним инструментом, проверка в Inspector и заметка об угрозах — пять строк со слайда 14 и контрмера к каждой.

### Слайд 18 — Результат

Что сдаём: .mcp.json без секретов, трасса и доказательство блокировки записи, код мини-сервера с логом Inspector и заметка об угрозах. Проверяйте в первую очередь заметку: студент должен связать каждую контрмеру с конкретной угрозой, а не просто перечислить лучшие практики.

### Слайд 19 — Далее: долгосрочная память агента

Итог. MCP даёт агенту руки — доступ к системам через один протокол. Но сервер — это код, а его вывод — недоверенный текст, поэтому права, аудит и границы остаются вашей работой. Дальше — память: агенту нужно помнить вас и проект между сессиями. Увидимся в модуле 3.
