## Что такое MCP

- **Model Context Protocol** — открытый протокол, который стандартизирует, как LLM-приложение получает контекст и инструменты из внешних систем
- Сообщения — **JSON-RPC 2.0**
- Идея заимствована у Language Server Protocol: один стандарт вместо интеграции каждого редактора с каждым языком
- Три роли: **host** (приложение с LLM), **client** (коннектор внутри host), **server** (даёт контекст и возможности)

> Слой доступа к системам — отдельно от модели и от агента.

## Архитектура и транспорты

**Host** → **Client** → **Server**

| Транспорт | Как работает | Когда |
|---|---|---|
| **stdio** | сервер — дочерний процесс, JSON построчно через stdin/stdout | локальные инструменты |
| **Streamable HTTP** | каждое сообщение — HTTP POST, ответ JSON или SSE-поток | удалённые и облачные серверы, OAuth |

Старый SSE-транспорт считается устаревшим. Свежая ревизия спецификации сделала запросы самодостаточными (без сессии `initialize`); клиенты и серверы поддерживают откат к старым версиям.

## Что может дать сервер: три примитива

- **Tools** — Функции, которые вызывает **модель**: запрос к БД, создание issue, поиск. Главный примитив для агентов
- **Resources** — Данные и контекст — файлы, схемы, записи — которые читает пользователь или модель
- **Prompts** — Шаблонные сообщения и сценарии, которые запускает **пользователь** (в Claude Code это слэш-команды)

Со стороны клиента: **elicitation** — сервер просит у пользователя недостающую информацию. Опциональные расширения: Tasks (долгие операции), MCP Apps (интерактивный UI), Skills over MCP.

## Как выглядит вызов инструмента

```json
→ {"jsonrpc":"2.0","id":7,"method":"tools/list"}
← {"result":{"tools":[{"name":"query","description":"Run a read-only SQL query",
     "inputSchema":{"type":"object","properties":{"sql":{"type":"string"}},"required":["sql"]}}]}}

→ {"jsonrpc":"2.0","id":8,"method":"tools/call",
   "params":{"name":"query","arguments":{"sql":"SELECT count(*) FROM users"}}}
← {"result":{"content":[{"type":"text","text":"count\n42"}]}}
```

- Модель видит **имя, описание и JSON-схему** аргументов — по ним она решает, вызывать ли инструмент
- Пример упрощён: служебные поля `_meta` и рукопожатие опущены

## Подключение в Claude Code

```bash
# локальный stdio-сервер (после -- идёт команда запуска)
claude mcp add --transport stdio db -- npx -y @bytebase/dbhub --dsn "$DB_READONLY_DSN"
# удалённый HTTP-сервер; OAuth: затем /mcp -> войти в браузере
claude mcp add --transport http sentry https://mcp.sentry.dev/mcp
claude mcp list           # Connected / Needs authentication / Failed
claude mcp get sentry ; claude mcp remove sentry
```

| Scope | Где хранится | Для чего |
|---|---|---|
| local | `~/.claude.json` | личные серверы и креды этого проекта |
| project | `.mcp.json` в корне | общие серверы команды — через git |
| user | `~/.claude.json` | ваши утилиты во всех проектах |

Инструменты называются `mcp__<сервер>__<инструмент>` — по этим именам пишутся правила прав, хуки и `allowed-tools`.

## Пример 1: база данных через MCP

```json
{ "mcpServers": { "db": {
    "type": "stdio", "command": "npx",
    "args": ["-y", "@bytebase/dbhub", "--dsn", "${DB_READONLY_DSN}"] } } }
```

- Агент читает схему, сам пишет и запускает запросы, анализирует результат
- **Правило №1: read-only роль БД**, лучше реплика или staging — не prod с правом записи
- DSN — в переменной окружения (`${VAR}` поддерживается), а не в git
- Лимиты на стороне БД: `statement_timeout`, ограничение строк
- Референс-серверы PostgreSQL и SQLite архивированы — берите поддерживаемые (DBHub, серверы вендоров вроде Supabase или Neon)

## Пример 2: открытые MCP-серверы

| Сервер | Что даёт | Подключение |
|---|---|---|
| **Filesystem** (reference) | операции с файлами в разрешённых каталогах | `npx -y @modelcontextprotocol/server-filesystem <dir>` |
| **Git** (reference) | чтение, поиск, операции с репозиторием | `uvx mcp-server-git` |
| **Fetch** (reference) | страница → markdown (внимание: injection!) | `uvx mcp-server-fetch` |
| **Memory** (reference) | граф знаний как постоянная память — модуль 3 | `npx -y @modelcontextprotocol/server-memory` |
| **GitHub** | issues, PR, репозитории | remote: `https://api.githubcopilot.com/mcp/` + токен |
| **Sentry**, **Notion**, **Stripe** | вендорские remote-серверы с OAuth | `https://mcp.sentry.dev/mcp` и др. |
| **Playwright** (Microsoft) | управление браузером для проверки UI | `npx @playwright/mcp@latest` (сверьтесь с README) |

Каталог опубликованных серверов — MCP Registry (`registry.modelcontextprotocol.io`). Серверы GitHub, GitLab, Slack, Puppeteer из референс-репозитория архивированы.

## Свой MCP-сервер за 10 строк

```python
# server.py     pip install mcp
from mcp.server.mcpserver import MCPServer   # в mcp 1.x: from mcp.server.fastmcp import FastMCP

mcp = MCPServer("tickets")

@mcp.tool()
def count_open(project: str) -> int:
    """Сколько открытых тикетов в проекте (только чтение)."""
    return db_count(project)        # ваша реализация

if __name__ == "__main__":
    mcp.run()                       # stdio по умолчанию
```

- Подключение: `claude mcp add --transport stdio tickets -- python server.py`
- Отладка без агента: `npx @modelcontextprotocol/inspector python server.py`
- Docstring и типы — это то, что видит модель. Мало узких инструментов лучше, чем много общих; ответы — короткие

## MCP, CLI или Skill: что выбрать

| Ситуация | Выбор | Почему |
|---|---|---|
| Инструмент уже есть в терминале и агент его знает (`git`, `gh`, `psql`) | CLI | нет затрат контекста на описания, меньше частей |
| Внешний сервис с OAuth, типизированные ответы, несколько клиентов | **MCP** | стандартная авторизация и схема, один сервер для всех |
| Повторяемая процедура, чек-лист, «как у нас принято» | Skill | модуль 4 |
| Правило, которое должно выполняться всегда | Hook | модуль 13 |

Описания MCP-инструментов занимают контекст. Claude Code по умолчанию подгружает инструменты по требованию (tool search) — но лишние серверы всё равно отключайте.

## Безопасность MCP: угрозы

- **Prompt injection через результаты инструментов** — страница, тикет, строка в БД содержат «инструкцию» (модуль 12)
- **Tool poisoning** — вредоносное описание инструмента; по спецификации описания недоверенны, пока сервер не доверенный
- **Rug pull и supply chain** — сервер изменил инструменты после одобрения; `npx -y` без пина версии
- **Избыточные права** — токен с write/admin там, где нужно чтение
- **Утечки** — секреты в аргументах и логах; удалённый сервер видит всё, что вы ему отправили

> Инструмент MCP — это выполнение произвольного кода. Согласие пользователя обязательно.

## Безопасность MCP: контроли

```json
{ "permissions": {
    "allow": ["mcp__db__query"],
    "deny":  ["mcp__db__execute"] } }
```

- **Наименьшие права**: read-only креды, минимальные OAuth-scope, allow-список инструментов
- **Пин версий** (`@bytebase/dbhub@X.Y.Z`) и просмотр кода сервера до подключения
- **Хук-аудит**: `PreToolUse` с matcher `mcp__.*` пишет каждый вызов в лог
- Project-серверы из `.mcp.json` требуют одобрения — не жмите «да» не глядя
- Песочница и ограничение исходящей сети для серверов с доступом в интернет

## MCP в агентной системе и в CI

- `stdio`-сервер в `.mcp.json` — это **команда, которая запускается на вашей машине**. Конфиг из чужого PR — недоверенный код (модуль 13, форки)
- В CI перечисляйте разрешённые инструменты явно: `--allowedTools "mcp__db__query"`; креды — секреты CI, только чтение
- В системе из нескольких агентов у каждой роли — **свой набор серверов**: planner читает, implementer пишет в свою ветку, reviewer только комментирует
- MCP — удобная граница для политики: права, аудит и лимиты живут на сервере, а не в промпте

## Далее: долгосрочная память агента

MCP даёт агенту руки: доступ к системам через один протокол. Но права, аудит и границы — по-прежнему ваша работа: сервер — это код, а его вывод — недоверенный текст.

Агенту также нужна память о вас и проекте.
