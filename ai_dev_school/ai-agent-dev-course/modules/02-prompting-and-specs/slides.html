Цели

  • Писать описания задач, снижающие потребность агента в догадках
  • Распознавать разрыв между «тем, что я имел в виду» и «тем, что я написал» — и закрывать его до того, как агент начал работу, а не после

Почему этот модуль сразу после первого

  • Модуль 1: цикл агента — план → действие инструментами → наблюдение → повтор
  • Цикл настолько хорош, насколько хорош запуск
  • Плохой промпт обычно не заставляет агента остановиться и спросить — он заставляет агента уверенно догадаться и продолжить

Сегодня — про контроль над входом в этот цикл.

«Что я имел в виду» vs. «что я написал»

У агента нет вашей ментальной модели, конвенций команды или невысказанных допущений.
Каждый пробел он заполняет наиболее правдоподобной догадкой — не обязательно вашей.

Плохой промпт

«Сделай функцию сортировки лучше»

Хороший промпт

«Отрефактори sort_users() в utils.py: замени bubble sort на встроенный sorted(). Сигнатура не меняется, тесты в test_utils.py проходят без изменений»

Контекст vs. инструкции

  • Контекст — что агенту нужно знать (факты, конвенции, существующие паттерны, что нельзя нарушать)
  • Инструкции — что вам нужно, чтобы он сделал (сама задача, сформулированная один раз и однозначно)
  • Смешение прячет запрос среди мелочей — или даёт инструкцию, которую не с чем сверить

Контекст — что знать

Файл-образец: src/routes/orders.js
Скриншот макета: design/checkout-v2.png
Документация: stripe.com/docs/pagination
Конвенция команды: «у нас везде cursor, не offset»

Инструкция — что сделать

«Добавь курсорную пагинацию в GET /api/orders по тому же паттерну, что в orders.js»

Контекст vs. инструкции — до / после

До (смешано)

«У нас API на Express и Postgres, и в других местах кодовой базы пагинация курсорная, добавь, пожалуйста, пагинацию к эндпоинту списка пользователей, и чтобы было быстро»

После (разделено)

Контекст: Express + Postgres. Существующие
эндпоинты используют курсорную пагинацию
(см. src/routes/orders.js как образец).

Задача: добавить курсорную пагинацию в
GET /api/users по тому же паттерну.

Критерии приёмки

  • Задача без проверяемого определения «готово» — это задача, которую агент завершит неверно, с полной уверенностью
  • Агент в любом случае где-то остановится — вопрос лишь в том, совпадёт ли эта точка с той, что нужна была вам
  • «Проверяемо» = то, что вы (или тесты) можете оценить как да/нет
def test_limit_over_100_returns_400():
    resp = client.get("/api/products?limit=500")
    assert resp.status_code == 400

def test_default_page_has_next_cursor():
    resp = client.get("/api/products")
    assert resp.json()["next_cursor"] is not None

Агент запускает такие тесты сам и видит pass/fail как наблюдение в своём цикле (Модуль 1) — а не гадает, «наверное, готово».

Критерии приёмки — до / после

До

«Добавь пагинацию к эндпоинту продуктов, чтобы не тормозило»

После

Критерии приёмки:
- GET /api/products принимает limit
  (default 20, max 100) и cursor
- В ответе есть next_cursor (string | null)
- limit > 100 → 400 с телом ошибки
- Без параметров → первая страница

Ограничения важны не меньше целей

  • Цель говорит, куда идти. Ограничение — что не сломать по пути.
  • Если ограничения не названы, агент вправе достичь цели самым дешёвым для себя способом — включая тот, что вам не нужен
  • «Не трогай публичный API», «держи всё в одном файле», «без новых зависимостей» — обозначайте границу, а не только пункт назначения
Цель: добавить курсорную пагинацию в GET /api/orders

Не цель (сознательно не делаем сейчас):
- не менять форму ответа для запросов без параметров
- не трогать offset-пагинацию в /api/legacy-reports
- не оптимизировать SQL-запрос, если он укладывается в SLA

Ограничения — до / после

До

«Отрефактори модуль авторизации, чтобы было чище»

После

Отрефактори auth/session.js для читаемости.
Ограничения:
- Не менять сигнатуры в auth/index.js
  (импортируют ещё три сервиса)
- Без новых зависимостей
- Диф не больше ~150 строк
- Существующие тесты проходят без изменений

Антипаттерн №1 — расплывчатый запрос

«Сделай это лучше». «Приведи в порядок обработку ошибок». «Оптимизируй это».

Как это ломает работу агента: у «лучше» нет общего для вас и агента определения — агент выбирает своё и уверенно уходит в него полностью, например переписывает архитектуру обработки ошибок целиком, хотя вы имели в виду два конкретных catch-блока.

Антипаттерн

«Приведи в порядок обработку ошибок в payments/charge.js»

Как надо

«В payments/charge.js оберни вызов Stripe API в try/catch: при ошибке логируй error.code и возвращай {success:false, reason}. Остальные функции файла не трогать»

Антипаттерн №2 — отсутствие «готово»

«Добавь рейт-лимитинг в API».

Как это ломает работу агента: он останавливается на первом же правдоподобном варианте — например, ставит глобальный лимит 100 req/min по IP на все эндпоинты сразу, включая вебхуки, которые как раз ограничивать было нельзя.

Антипаттерн

«Добавь рейт-лимитинг в API»

Как надо

«Рейт-лимитинг на POST /api/login: 5 попыток на IP за 15 минут, при превышении — 429 с заголовком Retry-After. Остальные эндпоинты не трогать»

Антипаттерн №3 — настоящее требование зарыто

«У нас уже был разговор про пагинацию, раньше использовали offset, команде БД это не нравилось... в общем, это должно быть готово до демо в 15:00, поэтому трогай, пожалуйста, только фронтенд, не API.»

Как это ломает работу агента: единственное жёсткое ограничение — последняя часть последнего предложения. Пока агент дочитывает предысторию, оно легко теряется из фокуса — а при сжатии контекста (Модуль 1) может пропасть совсем. На выходе — правки и в API тоже.

Антипаттерн

Длинная предыстория, ограничение зарыто в последнем придаточном последнего предложения

Как надо

«Ограничение: менять только фронтенд, не API. Контекст: переходим с offset на курсор, дедлайн — демо в 15:00»

Анатомия хорошо специфицированной задачи

  1. Контекст — факты и паттерны, которые нужны агенту
  2. Задача — одно однозначное предложение: что построить
  3. Ограничения — что не должно измениться или сломаться
  4. Критерии приёмки — проверяемое определение «готово»
  5. Граничные случаи — что происходит на границах

Не каждой задаче нужны все пять пунктов полностью — но пропуск пункта должен быть осознанным решением, а не случайностью.

## Контекст
Express + Postgres, см. src/routes/orders.js
## Задача
Добавить курсорную пагинацию в GET /api/users
## Ограничения
Без новых зависимостей, диф < 150 строк
## Критерии приёмки
limit ≤ 100, невалидный limit → 400
## Граничные случаи
курсор после последней страницы → []

V1 → V2 → V3

Разбор примера: три захода, одна фича

Фича: добавить пагинацию к GET /api/products. Один и тот же стартовый репозиторий, каждый раз чистая сессия — смотрим, что меняется в результате по мере роста точности.

V1 — расплывчато

Добавь пагинацию к эндпоинту списка продуктов.

Типичное поведение агента: выбирает какой-то вид пагинации (часто offset/limit — самый распространённый паттерн в обучающих данных) с неограниченным или произвольно выбранным лимитом, без гарантии, что это совпадает с конвенциями кодовой базы.

V2 — с ограничениями

Добавь пагинацию к GET /api/products.
- limit: по умолчанию 20, максимум 100
- cursor: непрозрачный, из next_cursor
  предыдущего ответа
- в ответе появляется next_cursor (string | null)

Типичное поведение агента: форма ответа верна — но граничные случаи (невалидный/просроченный курсор, запрос за пределами последней страницы) всё ещё на его усмотрение. Может вернуть 500. Может молча вернуть пустой список.

V3 — полностью специфицировано

...(V2, плюс:)
Граничные случаи:
- невалидный формат курсора → 400
- курсор за последней страницей → пустой
  items, next_cursor: null
- без параметров → первая страница
Критерий приёмки: существующие интеграционные
тесты для GET /api/products проходят без изменений.

Типичное поведение агента: граничные случаи обработаны — потому что они были названы. Точность окупилась ровно там, куда вы её вложили.

Лабораторная работа

  1. Выберите одну небольшую фичу (свою или пример с пагинацией)
  2. Напишите три версии запроса: расплывчато → с ограничениями → полностью специфицировано
  3. Прогоните каждую через чистую сессию агента (без общей истории)
  4. Сравните три получившихся результата

Результат

  • 3 промпта
  • 3 получившихся диффа
  • Краткое сравнение:
    • Что дала дополнительная точность?
    • Где она перестала иметь значение?
