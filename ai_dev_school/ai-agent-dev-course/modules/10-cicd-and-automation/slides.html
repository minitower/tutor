От напарника к участнику пайплайна

  • До сих пор в курсе: человек запускает агента, наблюдает, подтверждает каждый шаг
  • В CI/CD никто не наблюдает пошагово — агент работает без присмотра
  • Тот же цикл, что в Модуле 1 (план → действие → наблюдение → повтор) — но некому поймать плохое решение до того, как оно вступит в силу

Весь модуль — один вопрос: что меняется, когда никто не смотрит?

«Без присмотра» не значит «без контроля» — контроль просто переезжает от «живого человека» к «спроектированной границе».

Хуки: три разные вещи под одним именем

Git-хуки

Скрипты, которые локальный git запускает на событие (pre-commit, pre-push) — выполняются на машине разработчика.

Хуки Claude Code

Команды оболочки, которые запускает сам харнесс агента вокруг вызовов инструментов (PreToolUse, PostToolUse, Stop) — навязывают политику независимо от решения агента.

Хуки CI

Шаг пайплайна, запускаемый событием репозитория (on: pull_request, on: issues) — выполняется на CI-раннере, а не на ноутбуке.

Пример git-хука

.git/hooks/pre-commit (или через фреймворк вроде pre-commit/husky):

#!/usr/bin/env bash
# Блокируем коммит, если агент оставил маркер WIP или похожую на секрет строку
if git diff --cached | grep -qE 'TODO\(agent\)|AKIA[0-9A-Z]{16}'; then
  echo "Заблокировано: неразрешённый маркер агента или возможный секрет в диффе"
  exit 1
fi

Срабатывает до того, как код вообще покинет машину — агент не может обойти хук, если сам не управляет им (никогда не давайте ему такого доступа).

Пример хука Claude Code

.claude/settings.json:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command",
            "command": "scripts/block-dangerous-bash.sh" }
        ]
      }
    ]
  }
}

Обеспечивается харнессом, вне контроля модели — агент не может «уговорить» себя обойти хук, который отклоняет вызов.

Агенты по расписанию

Запускаются по таймеру, без триггерного события — например, ночной аудит зависимостей, еженедельная чистка устаревших issue.

# .github/workflows/nightly-audit.yml
on:
  schedule:
    - cron: "0 3 * * *"
jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: claude -p "Проверь зависимости на известные CVE; для каждой
                         находки открой issue. PR не открывать."

Результат заранее ограничен безопасным по конструкции форматом: issue, а не merge.

Агенты по триггеру

Запускаются в ответ на конкретное событие репозитория, а не по часам.

# .github/workflows/lint-fix.yml
on:
  pull_request:
    types: [opened, synchronize]
jobs:
  lint-fix:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: claude -p "Запусти линтер; исправь только его замечания;
                         закоммить как 'lint: auto-fix' в эту ветку."

Событийная область видимости = агент видит только диф, относящийся именно к этому PR.

Паттерн 1 — Автоисправление линтера

  • Триггер: PR открыт/обновлён → запускается линтер → агент исправляет только его замечания
  • Безопасно по конструкции, если область строго ограничена:
    • трогает только строки, отмеченные линтером
    • коммитит в ветку самого PR, никогда в main
    • неудачное автоисправление просто оставляет ошибку линтера человеку
  • Всё равно требует ревью перед merge — автоисправление это предложение, а не факт

Паттерн 2 — Триаж issue

  • Триггер: on: issues: [opened] → агент навешивает лейблы, находит дубликаты, задаёт уточняющие вопросы, связывает похожие issue/PR
  • Никогда: не закрывает issue, не назначает людей без согласования, не правит заголовки так, чтобы терялась исходная формулировка автора
  • Высокая польза при низком риске — худший случай — неверный лейбл, который дёшево исправить и который не трогает код или данные

Паттерн 3 — Черновик release notes

  • Триггер: запушен тег / срезана релизная ветка → агент собирает черновик заметок из сообщений коммитов и заголовков смерженных PR
  • Ключевое слово — черновик: результат ложится PR-ом в CHANGELOG.md или черновиком GitHub Release, никогда — письмом, постом в Slack или опубликованным релизом
  • Публикация/рассылка — это отдельный шаг, инициируемый человеком, всегда

Области прав доступа для агента без присмотра

  • Права агента без присмотра должны быть уже, чем у интерактивной сессии, а не такими же
  • Запрашивайте каждую возможность отдельно, не выдавайте «админку» по умолчанию: запись в репозиторий (в какие ветки?), может ли комментировать/мержить issue и PR, есть ли креденшл, дотягивающийся за пределы репозитория (Slack, почта, облачный биллинг, prod-БД)
  • Ответ по умолчанию на каждый пункт — нет, пока конкретная задача не обоснует иное
Интерактивная сессия Широкий доступ допустим — рядом живой человек
vs
Агент без присмотра По умолчанию — узко: «нет», пока задача не обоснует иное

Список «никогда без гейта»

Никогда не разрешайте агенту без присмотра делать это без явного шага подтверждения человеком, каким бы удобным это ни казалось:

  1. Опасноgit push --force — переписывает историю, на которую полагаются другие
  2. Опасноудаление данных — снести таблицу, rm за пределами рабочего дерева, закрыть/удалить issue
  3. Опасноотправка чего-либо вовне — письмо, Slack, опубликованный релиз, твит
  4. Опаснотрата денег — облачные расходы, платные вызовы API сверх небольшого фиксированного бюджета

Это ровно те действия, ошибку в которых нельзя отменить повторным запуском.

Песочница — ограничение зоны поражения

  • Запускайте агента в одноразовом окружении, а не в общей инфраструктуре: эфемерный CI-раннер / контейнер, уничтожаемый после job; сервисный аккаунт, ограниченный этим репозиторием; никаких production-креденшлов в окружении job вообще
  • Песочница — это второй слой защиты, а не замена списку «никогда»: она ограничивает ущерб, если граница прав всё же настроена неверно
permissions:
  contents: write     # только этот репозиторий
  pull-requests: write
  # без issues: write, если этому job он не нужен — уберите, не просто игнорируйте

Проектируем гейт: рядом нет живого человека

«Согласование» без живого человека рядом означает, что гейт должен быть структурным, проверяемым автоматически, а не человеком, нажимающим «да» в моменте.

Обязательное ревью PR

Агент может открыть PR, но перед merge нужен человек (или политика ревью: 1 одобрение, CODEOWNERS).

Вывод только черновиком

Артефакт агента неактивен, пока человек его не «продвинет» — черновик релиза, черновик PR, неотправленный changelog.

Защита ветки

main требует прохождения проверок и ревью — даже скомпрометированная учётная запись агента не может смержить в обход.

Пример гейта: защита ветки + обязательное ревью

# настройки репозитория (иллюстративно, не буквальный YAML для вставки)
branch_protection:
  main:
    required_pull_request_reviews:
      required_approving_review_count: 1
      require_code_owner_reviews: true
    restrict_pushes: true       # никаких прямых пушей, включая агента
    required_status_checks: [lint, tests]

Гейт живёт в настройках репозитория, а не в промпте агента — фраза «спроси перед merge» в промпте это пожелание; защита ветки — это стена.

Антипаттерны, которых стоит избегать

  • Агент ревьюит собственный PR — одна и та же учётная запись открывает и одобряет, и гейт теряет смысл целиком
  • Широкий токен, узкий промпт — «просто не делай force-push» в промпте, при этом креденшл технически может его сделать — граница должна работать там, где агент не может с ней «поспорить»
  • Тихий автомерж — любой путь, где «тесты прошли» само по себе мержит в main без шага ревью, убирает гейт, который вы только что спроектировали
  • Один общий токен бота на всё — один скомпрометированный job получает все права, которые вообще нужны были хоть одному job

Лабораторная — подключаем агента к пайплайну

Выберите одно:

  • Автоисправление линтера при открытии PR, коммит в ветку PR, ревью человеком перед merge
  • Черновик записи CHANGELOG.md из коммитов с последнего тега, открывается PR-ом, никогда не мержится автоматически

Требования:

  1. Рабочая конфигурация (файл workflow CI, или git-хук + скрипт)
  2. Конкретный, явный шаг подтверждения перед любым деструктивным или внешне видимым действием

Результат

  • Рабочая конфигурация пайплайна (workflow YAML / скрипт хука)
  • Короткая письменная заметка со списком того, что этой автоматизации не разрешено делать без присмотра — и почему выбрана каждая из границ
  • Привяжите каждую границу к списку «никогда» со слайда о гейтах или к риску, специфичному именно для вашего проекта

Далее: Governance, безопасность и внедрение в команде

Агентам без присмотра нужны границы, заложенные заранее, а не предполагаемые — хуки, области прав и песочницы это механизм. Черновик, а не отправка; предложение, а не merge — структурные гейты всегда надёжнее инструкций в промпте. Список «никогда» (force-push, удаление, отправка, траты) действует независимо от того, насколько удобно было бы его обойти.

Превращаем личные ограждения в командные нормы.
