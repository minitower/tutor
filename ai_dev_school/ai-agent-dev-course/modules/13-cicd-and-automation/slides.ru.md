## От напарника к участнику пайплайна

- До сих пор в курсе: человек запускает агента, наблюдает, подтверждает
  каждый шаг
- В CI/CD пошагово никто не наблюдает — агент работает **без присмотра**
- Тот же цикл из Модуля 1 (план → действие → наблюдение → повтор), но с
  новым ограничением:
  - некому поймать плохое решение **до** того, как оно вступит в силу
- Весь модуль — это один вопрос: **что меняется, когда никто не смотрит?**

---

<!-- Slide 5 -->

## Ключевое противоречие

| Интерактивная сессия | Агент в пайплайне без присмотра |
|---|---|
| Вы подтверждаете каждое рискованное действие вживую | Подтверждать вживую некому |
| Ошибки ловятся за секунды | Ошибка может уйти в прод раньше, чем кто-то заметит |
| Доверие строится шаг за шагом | Доверие нужно заложить заранее, на этапе проектирования |

> «Без присмотра» не значит «без контроля» — контроль просто
> переезжает от «живого человека» к «спроектированной границе».

## Хуки: три разные вещи под одним именем

- **Git-хуки** — скрипты, которые локальный git запускает на событие
  (`pre-commit`, `pre-push`) — выполняются на машине разработчика
- **Хуки Claude Code** — команды оболочки, которые запускает *сам
  харнесс агента* вокруг вызовов инструментов (`PreToolUse`,
  `PostToolUse`, `Stop`, …) — навязывают политику независимо от того,
  что решит агент
- **Хуки CI** — шаг пайплайна, запускаемый событием репозитория
  (`on: pull_request`, `on: issues`) — выполняются на CI-раннере, а не
  на вашем ноутбуке

---

<!-- Slide 7 -->

## Пример git-хука

`.git/hooks/pre-commit` (или через фреймворк вроде `pre-commit`/`husky`):

```bash
#!/usr/bin/env bash
# Блокируем коммит, если агент оставил маркер WIP или похожую на секрет строку
if git diff --cached | grep -qE 'TODO\(agent\)|AKIA[0-9A-Z]{16}'; then
  echo "Заблокировано: неразрешённый маркер агента или возможный секрет в диффе"
  exit 1
fi
```

- Срабатывает до того, как код вообще покинет машину — самое дешёвое
  место поймать ошибку
- Агент не может его обойти, если сам не управляет хуком (никогда не
  давайте ему такого доступа)

<!-- Slide 8 -->

## Пример хука Claude Code

`.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command",
            "command": "scripts/block-dangerous-bash.sh" }
        ]
      }
    ]
  }
}
```

- Обеспечивается харнессом, **вне** контроля модели — агент не может
  «уговорить» себя обойти хук, который отклоняет вызов
- Это механизм, а не политика — что именно запрещать, см. слайды 21–23

---

<!-- Slide 9 -->

## Когда хуки Claude Code нужны агентной системе

| Ситуация | Что использовать |
|---|---|
| «Никогда `rm -rf` и force-push» — должно быть истинным всегда | `PreToolUse` — блок |
| Автоформат и линт после каждой правки | `PostToolUse` (`Edit\|Write`) |
| «Не говори «готово» при красных тестах» | `Stop` |
| Аудит-лог: что агент без присмотра запускал | `PostToolUse` → лог |
| Подмешать контекст (ветка, номер тикета) | `SessionStart` / `UserPromptSubmit` |
| Стиль, предпочтения, «лучше так» | **не хук** — `CLAUDE.md` |

- В CI (`claude -p`) нет человека, который нажмёт «запретить», — хук
  и права остаются **единственной** стеной
- Правило: необратимо или нужно 100% → хук; предпочтение → инструкция

## Как добавить хук в проект

1. Напишите скрипт: `scripts/hooks/block-dangerous-bash.sh` — вход это
   JSON на stdin (`tool_name`, `tool_input`)
2. Подключите в конфиге и закоммитьте
3. `chmod +x scripts/hooks/*.sh`

Где лежит конфиг: `.claude/settings.json` — общий, в git;
`.claude/settings.local.json` — личный, вне git; `~/.claude/settings.json`
— для всех ваших проектов.

```json
{ "hooks": {
  "PreToolUse":  [{ "matcher": "Bash",
    "hooks": [{ "type": "command", "command": "scripts/hooks/block-dangerous-bash.sh" }] }],
  "PostToolUse": [{ "matcher": "Edit|Write",
    "hooks": [{ "type": "command", "command": "ruff format ." }] }],
  "Stop": [{ "hooks": [{ "type": "command", "command": "scripts/hooks/run-tests.sh" }] }]
} }
```

## Скрипт хука: блокируем опасное

```bash
#!/usr/bin/env bash
# scripts/hooks/block-dangerous-bash.sh — вход: JSON на stdin (нужен jq)
cmd=$(jq -r '.tool_input.command')
if echo "$cmd" | grep -qE 'rm -rf|git push.* (--force|-f)( |$)|curl .*\| *(sh|bash)'; then
  echo "Заблокировано политикой: $cmd. Предложи безопасную альтернативу." >&2
  exit 2
fi
exit 0
```

- `exit 0` — разрешить; `exit 2` — **заблокировать**, а `stderr` уходит
  агенту, он читает причину и пробует иначе
- `Stop`-хук с `exit 2` не даёт агенту закончить, пока тесты красные —
  проверяйте поле `stop_hook_active`, чтобы не зациклиться

## Как проектировать хуки

- **Начинайте с политики.** Каждая строка списка «никогда» — это хук
  или право; не наоборот
- **Детерминированные и быстрые:** без LLM внутри, доли секунды,
  предсказуемый результат
- **Fail-closed для опасного:** ошибка самого хука = блок. **Fail-open
  для удобств:** упавший форматтер не должен стопорить работу
- **Понятное сообщение в `stderr`** — его читает агент
- **Чёрный список хрупок:** `sh -c "..."`, base64, другой язык
  обходят регулярку. Хук дополняет права и песочницу, но не заменяет их;
  где можно — используйте allowlist

## Тестируем и защищаем хуки

Хук — это код политики, значит, у него есть тесты:

```python
# tests/hooks/test_block_dangerous.py
import json, subprocess

def run(cmd):
    p = subprocess.run(["scripts/hooks/block-dangerous-bash.sh"], text=True,
                       input=json.dumps({"tool_input": {"command": cmd}}))
    return p.returncode

def test_blocks_force_push(): assert run("git push --force") == 2
def test_allows_status():     assert run("git status") == 0
```

- Защитите сами хуки: `.claude/` и `scripts/hooks/` — в `CODEOWNERS` и
  под deny-правилом записи для агента
- Логируйте каждое срабатывание: блок — это сигнал, а не мусор

## Агенты по расписанию

- Запускаются по таймеру, без триггерного события — например, ночной
  аудит зависимостей, еженедельная чистка устаревших issue

```yaml
# .github/workflows/nightly-audit.yml
on:
  schedule:
    - cron: "0 3 * * *"
jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: claude -p "Проверь зависимости на известные CVE; для каждой
                         находки открой issue. PR не открывать."
```

- Результат заранее ограничен безопасным по конструкции форматом:
  issue, а не merge

---

<!-- Slide 15 -->

## Агенты по триггеру

- Запускаются в ответ на конкретное событие репозитория, а не по часам

```yaml
# .github/workflows/lint-fix.yml
on:
  pull_request:
    types: [opened, synchronize]
jobs:
  lint-fix:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: claude -p "Запусти линтер; исправь только его замечания;
                         закоммить как 'lint: auto-fix' в эту ветку."
```

- Событийная область видимости = агент видит только диф, относящийся
  именно к этому PR

## CI/CD-платформы: GitHub Actions и альтернативы

| Платформа | Конфиг | Триггеры | Запуск агента |
|---|---|---|---|
| **GitHub Actions** | `.github/workflows/*.yml` | `pull_request`, `issues`, `schedule`, теги | `run: claude -p ...` или `anthropics/claude-code-action` |
| **GitLab CI/CD** | `.gitlab-ci.yml` | `merge_request_event`, pipeline schedules | `script: claude -p ...` |
| **Jenkins** | `Jenkinsfile` | webhook, `cron` | `sh 'claude -p ...'` |
| **CircleCI** | `.circleci/config.yml` | webhook, scheduled pipelines | `run: claude -p ...` |
| **Bitbucket / Azure Pipelines** | `bitbucket-pipelines.yml` / `azure-pipelines.yml` | PR, расписание | `script:` |

- Headless `claude -p` работает на любой платформе — отличаются
  триггеры, секреты и права токена, а не идея

<!-- Slide 17 -->

## Тот же агент в GitLab CI

```yaml
# .gitlab-ci.yml
agent-review:
  image: node:22
  timeout: 10 minutes
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - npm install -g @anthropic-ai/claude-code
    - >
      claude -p "Проверь дифф этого MR по чек-листу ревью.
      Только комментарии, ничего не меняй."
      --allowedTools "Read,Grep,Glob" --max-turns 10
  # ANTHROPIC_API_KEY — masked и protected переменная CI
```

- `rules` — аналог `on: pull_request`; `timeout` и `--max-turns` —
  потолок времени и шагов
- `--allowedTools` — агент только читает: комментарий делает
  отдельный шаг с узким токеном

<!-- Slide 18 -->

## Общие требования к агенту в любой CI-платформе

- **Секреты** — masked/protected переменные; не в репозитории, не в
  логах, не в промпте
- **Токен job — минимальный:** `permissions:` (GitHub), `CI_JOB_TOKEN`
  со ограниченной областью (GitLab); OIDC вместо долгоживущих облачных
  ключей
- **PR из форков** не получают секретов; `pull_request_target` с
  чужим кодом на GitHub опасен — агент прочитает и исполнит
  недоверенный контент (см. модуль 12, prompt injection)
- **Пределы:** `timeout`, `--max-turns`, `concurrency` (не запускать
  дважды на один PR), бюджет API
- **Аудит:** сохраняйте лог и вывод агента как артефакт job

## Паттерн 1 — Автоисправление линтера

- Триггер: PR открыт/обновлён → запускается линтер → агент исправляет
  только его замечания
- Безопасно по конструкции, **если** область строго ограничена:
  - трогает только строки, отмеченные линтером
  - коммитит в ветку самого PR, никогда не в `main`
  - неудачное автоисправление просто оставляет ошибку линтера человеку,
    ничего дальше не блокирует
- Всё равно требует ревью перед merge — автоисправление это
  предложение, а не факт

---

<!-- Slide 20 -->

## Паттерн 2 — Триаж issue

- Триггер: `on: issues: [opened]` → агент навешивает лейблы, находит
  дубликаты, задаёт уточняющие вопросы, связывает похожие issue/PR
- Никогда: не закрывает issue, не назначает людей без согласования, не
  правит заголовки так, чтобы терялась исходная формулировка автора
- Высокая польза при низком риске — худший случай — неверный лейбл,
  который дёшево исправить и который не трогает код или данные

---

<!-- Slide 21 -->

## Паттерн 3 — Черновик release notes

- Триггер: запушен тег / срезана релизная ветка → агент собирает
  черновик заметок из сообщений коммитов и заголовков смерженных PR
- Ключевое слово — **черновик**: результат ложится PR-ом в
  `CHANGELOG.md` или черновиком GitHub Release, никогда — письмом,
  постом в Slack или опубликованным релизом
- Публикация/рассылка — это **отдельный** шаг, инициируемый человеком,
  всегда

---

<!-- Slide 22 -->

## Области прав доступа для агента без присмотра

- Права агента без присмотра должны быть **уже**, чем у интерактивной
  сессии, а не такими же
- Запрашивайте каждую возможность отдельно — не выдавайте «админку» по
  умолчанию:
  - запись в репозиторий? в какие ветки?
  - может ли комментировать issue/PR? может ли мержить?
  - есть ли у него хоть один креденшл, дотягивающийся за пределы
    репозитория (Slack, почта, облачный биллинг, prod-БД)?
- Ответ по умолчанию на каждый пункт: **нет**, пока конкретная задача
  не обоснует иное

---

<!-- Slide 23 -->

## Список «никогда без гейта»

Никогда не разрешайте агенту без присмотра делать это **без явного
шага подтверждения человеком**, каким бы удобным это ни казалось:

- `git push --force` (переписывает историю, на которую полагаются
  другие)
- удаление данных (снести таблицу, `rm` за пределами рабочего
  дерева, закрыть/удалить ветку issue)
- отправка чего-либо вовне (письмо, Slack, опубликованный релиз, твит)
- трата денег (облачные расходы, платные вызовы API сверх небольшого
  фиксированного бюджета)

*Это ровно те действия, ошибку в которых нельзя отменить повторным
запуском.*

## Песочница — ограничение зоны поражения

- Запускайте агента в одноразовом окружении, а не в общей
  инфраструктуре:
  - эфемерный CI-раннер / контейнер, уничтожаемый после job
  - сервисный аккаунт, ограниченный *этим репозиторием*, а не всей
    организацией
  - никаких production-креденшлов в окружении job вообще
- Песочница — это второй слой защиты, а не замена списку «никогда»: она
  ограничивает ущерб, *если* граница прав всё же настроена неверно

```yaml
permissions:
  contents: write     # только этот репозиторий
  pull-requests: write
  # без issues: write, если этому job он не нужен — уберите, не просто игнорируйте
```

## Проектируем гейт: рядом нет живого человека

- «Согласование» без живого человека рядом означает, что гейт должен
  быть **структурным**, проверяемым автоматически, а не человеком,
  нажимающим «да» в моменте
- Работающие паттерны:
  - **обязательное ревью PR** — агент может открыть PR, но перед merge
    нужен человек (или политика ревью: 1 одобрение, CODEOWNERS)
  - **вывод только в виде черновика** — артефакт агента неактивен, пока
    человек его не «продвинет» (черновик релиза, черновик PR,
    неотправленный changelog)
  - **защита ветки** — `main` требует прохождения проверок и ревью, так
    что даже скомпрометированная учётная запись агента не может
    смержить в обход

---

<!-- Slide 26 -->

## Пример гейта: защита ветки + обязательное ревью

```yaml
# настройки репозитория (иллюстративно, не буквальный YAML для вставки)
branch_protection:
  main:
    required_pull_request_reviews:
      required_approving_review_count: 1
      require_code_owner_reviews: true
    restrict_pushes: true       # никаких прямых пушей, включая агента
    required_status_checks: [lint, tests]
```

- Гейт живёт в **настройках репозитория**, а не в промпте агента —
  фраза «спроси перед merge» в промпте это пожелание; защита ветки —
  это стена

<!-- Slide 27 -->

## Антипаттерны, которых стоит избегать

- **Агент ревьюит собственный PR** — одна и та же учётная запись
  открывает и одобряет, и гейт теряет смысл целиком
- **Широкий токен, узкий промпт** — «просто не делай force-push» в
  промпте, при этом креденшл *технически может* его сделать — граница
  должна работать там, где агент не может с ней «поспорить»
- **Тихий автомерж** — любой путь, где «тесты прошли» само по себе
  мержит в `main` без шага ревью, убирает гейт, который вы только что
  спроектировали
- **Один общий токен бота на всё** — один скомпрометированный job
  получает все права, которые вообще нужны были хоть одному job

---

<!-- Slide 28 -->

## Паттерны, которые работают вместо антипаттернов

| Антипаттерн | Паттерн вместо него |
|---|---|
| Агент ревьюит собственный PR | Отдельная identity у ревьюера (read-only + комментарии); одобряет человек или `CODEOWNERS` |
| Широкий токен, узкий промпт | Токен на job с `permissions:` ровно под задачу; OIDC |
| Тихий автомерж | Merge queue + обязательные проверки; автомерж только для класса низкого риска с тестами |
| Один общий токен бота | Отдельный бот-аккаунт на роль: triage, lint-fix, release |
| «Спроси перед merge» в промпте | Защита ветки в настройках репозитория |
| Агент правит свои хуки и CI | `CODEOWNERS` на `.github/`, `.claude/`, `scripts/hooks/` |

## Система только из агентов: архитектура

**Issue** → **Planner** → **Implementer** → **Гейты CI** → **Reviewer** → **Merge queue**

| Роль | Права |
|---|---|
| Planner | читает репозиторий, пишет план в issue |
| Implementer | пишет только в свою ветку, открывает PR |
| Гейты CI | тесты, линтеры, сканеры — обычный код, не LLM |
| Reviewer | read-only + комментарии, другая identity |
| Merge queue | мержит только при зелёных проверках и политике |

Человек: пишет политику, выборочно аудитирует, получает эскалации

---

<!-- Slide 30 -->

## Правила системы из агентов

- **Роли = разные identity и права.** Ни одна роль не одобряет
  собственную работу
- **Общаются через артефакты**, а не через общий контекст: issue, PR,
  файл спеки, файл статуса. Состояние живёт в git — можно
  возобновить, проверить, откатить
- **Между агентами — детерминированные гейты:** LLM не единственный
  судья над LLM
- **Идемпотентность:** повторный запуск не даёт дубликатов PR и
  комментариев (ищите существующий, прежде чем создавать)

---

<!-- Slide 31 -->

## Предохранители, наблюдаемость и место человека

- **Бюджеты:** `--max-turns`, `timeout`, лимит итераций «исправь →
  проверь» (например, 3), потолок стоимости на job и на сутки
- **Kill switch:** флаг или переменная, отключающая всех агентов
  разом, — проверьте, что он реально работает
- **Наблюдаемость:** логи хуков, лог действий агента как артефакт,
  метрики: доля откатов, доля эскалаций, стоимость на PR
- **Эскалация:** агент, который не уверен или упёрся в лимит, должен
  позвать человека, а не гадать
- **«Только агенты» ≠ «без ответственного»:** человек владеет политикой
  и выборочным аудитом

---

<!-- Slide 32 -->

## Лабораторная — подключаем агента к пайплайну

Выберите **одно**:
- Автоисправление линтера при открытии PR, коммит в ветку PR, ревью
  человеком перед merge
- Черновик записи `CHANGELOG.md` из коммитов с последнего тега,
  открывается PR-ом, никогда не мержится автоматически

Требования:
1. Рабочая конфигурация (файл workflow CI, или git-хук + скрипт)
2. Конкретный, явный шаг подтверждения перед любым деструктивным или
   внешне видимым действием

## Результат

- Рабочая конфигурация пайплайна (workflow YAML / скрипт хука)
- Короткая письменная заметка со списком того, что этой автоматизации
  **не разрешено** делать без присмотра — и **почему** выбрана каждая
  из границ
  - привяжите каждую границу к списку «никогда» со слайда 23 или к
    риску, специфичному именно для вашего проекта

## Итоги и следующий модуль

- Агентам без присмотра нужны границы, **заложенные заранее**, а не
  предполагаемые — хуки, области прав и песочницы — это механизм
- Черновик, а не отправка. Предложение, а не merge. Структурные гейты
  всегда надёжнее инструкций в промпте
- Список «никогда» (force-push, удаление, отправка, траты) действует
  независимо от того, насколько удобно было бы его обойти
