Как на самом деле работают агентные циклы

Agentic Software Development: From Specs to Shipped Code

План занятия

  • Что вообще значит «агентный» (в отличие от автодополнения)
  • Базовый цикл: план → действие → наблюдение → повтор
  • Разбор реальной трассировки, вызов за вызовом
  • Контекстные окна, память и сжатие (compaction)
  • Права доступа и песочницы
  • Лабораторная: трассируем и аннотируем работу агента

Цели модуля

К концу модуля вы сможете:

  1. Объяснить цикл агента: план → действие через инструменты → наблюдение → повтор
  2. Отличить помощь в стиле автодополнения от агентных инструментов
  3. Объяснить, что такое контекстное окно и почему длинные сессии сжимаются (compaction)
  4. Объяснить, почему важные решения должны жить в файлах, а не в истории чата
Обычный чат Отвечает текстом на сообщение — и всё
vs
Агент + инструменты Читает файлы, запускает команды, проверяет результат

Что значит «агентный»?

  • Это не «автодополнение, только умнее»
  • Это программа, которая умеет:
    • действовать в реальном мире (читать/писать файлы, запускать команды)
    • наблюдать, что произошло на самом деле
    • решать, что делать дальше, опираясь на это наблюдение
  • Агентом инструмент делает именно цикл, а не сама модель
Чат-модель отвечает на вопросы. Агент делает работу и проверяет результат этой работы.

Базовый цикл

ПЛАНчто делать дальше, учитывая цель?
→
ДЕЙСТВИЕвызов инструмента
→
НАБЛЮДЕНИЕрезультат возвращается в контекст

↻ повтор, пока задача не решена (или тупик)

Это паттерн ReAct (Reason + Act): модель рассуждает о следующем шаге, действует, наблюдает результат — и следующее рассуждение уже опирается на это наблюдение.

Шаг 1 — План

  • Опираясь на цель и всё, что есть в контексте, модель выбирает одно следующее действие
  • Это не фиксированный сценарий — план пересматривается после каждого наблюдения
  • Планирование дешёво пересчитать заново — в этом и весь смысл цикла
«Нужно добавить флаг --verbose. Я ещё не знаю, где в этом проекте разбираются флаги CLI — сначала найду существующие определения флагов.»

Это рассуждение соответствует конкретному состоянию, которое агент держит между шагами:

{
  "goal": "Добавить флаг --verbose в CLI",
  "completed_steps": [],
  "next_action": {
    "reasoning": "Не знаю, где определяются флаги — сначала найду существующие",
    "tool": "grep",
    "input": { "pattern": "add_argument", "path": "src/cli.py" }
  },
  "open_questions": []
}

Шаг 2 — Действие через инструменты

  • План превращается в структурированный вызов инструмента, а не в свободный текст
  • Примеры: read_file, grep, run_tests, edit_file, bash
{
  "tool": "grep",
  "input": { "pattern": "add_argument", "path": "src/cli.py" }
}

Вызов инструмента — это интерфейс между «размышлением» и «действием»

Шаг 3 — Наблюдение

  • Результат инструмента (stdout, содержимое файла, диф, ошибка) добавляется обратно в контекст модели
  • Агент не «предполагает» успех — он читает то, что реально вернулось
$ grep add_argument src/cli.py
src/cli.py:14:    parser.add_argument("--output", ...)
src/cli.py:18:    parser.add_argument("--dry-run", ...)

Именно этот шаг вообще делает возможной верификацию

Шаг 4 — Повтор и остановка

Цикл продолжается, пока не наступит одно из:

  • выполнено условие завершения задачи (тесты прошли, файл изменён как требовалось)
  • агент зашёл в тупик и спрашивает человека
  • действие заблокировано запросом на разрешение
  • достигнут жёсткий лимит (число шагов, время, контекст)

Правильно остановиться сложнее, чем кажется — подробнее в Модуле 9.

Полный цикл с аннотациями

Задача: «Добавить флаг --verbose в CLI»

  1. План найти, где определяются флаги
  2. Действие grep "add_argument" src/cli.py
  3. Наблюдение найдено 2 существующих флага, один и тот же паттерн
  4. План добавить новый флаг по этому паттерну
  5. Действие edit_file src/cli.py (+1 строка)
  6. Наблюдение диф применился без конфликтов
  7. План проверить, что ничего не сломалось
  8. Действие run_tests
  9. Наблюдение 42 пройдено, 0 упало
  10. План готово — подвести итог для пользователя

Разбор трассировки — почему случился каждый вызов

№Вызов инструментаПочему
1grep add_argumentУзнать существующее соглашение, прежде чем добавлять к нему своё
2read_file src/cli.pyУточнить точное место вставки и импорты
3edit_fileВнести минимальное изменение
4run_testsУбедиться, что изменение ничего не сломало

Именно такую таблицу вы будете строить в результате лабораторной.

В проде это смотрят как трассировку (tracing), а не как чат

Каждый вызов инструмента — отдельный span (OpenTelemetry-совместимый формат): id, длительность, вход/выход и срез состояния сразу после шага.

{
  "trace_id": "a1b2c3", "span_id": "s1",
  "name": "tool_call: grep",
  "duration_ms": 42,
  "input": { "pattern": "add_argument", "path": "src/cli.py" },
  "output": { "matches": 2 },
  "state_after": { "completed_steps": 1, "open_questions": 0 }
}

Контекстные окна — что это такое

  • Контекстное окно — это всё, что модель «видит» на данном шаге:
    • системный промпт / инструкции
    • история диалога
    • содержимое прочитанных файлов
    • результаты вызовов инструментов
Оно конечно. Представьте его как рабочий стол, а не архив — работать можно только с тем, что лежит на столе прямо сейчас.

Ограничения контекста на практике

  • Чтение огромного файла или многословный вывод команды может занять значительную долю доступного пространства за один шаг
  • Эффекты по мере заполнения сессии:
    • более ранние инструкции «вытесняются» из фокуса внимания
    • агент может повторно прочитать файл, который уже видел
    • качество может проседать ближе к пределу
  • Хорошие агенты читают узко: конкретные строки, отфильтрованный grep

grep / ripgrep

Точный текстовый поиск по репозиторию — быстро и дёшево по контексту, но находит только то, что совпадает буквально

RAG по кодовой базе

Код заранее превращён в эмбеддинги и лежит в векторной базе; агент ищет по смыслу запроса, а не по точной строке

Code graph

Граф символов и вызовов (кто кого вызывает, кто что импортирует) — навигация по структуре, а не по тексту

Все три — способы прочитать «ровно то, что нужно», не затягивая в контекст весь репозиторий целиком.

Память и сжатие (compaction)

  • Когда сессия становится длинной, инструмент сжимает её: более ранние шаги суммаризируются, чтобы диалог снова уместился в окно
  • Переживает сжатие: текущая цель, ключевые решения, состояние файлов
  • Теряется: точные формулировки из прошлого, второстепенные детали, ход рассуждений, приведший к решению
Сжатие — это фича, а не баг. Но оно с потерями. Планируйте это заранее.

Решения должны жить в файлах

  • История чата не является надёжным хранилищем — она сжимается или теряется вместе с сессией
  • Надёжная память — это файлы в репозитории:
    • CLAUDE.md / AGENTS.md — постоянные инструкции для агента
    • спецификации, ADR, комментарии в коде — устойчивые решения
Правило: если потерю было бы обидно допустить — это должно быть в файле, а не только в том, что вы напечатали в чате.

Права доступа и песочницы

  • Агент спрашивает разрешение перед рискованными, труднообратимыми действиями:
    • выполнение произвольных команд оболочки
    • изменение/удаление файлов вне рабочего набора
    • доступ к сети, установка пакетов
  • Дело не в неуверенности модели — это осознанно заложенная граница доверия
  • Право на чтение ≠ право на запись ≠ право на выполнение
  1. Опасноrm -rf — необратимое удаление
  2. Опасноcurl ... | sh — выполнение кода из сети без просмотра
  3. Опасноgit push --force — может затереть чужую историю
  4. Опасночтение .env / доступа к секретам

Итог — агентный подход vs. чат / автодополнение

Чат / автодополнениеАгентный цикл
ПредлагаетПланирует, действует, наблюдает, повторяет

Типичные сбои, на которые стоит обращать внимание

  • Зацикленный повтор — одно и то же неудачное действие без новой информации
  • Незаметное расширение задачи — «исправление» того, о чём никто не просил
  • Исчерпание контекста посреди задачи — потеря исходной цели
  • Излишнее доверие к выводу инструмента — вывод «успех» не перепроверяется

Привычки против этого начнём строить с Модуля 2, а системно — в Модуле 9.

Лабораторная — трассируем агента

  1. Возьмите небольшой незнакомый учебный репозиторий
  2. Дайте агенту одну задачу: «добавь флаг CLI, который делает X»
  3. Залогируйте каждый вызов инструмента: чтения, grep, изменения, запуски тестов
  4. Рядом с каждым — одно предложение: почему, по-вашему, агент это сделал?
Цель: увидеть цикл со слайдов 6–12 вживую, в своей собственной трассировке.

Для лекции: та же трассировка в формате OpenAI-совместимого API

{ "role": "assistant", "tool_calls": [{
    "id": "call_1", "type": "function",
    "function": { "name": "grep",
      "arguments": "{\"pattern\":\"add_argument\",\"path\":\"src/cli.py\"}" }
}]}
{ "role": "tool", "tool_call_id": "call_1",
  "content": "src/cli.py:14: add_argument(\"--output\")\nsrc/cli.py:18: add_argument(\"--dry-run\")" }

Результат

  • Аннотированная трассировка вызовов инструментов (как таблица на слайде 12)
  • Описание на полстраницы, отвечающее на вопросы:
    • На что агент потратил больше всего «усилий» — на чтение/понимание или на написание кода?
    • Что-нибудь удивило вас в порядке действий?

Далее: Промптинг и постановка задачи

Агентный подход = план → действие → наблюдение → повтор с реальной верификацией. Контекстные окна конечны; сжатие происходит с потерями — устойчивую память нужно класть в файлы. Права доступа существуют потому, что действие/наблюдение затрагивают реальный мир.

Точность на входе — точность на выходе.
