# Модуль 7 — Детерминированные дизайн-системы для UI, созданного ИИ

## Зачем нужен этот модуль

Сессия агента не помнит, *почему* в прошлый раз был выбран именно этот
синий, эта шкала отступов или этот шрифт. Если «дизайн» существует
только как разговор в чате, каждая новая сессия заново выводит его из
расплывчатых прилагательных («современный», «чистый») и выдаёт заметно
другой результат. Это та же проблема, которую Модуль 6 (DDD) решает для
поведения фичи, применённая к визуальному оформлению: детерминизм
достигается переносом решений из разговора в файлы, которые агент
читает заново каждую сессию, а не каким-то приёмом промптинга.

## Цели обучения
- Выносить дизайн-решения во внешние артефакты, которые агент читает
  перед генерацией любого UI, вместо того чтобы заново выводить их из
  прилагательных каждую сессию
- Понимать, почему именно конкретные значения (hex-коды, шкала
  отступов, стек шрифтов) обеспечивают детерминизм — описательный язык
  как раз и есть место, где закрадывается расхождение от сессии к сессии
- Замыкать цикл визуальной верификацией, а не полагаться на текстовый
  дифф для отлова расхождений в дизайне

## Ключевые концепции

**1. Файл дизайн-токенов — значения, а не проза.**
Настоящий `tokens.css`/`tokens.json` (или эквивалент), который реально
импортируется кодом, а не просто документация о палитре:
```css
:root {
  --color-bg: #0b0d10;
  --color-accent: #6ee7ff;
  --font-heading: "Inter", system-ui, sans-serif;
  --space-unit: 8px;
  --radius-base: 6px;
}
```
Поскольку токены потребляются кодом, расхождение структурно затруднено —
агенту приходится трогать файл токенов, чтобы ввести новый цвет, а это
видимое, проверяемое изменение, а не незаметное.

Как это выглядит на практике: добавить токен — одна строка в
`tokens.css`, доступная сразу через `var(--color-accent-2)`, без
отдельной сборки. Агент подключается к файлу тем же путём, что и
человек — по правилу в `CLAUDE.md` (см. пункт 3). Типичная структура
папки:
```
design/
  tokens.css   # источник истины — импортируется в index.html
  system.md    # паттерны и обоснование
```

**2. Документ дизайн-системы — паттерны и обоснование.**
Короткий документ (одна страница, не брендбук): сетка макета,
контрольные точки (breakpoints), состояния компонентов
(hover/active/disabled), тон/голос, 1–2 референсных сайта. Это «почему»,
которое один только файл токенов передать не может.

**3. Правило на уровне репозитория, принудительно требующее проверки.**
Ни один из артефактов не поможет, если агент не знает, что нужно их
искать. Это должно быть явной инструкцией в `CLAUDE.md`/`AGENTS.md`, а
не предположением:
```md
## Design
Before any UI/styling work, read design/tokens.css and design/system.md.
Do not introduce new colors, fonts, or spacing values outside the tokens
file — extend the tokens file instead and use the new token.
```

**4. Упаковать повторяющуюся дизайн-работу как Skill.**
Если страницы/компоненты строятся часто, оберните «построить страницу по
нашей дизайн-системе» как Skill (Модуль 6.5 /
[practice-tasks.md](../practice-tasks.md)), который всегда сначала
загружает токены + документ системы. Это делает проверку происходящей
по построению, а не зависящей от памяти.

Skill — это папка, а не файл: обязательный `SKILL.md` (фронтматтер
`name`/`description`, по которому агент решает, грузить ли skill, плюс
тело-markdown с шагами) и, при необходимости, `references/*.md` для
деталей. Пример из этого курса:
```
.claude/skills/
  write-slides-html/
    SKILL.md
    references/
      components.md
      icons.md
```
Skill — тоже файл в репозитории, поэтому его может написать сам агент —
для этого есть мета-skill `skill-creator`, проводящий через структуру и
формулировку `description`.

**5. Верифицировать визуально, а не только чтением диффа.**
Только текстовое ревью упускает расхождения в дизайне. Отрендерите
страницу (dev-сервер + предпросмотр в браузере, или скриншот) и
сравнивайте с документом дизайна каждую сессию — отлавливайте регрессии
немедленно, а не после того, как они накопятся за недели сессий.

Это может делать и сам агент: поднять dev-сервер, открыть страницу,
сделать скриншот и проверить DOM программно — например,
`element.scrollHeight <= element.clientHeight` детерминированно ловит
переполнение, без человека, решающего «на глаз».

## Лабораторная работа

1. Напишите файл токенов и одностраничный документ дизайн-системы для
   небольшого многостраничного/многокомпонентного UI (достаточно 3–4
   экранов или компонентов).
2. Добавьте правило в `CLAUDE.md`/`AGENTS.md`, указывающее на оба
   документа.
3. **Сессия A:** в свежей сессии постройте UI, используя только файл
   токенов, документ дизайна и правило репозитория — без дополнительных
   устных указаний по дизайну сверх самой фичи.
4. **Сессия B:** снова свежая сессия (без памяти о Сессии A), постройте
   *другую* страницу/компонент из того же UI с теми же ограничениями.
   Сделайте скриншоты обеих и сравните визуальную согласованность.
5. **Сессия C (контрольная):** свежая сессия, тот же запрос на фичу, но
   *без* указания на файл токенов или документ — просто «сделай
   современно и согласованно с остальной частью сайта». Сделайте
   скриншот и сравните с A/B, чтобы увидеть расхождение напрямую.

## Результат
- Файл токенов и документ дизайн-системы
- Фрагмент `CLAUDE.md`/`AGENTS.md`
- Скриншоты из Сессий A, B и C
- Краткое описание: где A и B совпали, где C разошлась, и прослеживается
  ли какое-либо расхождение в A/B до того, что токены/документ оставили
  недоспецифицированным (если да, это пробел в документе, который нужно
  закрыть — та же дисциплина, что и шаг корректировки спецификации в
  Модуле 6)

## Вопросы для обсуждения
- В какой момент документ дизайн-системы становится настолько
  подробным, что его дороже поддерживать, чем предотвращаемое им
  расхождение?
- Должны ли дизайн-токены жить в той же спецификации, что и
  функциональные требования, или оставаться отдельным документом со
  своим циклом обновления?
- Как это меняется для дизайна, который намеренно должен варьироваться
  (например, генеративные/художественные страницы), а не оставаться
  согласованным?
