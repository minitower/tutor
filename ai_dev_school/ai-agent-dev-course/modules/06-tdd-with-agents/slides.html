Модуль 6

TDD с агентами

Тесты как спецификация

Agentic Software Development: From Specs to Shipped Code

План занятия

  • Почему тесты — спецификация лучше, чем текст, для агента
  • Red/green/refactor с агентом за рулём
  • Разбор примера: баг-репорт → падающий тест → исправление
  • Связь с DDD: спецификация → тест-кейсы → код; как найти кейсы до первого падения
  • Тесты на примерах vs. property-based тесты (и откуда берётся генератор)
  • Почему падающие тесты снижают галлюцинации
  • Лабораторная: только баг-репорт, без подсказок
  • Результат и подведение итогов

Цели занятия

  • Использовать тесты как исполняемую, недвусмысленную спецификацию для агента
  • Понимать, почему падающий тест, написанный до исправления, снижает галлюцинации агента
  • Знать, когда TDD с агентами — подходящий инструмент, а когда нет

Почему TDD важен ещё больше с агентами

  • Для человека TDD — это в основном вопрос дисциплины
  • Для агента это вопрос прицеливания — дать модели недвусмысленное определение «готово»
  • Текстовую спецификацию можно выполнить формально, упустив суть
У падающего теста есть ровно один законный способ стать зелёным.

Краткое напоминание: Red / Green / Refactor

Redтест на несуществующее поведение, убедиться, что падает
→
Greenминимум кода, чтобы тест прошёл
→
Refactorнавести порядок, тесты остаются зелёными

↻ повторять маленькими шагами

Цикл с агентом за рулём

  1. Агент пишет падающий тест
  2. Вы (или CI) подтверждаете, что он падает — и падает по правильной причине
  3. Агент реализует исправление
  4. Агент (или вы) подтверждает, что весь набор тестов зелёный
  5. Агент делает рефакторинг
  6. Повторить

Шаг 2 — тот самый, который пропускают люди, а агенты пропускают ещё чаще.

Связь с DDD: документ → тесты → код

Спекацель, граничные случаи, критерии приёмки (Модуль 3)
→
Redкаждый критерий → падающий тест
→
Greenагент реализует, тесты зелёные
→
Обновить спекуновый случай — в документ и в тест

↻ документ остаётся правдивым, пока тесты зелёные

Спецификация говорит, что должно быть. Тест проверяет, что так и есть.

Как найти тест-кейсы до первого падения

Из спецификации

Каждый критерий приёмки и каждый граничный случай — минимум один тест. Список кейсов уже написан в документе.

Из границ

N−1, N, N+1; ноль, пусто, максимум. Именно так ловится баг «ровно 10».

Из вопроса агенту

«Перечисли кейсы текстом, без кода». Вы вычёркиваете лишнее и добавляете пропущенное — до первого теста.

Баг-репорт — это один готовый кейс. Вопрос: какие соседние кейсы он не показал?

Тесты для каждой новой фичи — прямо в документе

## Test cases   (пишутся до кода)
- [x] 10 шт → скидка 10%      test_bulk_discount_applies_at_exactly_10_items
- [x] 9 шт → без скидки       test_no_discount_at_9_items
- [ ] 0 шт → сумма 0          test_zero_quantity
- [ ] сумма ≤ полной цены     test_discount_never_exceeds_full_price
  • Раздел Test cases в спецификации фичи: строка в списке → тест → код
  • «Готово» = все чекбоксы закрыты, тесты зелёные, документ обновлён
  • Новый баг: сначала строка в списке, потом тест, потом исправление
«Клиенты жалуются: при покупке ровно 10 единиц оптовая скидка не применяется. При 11 единицах всё работает».

Это весь баг-репорт, который получает агент — ни имён файлов, ни стектрейса, ни предполагаемой причины.

Шаг 1 — Написать падающий тест

def test_bulk_discount_applies_at_exactly_10_items():
    total = calculate_discount(quantity=10, unit_price=5.00)
    assert total == 45.00  # 10 * 5.00 * 0.9
  • Превращает баг-репорт в одно конкретное, проверяемое утверждение
  • Запустить его сейчас — до того, как трогать код реализации

Шаг 2 — Убедиться, что падает по правильной причине

AssertionError: 50.0 != 45.00
  • Хорошее падение: математика скидки действительно неверна, ровно как в репорте
  • Плохое падение (тревожный сигнал): NameError, ImportError, сломанная фикстура — неправильный тест, а не код

Пропуск этой проверки — вот как агенты «чинят» опечатки и считают задачу выполненной.

Шаг 3 — Реализовать исправление, убедиться в зелёном

- if quantity > 10:
+ if quantity >= 10:
      total *= 0.9
  • Перезапустить новый тест → проходит
  • Перезапустить весь набор тестов → ничего больше не сломалось
  • Только после этого агент трогает что-то ещё

Шаг 4 — Рефакторинг (шаг, который агенты пропускают)

BULK_DISCOUNT_THRESHOLD = 10
BULK_DISCOUNT_RATE = 0.9

if quantity >= BULK_DISCOUNT_THRESHOLD:
    total *= BULK_DISCOUNT_RATE

Зелёные тесты ощущаются агентом как «готово» — рефакторинг не требует ни один тест, поэтому попросить об этом должны вы. Зелёные тесты — это страховка для уборки кода, а не повод её пропустить.

Тесты на примерах как спецификация

def test_bulk_discount_applies_at_exactly_10_items(): ...
def test_no_discount_at_9_items(): ...
def test_discount_on_a_large_order(): ...
  • Точные, читаемые, дёшево обходятся агенту в написании
  • Хороши ровно настолько, насколько хороши примеры, которые кто-то догадался написать
  • Агент с радостью напишет примеры, подтверждающие его собственное предположение о том, где проходит граница

Property-based тесты как спецификация

  • Вместо конкретных входных данных формулируется инвариант, который должен выполняться для всех входов
  • Генератор создаёт сотни случаев — включая те, что никто не додумался написать вручную
  • Инвариант для этой функции: итоговая сумма со скидкой никогда не превышает полную цену

Откуда берётся генератор

st.integers(0, 10_000)       # генератор целых: чаще берёт 0, 1, границы
st.floats(0.01, 10_000)      # и «неудобные» дробные значения

orders = st.builds(Order,    # составной объект — из простых генераторов
    quantity=st.integers(0, 10_000),
    unit_price=st.floats(0.01, 10_000))
  • Генератор (strategy) — описание пространства входов; библиотека сама сэмплирует его
  • Диапазоны берём из контракта в спецификации — агент не должен выдумывать их сам
  • При падении Hypothesis сжимает пример до минимального; закрепите его обычным тестом на примерах

Разбор примера: property-based тест

from hypothesis import given, strategies as st

@given(
    quantity=st.integers(min_value=0, max_value=10_000),
    unit_price=st.floats(min_value=0.01, max_value=10_000),
)
def test_discount_never_exceeds_full_price(quantity, unit_price):
    assert calculate_discount(quantity, unit_price) <= quantity * unit_price

Отлавливает случаи, которых тесты на примерах никогда не касались: quantity=0, огромные заказы, округление float.

Выбор подхода, когда за рулём агент

На примерахProperty-based
Лучше всего дляточного сценария из баг-репортапокрытия границ и инвариантов
Агент пишетбыстро, прямо из репортанужен инвариант, сформулированный вами
Основной рискузость — проверяет только то, что представилирасплывчатость при слабом инварианте

Используйте тесты на примерах, чтобы воспроизвести баг; добавляйте property-based, чтобы проверить, что исправление действительно общее.

Почему падающие тесты снижают галлюцинации

  • Текстовый баг-репорт неоднозначен — агент заполняет пробелы догадкой, поданной как уверенность
  • Падающий тест — проверяемый контракт: исправление либо зелёное, либо нет — никакое убедительное объяснение это не заменит
  • Он заставляет агента запустить что-то, а не утверждать, что оно сработало

Режим отказа: тест, который проходит по неправильной причине

def test_bulk_discount():
    assert True  # "проверено вручную"

Крайний пример, но паттерн реальный: избыточные моки, проверка константы, тестирование мока вместо кода.

Решение: прочитать текст ошибки падающего теста, прежде чем доверять зелёному.

Где это сочетается хорошо — а где плохо

Хорошо

Исправление багов, чётко определённая логика, чистые функции, парсеры, вычисления — «правильный» ответ уже известен

Плохо

Исследовательская работа над UI, задачи вида «чтобы ощущалось правильно» — вы бы писали проверки на ответ, которого ещё нет

TDD с агентами предполагает, что тест верен до того, как его написали — это реальное допущение, а не данность.

Лабораторная: только баг-репорт

Вы дадите агенту только баг-репорт — без имён файлов, без подсказок, без предполагаемой причины.

Обязательная последовательность:

  1. Написать тест, который воспроизводит баг и падает
  2. Убедиться, что падение происходит по правильной причине
  3. Реализовать исправление
  4. Убедиться, что тест проходит и ничего другого не сломалось

Разбор лабораторной — как выглядит «готово»

  • Два отдельных коммита: падающий тест, затем исправление — никогда не сквошить
  • Дифф коммита с падающим тестом не должен содержать никаких изменений в продакшн-коде
  • Перед merge: перечитать assertion — он действительно кодирует баг-репорт, или что-то лишь смежное с ним?

Результат

  • Два коммита: падающий тест → исправление, раздельные в истории
  • Однострочная заметка: действительно ли первая попытка агента написать тест уловила баг, или потребовалась коррекция?
Эта заметка — настоящий сигнал: она показывает, насколько можно доверять следующему тесту агента без присмотра.

Тесты как исполняемая спецификация закрывают агенту пространство для догадок. Red/green/refactor — «убедиться, что падает правильно» — это шаг, который на самом деле имеет значение.

Спецификация (Модуль 3) говорит, что проверять; тесты — её исполняемая версия.

Что происходит без документа заранее и вообще без тестов.
