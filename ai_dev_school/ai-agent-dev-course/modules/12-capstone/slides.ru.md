<!-- Slide 4 -->
## Повторение: весь инструментарий, бок о бок

| Методология | Хороша для | Слаба для | Артефакт на выходе |
|---|---|---|---|
| DDD (спецификация-первой) | Фич с реальной неоднозначностью, много участников | Мелких правок (лишние накладные расходы) | Устойчивый документ-спецификация |
| План-первой | Рефакторингов, рискованных изменений в нескольких файлах | Быстрого исследования | Одноразовый план (или ADR) |
| TDD с агентом | Багфиксов, чётко определённой логики | Расплывчатой/исследовательской UI-работы | Набор тестов |
| Разговорный подход | Прототипов, разовых скриптов | Всего, что требует бумажного следа | Ничего (только история чата) |
| Ревью несколькими агентами | Критичных, чувствительных к безопасности изменений | Мелких, низкорисковых изменений | Транскрипт ревью |

Этот модуль — не новая техника, а осознанное применение сразу нескольких из них на одной фиче.

<!-- Slide 5 -->
## Сегодняшняя фича: экспорт в CSV с фильтром по датам

- Кнопка «Export CSV» на дашборде отчётов
- Экспорт учитывает уже выбранный на экране диапазон дат
- Достаточно маленькая, чтобы пройти от начала до конца за одну сессию
- Достаточно настоящая, чтобы затронуть UI-элемент, границу данных **и**
  граничный случай, достойный теста
- Связывает воедино Модули 3, 4, 5, 6 и 9 — один сквозной пример

---

<!-- Slide 6 -->
## Шаг 1 — Специфицируем (Модуль 3, DDD)

```markdown
## Goal
Let a user export the currently filtered report rows to a CSV file,
matching the date range they've already selected on the dashboard.

## Non-goals
- No new file formats (CSV only, not XLSX/PDF)
- No server-side scheduled/emailed exports — synchronous, on-click only

## Interface
- A button labeled "Export CSV" next to the date-range picker
- Downloads `report_<start>_<end>.csv`
- Columns match the visible table columns, same order
```

---

<!-- Slide 7 -->
## Шаг 1 — Граничные случаи и критерии приёмки

```markdown
## Edge cases
- No rows in range → header-only CSV, not an error
- Range spans a DST transition → use UTC dates everywhere, to avoid
  off-by-one-day bugs
- An active column filter is applied too → export respects it, not
  just the date range

## Acceptance criteria
- A known 3-row range → CSV with exactly those 3 rows + header
- An empty range → header-only CSV, not a 500 or a blank file
- Filename uses UTC dates
```

Осознанно оставлено открытым: делать кнопку неактивной или скрывать её,
когда экспортировать нечего — это мелкий UI-вопрос, а не ключевое поведение.

---

<!-- Slide 8 -->
## Почему эта спецификация имеет правильный размер

- Явно называет **граничный случай с переходом на летнее/зимнее время** —
  именно то, что теряется, если фичу заказали устно, в разговоре
- Явно называет «**учитывает и другие фильтры тоже**» — не только
  очевидный случай с диапазоном дат
- Оставляет открытым ровно один действительно мелкий вопрос, вместо того
  чтобы переспецифицировать всё подряд
- Посторонний человек мог бы реализовать фичу без единого уточняющего
  вопроса по **поведению** — только по одному явно отмеченному открытому вопросу

## Шаг 2 — Проверяем дизайн-систему (Модуль 4)

Правило из `CLAUDE.md` репозитория срабатывает автоматически, ещё до
написания UI-кода:

> Before any UI/styling work, read `design/tokens.css` and
> `design/system.md`. Do not introduce new colors, fonts, or spacing
> values outside the tokens file.

- Новая кнопка использует существующие токены `--color-accent` /
  `--space-unit`
- Здесь ничего не нужно **делать** — только проверить, что правило
  сработало (посмотреть дифф на предмет «сырых» hex-значений)
- Ноль дополнительных усилий, потому что правило в репозитории уже
  существовало

<!-- Slide 10 -->
## Шаг 3 — Планируем перед реализацией (Модуль 5)

Спецификация идёт как задача; используется режим планирования, потому
что фича затрагивает и фронтенд, и бэкенд:

```
1. Add GET /api/reports/export — same query params as /api/reports
2. Reuse existing filter-building logic from ReportsQuery (don't
   duplicate it)
3. Serialize rows to CSV using the existing column config
4. Frontend: add the button, wire it to trigger the download
5. Open question from spec: propose DISABLING (not hiding) the button
   when the result set is empty — flagging for approval
```

<!-- Slide 11 -->
## Шаг 3 — Что поймал контрольный пункт утверждения

- Пункт 2 — **переиспользование логики фильтрации** — это ровно то, что
  стоит поймать **до** написания кода
- Оставь это без внимания — и получится вторая, чуть иная копия логики
  фильтрации, которая со временем разойдётся с первой
- Ревью человеком: план утверждён как есть, включая решение про
  неактивную кнопку
- Цена поймать это здесь: прочитать план из 5 строк. Цена поймать это
  постфактум в ревью: второй дифф.

<!-- Slide 12 -->
## Шаг 4 — TDD основной логики (Модуль 6): баг с переходом на летнее время

Рискованная часть — не кнопка, а работа с датами. Сначала тест:

```python
def test_export_filename_uses_utc_dates_across_dst_transition():
    # range crosses a US DST transition (Mar 10, 2024)
    filename = build_export_filename(start="2024-03-09", end="2024-03-11")
    assert filename == "report_2024-03-09_2024-03-11.csv"
```

**Запуск → падает.** Билдер имени файла использовал локальное время
сервера, из-за чего дата смещалась на день. Исправление внесено.
Повторный запуск → **проходит.**

---

<!-- Slide 13 -->
## Шаг 4 — TDD основной логики: форма ответа для пустого диапазона

```python
def test_export_empty_range_returns_header_only_csv():
    csv_output = export_reports_csv(start="2024-01-01", end="2024-01-01", filters={})
    lines = csv_output.strip().split("\n")
    assert len(lines) == 1  # header only, no rows, no error
```

Написан первым, падает на наивной первой реализации — та возвращала
**204 без тела** вместо CSV с одной строкой заголовков. Именно такое
расхождение и ловит записанный критерий приёмки — до того, как это
уйдёт в прод.

<!-- Slide 14 -->
## Шаг 5 — Ревью вторым агентом (паттерн Модуля 8)

Свежая сессия. На вход — только дифф и исходная спецификация, **без
доступа** к рассуждениям первой сессии:

> - Совпадает со спецификацией по формату имени файла и поведению на
>   пустом диапазоне ✓
> - Граничный случай «учитывает и другие фильтры тоже» не покрыт ни
>   одним тестом — эндпоинт принимает параметр `filters`, но нет теста,
>   сочетающего его с диапазоном дат. Рекомендуется добавить тест перед мёрджем.
> - Незначительно: новый эндпоинт не использует общий rate-limiting
>   с остальными `/api/reports/*` — стоит подтвердить, что это осознанно.

<!-- Slide 15 -->
## Шаг 5 — Почему важны обе находки

- Находка 1 — это **прямой разрыв между спецификацией и тестами**,
  ровно то, на поиск чего натренирована привычка ревью из Модуля 9
- Находка 2 — это **вопрос об объёме собственной работы**, который у
  исполнителя не было причин задать самому себе — не ошибка, а
  непроверенное допущение
- Ни одна находка не потребовала от ревьюера заново разбираться в
  фиче — только сверить дифф со спецификацией, строка за строкой

---

<!-- Slide 16 -->
## Шаг 6 — Замыкаем цикл: обновляем спецификацию

По дисциплине Модуля 3 — как только недостающий тест добавлен, а
вопрос про rate limit решён (осознанно: экспорт вызывается редко):

```markdown
## Acceptance criteria (addendum)
- Exporting with both a date range and a non-date column filter
  reflects both (added after review caught this was untested)

## Notes
- Export endpoint intentionally uses a separate, higher rate limit —
  exports are infrequent, user-triggered actions
```

Теперь спецификация соответствует тому, что реально было построено —
следующий читатель увидит настоящую картину, а не версию первого дня.

## Синтез — что поймала каждая техника

- **DDD (3)** — граничные случаи с переходом на летнее время и
  несколькими фильтрами пойманы **ещё до того, как появился код**
- **Дизайн-токены (4)** — кнопка осталась в рамках палитры, без
  дополнительных усилий
- **План-первой (5)** — риск дублирования кода пойман до того, как код
  был написан
- **TDD (6)** — пойман реальный баг (неверная временная зона) и ответ
  неверной формы (204 вместо CSV с заголовками)
- **Ревью (9)** — пойман разрыв между спецификацией и тестами, который
  не заметили ни автор спецификации, ни исполнитель
- Ни одна техника здесь не поймала бы **всё** — у каждой есть слепое
  пятно ровно там, где сильна другая

**Вот Модуль 12 одной фразой: перестаньте выбирать по умолчанию — начните осознанно комбинировать.**

<!-- Slide 18 -->
## Задание capstone

Выберите фичу, достаточно существенную, чтобы быть достойной
спецификации. Затем примените ту же дисциплину, которую вы только что
увидели, — на своей фиче:

1. **Специфицируйте её** (Модуль 3, DDD) — цель, не-цели, интерфейсы,
   граничные случаи, критерии приёмки
2. **Спланируйте её** (Модуль 5) — агент предлагает план по
   спецификации; вы проверяете и утверждаете его первым
3. **Примените TDD к основной логике** (Модуль 6) — как минимум к
   частям с реальной бизнес-логикой
4. **Проведите ревью вторым агентом** (Модуль 8) — свежая сессия,
   фокус на спецификации и безопасности
5. **Обновите спецификацию**, чтобы она отражала то, что реально построено

---

<!-- Slide 19 -->
## Как выбрать свою фичу

- Достаточно существенная, чтобы быть достойной спецификации — не
  однострочная правка
- Ничего не приходит в голову? Возьмите небольшой сквозной срез: новый
  аутентифицированный API-эндпоинт с персистентностью и набором тестов
- Где-то внутри должна быть настоящая бизнес-логика — не только
  CRUD-каркас
- Плюс в карму, если найдётся настоящий граничный случай вроде бага с
  летним временем — то, что разговорный запрос скорее всего пропустил бы

## Результат

- Репозиторий (или дифф) для фичи
- **Документ спецификации, план, тесты и заметки ревью** — как
  отдельные артефакты, а не всё скомкано в одно сообщение коммита
- **Ретроспектива** (от половины до одной страницы) — следующий слайд

<!-- Slide 21 -->
## Вопрос для ретроспективы

> Как бы это выглядело, если бы вы построили это в одиночку, без
> агента, полгода назад?

- Где выбор методологии **сэкономил время**?
- Где он добавил **церемоний, которые не окупились**?
- Честная ретроспектива называет реальные компромиссы — «ИИ — это
  здорово» ретроспективой не является

---

<!-- Slide 22 -->
## Критерии самооценки (групповой формат)

- **Качество спецификации** — сможет ли по ней реализовать фичу
  посторонний человек?
- **Соответствие плана и спецификации** — соответствовала ли
  реализация утверждённому плану; задокументированы ли расхождения?
- **Качество тестов** — фиксируют ли тесты реальное поведение, или
  только счастливый путь?
- **Строгость ревью** — поймал ли ревьюер что-то реальное, или это
  формальный штамп?
- **Честность ретро** — названы ли реальные компромиссы, а не только похвала

## Сегодняшняя лабораторная

1. Выберите фичу (5 минут — сверьтесь с соседом или преподавателем)
2. Напишите спецификацию — цель, не-цели, интерфейсы, граничные
   случаи, критерии приёмки
3. Получите план, проверьте его, утвердите
4. Примените TDD к самой рискованной части логики — не к шаблонному коду
5. Проведите ревью в свежей сессии по спецификации и безопасности
6. Замкните цикл: обновите спецификацию, напишите ретро

Работайте в своём темпе — это единственная лабораторная, рассчитанная
на оставшуюся часть занятия.

- **10–11**: как безопасно встроить всё это в пайплайн и в команду
