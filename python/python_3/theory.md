# Asyncio: теория, которая не поместилась в ноутбук

Практический ноутбук (`main.ipynb`) показывает *как писать* асинхронный код. Этот файл —
про то, *почему* он работает именно так, и про вещи, которые обычно всплывают уже в реальных
проектах.

## 1. Что происходит "под капотом"

### Coroutine, Future, Task — в чём разница

- **Coroutine** (`async def`) — это описание работы. Сама по себе она ничего не планирует
  и не выполняется, пока её не передали в event loop.
- **Future** — низкоуровневый примитив: объект-обещание результата, который появится
  в будущем. У него есть состояние (pending / done / cancelled) и колбэки, которые
  вызываются при завершении.
- **Task** — это `Future` + корутина. `asyncio.create_task(coro)` оборачивает корутину
  в `Task`, который сам продвигает её выполнение шаг за шагом, взаимодействуя с event loop.
  Именно `Task` умеет быть отменённым, иметь исключение, статус и т.д.

Схематично: `Task` наследуется от `Future` и знает, как исполнять именно корутины.
Когда вы пишете `await coro`, интерпретатор либо создаёт `Task` неявно (если await
происходит на верхнем уровне через `asyncio.run`), либо просто продвигает выполнение
корутины внутри уже существующей задачи.

### Event loop изнутри

Event loop — это, по сути, бесконечный цикл, который:

1. Смотрит, какие файловые дескрипторы/сокеты готовы к чтению/записи (через `select`,
   `epoll`, `kqueue` или `IOCP` на Windows — конкретный механизм зависит от ОС).
2. Смотрит, у каких таймеров (`asyncio.sleep`, таймауты) истекло время.
3. Вызывает соответствующие callback'и, которые "будят" ожидающие корутины и продвигают
   их до следующего `await`.

`await` — это точка, где корутина говорит event loop'у: "я жду внешнего события,
можешь пока заняться чем-то другим". Именно поэтому блокирующий вызов вроде `time.sleep`
внутри корутины — это катастрофа: он ничего не говорит event loop'у, а просто
физически останавливает поток, в котором крутится весь loop.

### Откуда это появилось

Синтаксис `async`/`await` — не изобретение с нуля. До PEP 492 (Python 3.5) то же самое
делали через генераторы и `yield from` (`@asyncio.coroutine` + `yield from other_coro()`).
`async`/`await` — синтаксический сахар над той же идеей: приостанавливаемая функция,
которая умеет возвращать управление наружу и получать его обратно.

## 2. asyncio vs threading vs multiprocessing

Все три — про конкурентность, но решают разные задачи:

| Подход | Что даёт | Когда использовать | Ограничение |
|---|---|---|---|
| `asyncio` | Конкурентность в одном потоке, кооперативная | Много I/O-bound операций (сеть, диск, БД) с поддержкой async-библиотек | Один блокирующий вызов стопорит весь loop |
| `threading` | Конкурентность через ОС-потоки, вытесняющая | I/O-bound код, который нельзя переписать на asyncio (старые блокирующие библиотеки) | GIL не даёт параллелизма для CPU-bound кода |
| `multiprocessing` | Настоящий параллелизм через отдельные процессы | CPU-bound задачи (вычисления, обработка данных) | Дорогое создание процессов, сериализация данных между ними |

GIL (Global Interpreter Lock) не даёт двум потокам одновременно исполнять байткод Python,
поэтому `threading` не ускоряет CPU-bound код. Но во время I/O-операции (сетевой запрос,
чтение файла) GIL освобождается — здесь и `threading`, и `asyncio` реально помогают.
`asyncio` обычно предпочтительнее `threading` для I/O-bound нагрузки с большим числом
одновременных операций (тысячи "лёгких" задач-корутин дешевле, чем тысячи ОС-потоков).

Если задача CPU-bound (тяжёлые вычисления) — ни `asyncio`, ни `threading` не спасут,
нужен `multiprocessing` или вынос вычислений во внешний процесс/сервис.

## 3. Совмещение с CPU-bound кодом: `run_in_executor`

Если внутри асинхронной программы всё же нужно выполнить блокирующую или тяжёлую
CPU-bound операцию, её выносят из event loop в пул потоков или процессов:

```python
import asyncio
from concurrent.futures import ProcessPoolExecutor

def cpu_heavy(n: int) -> int:
    return sum(i * i for i in range(n))

async def main():
    loop = asyncio.get_running_loop()
    with ProcessPoolExecutor() as pool:
        result = await loop.run_in_executor(pool, cpu_heavy, 10_000_000)
    print(result)
```

`run_in_executor` возвращает `Future`, который можно `await`-ить — event loop не блокируется,
пока тяжёлая функция считается в отдельном потоке/процессе. Для блокирующего I/O
(например, синхронной библиотеки без async-версии) обычно достаточно `ThreadPoolExecutor`.

## 4. Структурная конкурентность: `asyncio.TaskGroup` (Python 3.11+)

`asyncio.gather` — исторически основной способ запускать корутины конкурентно, но у него
есть шероховатости: при исключении в одной из задач остальные не отменяются автоматически
(если явно не обработать), а `return_exceptions=True` требует ручной проверки результатов.

`TaskGroup` — более безопасная альтернатива:

```python
async def main():
    async with asyncio.TaskGroup() as tg:
        tg.create_task(fetch_async('A', 1))
        tg.create_task(fetch_async('B', 1))
    # здесь все задачи гарантированно завершены (или отменены при ошибке)
```

Если внутри группы падает исключение, `TaskGroup` автоматически отменяет остальные
задачи и пробрасывает наружу `ExceptionGroup` со всеми ошибками сразу — это и называется
"структурной конкурентностью": время жизни дочерних задач жёстко привязано к блоку `async with`,
они не могут "утечь" за его пределы.

## 5. Ограничение параллелизма: `asyncio.Semaphore`

Если нужно, например, сделать 1000 запросов, но не более 10 одновременно (чтобы не положить
сервер или не упереться в лимиты API), используют семафор:

```python
sem = asyncio.Semaphore(10)

async def fetch_limited(url):
    async with sem:
        return await fetch(url)

async def main():
    await asyncio.gather(*(fetch_limited(u) for u in urls))
```

`Semaphore` пропускает не больше N задач одновременно в защищённый блок, остальные ждут
своей очереди — в отличие от `Lock` (максимум 1), здесь можно задать любое ограничение.

## 6. Асинхронные генераторы, comprehensions и контекстные менеджеры

- **`async for`** — итерация по асинхронному источнику (например, постраничная выгрузка
  из API), где каждое "получение следующего элемента" само является `await`-операцией.
- **Асинхронный генератор**: функция с `async def` и `yield` внутри — работает как обычный
  генератор, но можно `await` внутри тела.

  ```python
  async def stream_numbers(n):
      for i in range(n):
          await asyncio.sleep(0.1)
          yield i

  async def main():
      async for num in stream_numbers(5):
          print(num)
  ```

- **`async with`** — асинхронный контекстный менеджер, реализующий `__aenter__`/`__aexit__`
  (например, для соединений с БД, HTTP-сессий: открытие/закрытие само по себе I/O-операция).
- **Асинхронные comprehensions**: `[x async for x in stream_numbers(5)]` работает точно
  так же, как обычный list comprehension, но с асинхронным источником.

## 7. Частые ошибки на практике

- **Забытый `await`.** `fetch_async(...)` без `await` просто создаёт объект-корутину
  и ничего не выполняет — Python выдаст `RuntimeWarning: coroutine was never awaited`.
  Ноутбук это уже показывал явно.
- **"Fire-and-forget" задачи теряют ссылку.** `asyncio.create_task(coro())` без
  сохранения результата в переменную может быть удалён сборщиком мусора до завершения —
  задача просто оборвётся. Стандартная практика — хранить ссылки в множестве:

  ```python
  background_tasks = set()

  task = asyncio.create_task(coro())
  background_tasks.add(task)
  task.add_done_callback(background_tasks.discard)
  ```

- **Проглоченные исключения в незаависимых задачах.** Если `Task` упал с исключением,
  но его никто не `await`-ит и не проверяет через `task.exception()`, ошибка молча
  осядет внутри объекта задачи и никогда не будет замечена (кроме предупреждения в логах
  при сборке мусора).
- **Смешивание синхронного и асинхронного кода.** Любой блокирующий вызов внутри корутины
  (синхронный HTTP-клиент, `time.sleep`, тяжёлые вычисления) стопорит весь event loop —
  см. пример в ноутбуке.

## 8. Инструменты и экосистема

- **Отладка:** переменная окружения `PYTHONASYNCIODEBUG=1` или `asyncio.run(main(), debug=True)`
  включает предупреждения о медленных callback'ах и незавершённых корутинах.
- **`uvloop`** — альтернативная реализация event loop поверх `libuv`, заметно быстрее
  стандартного на Linux/macOS (на Windows не поддерживается).
- **Асинхронные библиотеки:** `aiohttp`/`httpx` (HTTP-клиенты), `asyncpg`/`aiomysql`
  (базы данных), `aiofiles` (файлы), `motor` (MongoDB) — синхронные версии этих библиотек
  внутри корутины будут блокировать loop так же, как `time.sleep`.
- **Альтернативы `asyncio`:** `trio` и `curio` — другие асинхронные фреймворки с похожими
  идеями, но более строгой моделью структурной конкурентности (во многом на них
  ориентировался `TaskGroup`, добавленный в сам `asyncio`).
