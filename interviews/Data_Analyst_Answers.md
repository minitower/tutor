# Ответы: Data Analyst

## 1. SQL

**1. INNER / LEFT / FULL OUTER JOIN**
- `INNER JOIN` — только строки с совпадением в обеих таблицах. Пример: заказы, у которых есть привязанный клиент в справочнике.
- `LEFT JOIN` — все строки левой таблицы + совпадения справа (иначе `NULL`). Пример: все клиенты, включая тех, кто ещё не сделал заказ.
- `FULL OUTER JOIN` — объединение обеих таблиц целиком с `NULL` там, где совпадений нет. Пример: сверка данных из двух разных систем.

**2. Оконные функции**
Позволяют считать значения относительно "окна" строк без схлопывания результата в одну запись:
```sql
-- Ранг клиента по сумме покупок
SELECT customer_id, total_amount,
       RANK() OVER (ORDER BY total_amount DESC) AS rnk
FROM customer_totals;

-- Накопительная сумма продаж по месяцам
SELECT month, amount,
       SUM(amount) OVER (ORDER BY month) AS running_total
FROM monthly_sales;
```
Использовал(а), например, для расчёта доли клиента в общих продажах региона или для поиска "первого события" пользователя.

**3. GROUP BY vs PARTITION BY**
`GROUP BY` схлопывает строки в одну на группу и допускает только агрегаты и группирующие поля в `SELECT`. `PARTITION BY` (в оконных функциях) не схлопывает строки — каждая исходная строка остаётся, но расчёт ведётся в разрезе своей группы (партиции).

**4. Клиенты с покупками в двух последовательных месяцах**
```sql
WITH monthly AS (
    SELECT DISTINCT customer_id, DATE_TRUNC('month', order_date) AS mth
    FROM orders
),
with_prev AS (
    SELECT customer_id, mth,
           LAG(mth) OVER (PARTITION BY customer_id ORDER BY mth) AS prev_mth
    FROM monthly
)
SELECT DISTINCT customer_id
FROM with_prev
WHERE mth = prev_mth + INTERVAL '1 month';
```

**5. Поиск и удаление дубликатов**
```sql
WITH ranked AS (
    SELECT *,
           ROW_NUMBER() OVER (PARTITION BY customer_id, order_date, amount
                               ORDER BY order_id) AS rn
    FROM orders
)
DELETE FROM orders
WHERE order_id IN (SELECT order_id FROM ranked WHERE rn > 1);
```
Сначала лучше сделать `SELECT` с `rn > 1`, чтобы убедиться, что группировка по нужным полям действительно выделяет дубликаты, и только потом удалять.

**6. CTE vs подзапросы**
CTE (`WITH ...`) делает запрос читаемым, разбивая логику на именованные, последовательные шаги, и его можно переиспользовать несколько раз в одном запросе. Подзапросы (особенно вложенные) быстрее приводят к нечитаемому коду при усложнении логики. С точки зрения производительности разница обычно минимальна и зависит от конкретной СУБД и её оптимизатора.

**7. NULL в агрегатах и джойнах**
Агрегатные функции (`SUM`, `AVG`, `COUNT(column)`) игнорируют `NULL` — это может искажать результат, если не учитывать это явно (например, `AVG` считается только по непустым значениям, а не по всем строкам). В джойнах `NULL` никогда не равен `NULL`, поэтому джойн по полю с `NULL` не даст совпадения — нужно либо предварительно заменить `NULL` на значение по умолчанию (`COALESCE`), либо явно обрабатывать такие строки отдельно.

## 2. Статистика и математическая база

**1. Среднее, медиана, мода**
Среднее — сумма значений делённая на количество, чувствительно к выбросам. Медиана — значение, делящее выборку пополам, устойчива к выбросам. Мода — наиболее часто встречающееся значение, полезна для категориальных данных. Медиана более информативна, когда распределение скошено (например, доходы населения или суммы чеков с редкими очень крупными покупками).

**2. Стандартное отклонение и дисперсия**
Дисперсия — средний квадрат отклонений от среднего, стандартное отклонение — корень из дисперсии (выражено в тех же единицах, что и исходные данные, поэтому интерпретировать легче). В бизнесе показывает разброс/стабильность метрики: например, высокое стандартное отклонение времени доставки говорит о нестабильности процесса, даже если среднее время в норме.

**3. Статистическая значимость и p-value**
Статистическая значимость показывает, насколько вероятно, что наблюдаемый эффект — не случайность. p-value — вероятность получить наблюдаемый (или более выраженный) результат при условии, что на самом деле никакого эффекта нет (нулевая гипотеза верна). Маленький p-value (обычно < 0.05) — повод отклонить нулевую гипотезу, но это не доказательство практической значимости эффекта и не вероятность того, что гипотеза верна.

**4. Корреляция и причинность**
Корреляция показывает статистическую связь между двумя переменными, но не доказывает, что одна вызывает другую — возможна обратная причинность, третий скрытый фактор или случайное совпадение. Классический пример: продажи мороженого и число утоплений коррелируют летом, но причина в обеих — жаркая погода, а не в том, что мороженое вызывает утопления.

**5. A/B-тестирование**
Сравнение двух (или более) вариантов продукта/функции на случайно разделённых группах пользователей для оценки влияния изменения на метрику. Размер выборки определяется через расчёт мощности теста (power analysis) — исходя из ожидаемого минимального эффекта (MDE), базового уровня конверсии, желаемого уровня значимости (обычно 0.05) и мощности (обычно 0.8). Длительность теста выбирают так, чтобы захватить полный бизнес-цикл (например, неделю целиком из-за дневной сезонности) и набрать достаточный объём наблюдений.

**6. Доверительный интервал**
Диапазон значений, в котором с заданной вероятностью (например, 95%) находится истинное значение параметра генеральной совокупности. Интерпретация: если повторить эксперимент много раз, в 95% случаев построенный таким образом интервал будет содержать истинное значение — это не означает "95% вероятность, что истинное значение лежит именно в этом конкретном интервале".

**7. Скошенное распределение**
Вместо среднего использовать медиану, вместо стандартного отклонения — межквартильный размах (IQR). Также можно рассмотреть логарифмическое преобразование данных перед дальнейшим анализом или использовать процентили (например, p50, p90, p99) для более полной картины.

**8. Выбросы**
Методы обнаружения: правило 3 сигм (значения дальше 3 стандартных отклонений от среднего), метод межквартильного размаха (значения за пределами `Q1 - 1.5*IQR` и `Q3 + 1.5*IQR`), визуально — box plot или scatter plot. Важно не удалять выбросы автоматически, а сначала разобраться, ошибка это в данных или реальное, но редкое событие.

## 3. Работа с данными (Excel / Python / инструменты)

**1. Инструменты и рабочий процесс**
Типичный процесс: получить/выгрузить данные (SQL или экспорт), проверить качество и структуру, провести исследовательский анализ (EDA), построить нужные агрегации/визуализации, оформить выводы для заказчика. Стоит рассказать, какие инструменты используются на каждом этапе конкретно у себя (например, SQL для выгрузки → Pandas для трансформации → Power BI/Excel для визуализации).

**2. Сводная таблица vs SUMIFS**
Сводная таблица подходит для быстрого исследовательского анализа с гибкой перегруппировкой полей "мышкой" и получением многомерного среза данных. `SUMIFS`/`СУММЕСЛИМН` удобнее, когда нужен статичный расчёт в фиксированной ячейке, встроенный в дальнейшие формулы, или когда требуется обновляемый "живой" отчёт без ручного обновления сводной таблицы.

**3. Объединение таблиц и обработка пропусков в Pandas**
```python
merged = orders.merge(customers, on='customer_id', how='left')
merged['amount'] = merged['amount'].fillna(0)
merged = merged.dropna(subset=['customer_id'])
```
Выбор `how` (`left`/`inner`/`outer`) зависит от того, какие строки обязательно нужно сохранить. Для пропусков — либо заполнение значением по умолчанию/медианой, либо удаление строк, в зависимости от доли пропусков и их значимости для анализа.

**4. Проверка качества данных перед анализом**
Проверка на дубликаты, диапазоны значений (нет ли отрицательных сумм там, где не должно быть), долю пропущенных значений по колонкам, соответствие типов данных, сверка общих сумм/количества строк с исходным источником, проверка на аномальные выбросы, которые могут быть ошибкой выгрузки.

**5. Автоматизация рутинного отчёта**
Пример подхода: заменить ручное копирование данных на SQL-запрос/скрипт (Python), который выгружает и агрегирует данные, настроить шаблон отчёта (Excel-макрос, Power BI dataset с обновлением по расписанию, или Python-скрипт с рассылкой), чтобы отчёт формировался автоматически без ручного труда.

## 4. Визуализация и коммуникация результатов

**1. Выбор типа графика**
- Динамика во времени → линейный график.
- Сравнение категорий → столбчатая диаграмма (горизонтальная при длинных названиях/многих категориях).
- Распределение → гистограмма или box plot.
- Связь между переменными → scatter plot.
Выбор всегда определяется вопросом, на который график должен ответить, а не "красотой".

**2. Частые ошибки визуализации**
Обрезанная ось Y, создающая ложное впечатление о масштабе разницы; слишком много цветов/категорий на одном графике; круговые диаграммы с большим числом сегментов (глазу сложно сравнивать площади/углы); 3D-эффекты, искажающие восприятие пропорций; отсутствие подписей осей и единиц измерения.

**3. Представление результатов нетехнической аудитории**
Начинать с главного вывода и рекомендации, а не с методологии; убирать технические детали (p-value, код) из основной презентации, оставляя их в приложении на случай вопросов; использовать простые визуализации с явным акцентом на ключевую цифру; формулировать выводы в терминах бизнес-действий ("рекомендую снизить цену на X", а не "коэффициент корреляции составил 0.7").

**4. Дашборд vs разовый отчёт**
Дашборд — живой, регулярно обновляемый инструмент для мониторинга метрик в динамике, обычно интерактивный. Разовый отчёт (ad-hoc) — статичный анализ под конкретный вопрос в конкретный момент времени, обычно с более глубоким разбором причин, а не просто набором цифр.

## 5. Бизнес-мышление и решение задач

**1. Падение продаж на 15%**
План: 1) подтвердить, что это не ошибка в данных (сверить источник); 2) декомпозировать падение — по регионам, продуктам, каналам, сегментам клиентов, чтобы понять, равномерное падение или локализованное; 3) сравнить с сезонностью прошлых лет; 4) проверить внешние факторы (акции конкурентов, изменения цен, сбои на сайте, изменения в рекламных кампаниях); 5) разделить эффект на "меньше клиентов" vs "меньше средний чек" vs "меньше конверсия"; 6) сформулировать гипотезы и проверить их данными, прежде чем делать выводы.

**2. Выбор North Star Metric**
Метрика должна отражать ценность, которую продукт даёт пользователю, и коррелировать с долгосрочным бизнес-успехом (а не быть просто удобной для замера). Выбирается совместно с продуктовой командой исходя из бизнес-модели — например, для маркетплейса это может быть число завершённых транзакций, а не просто трафик.

**3. Запрос без чёткого вопроса**
Сначала стоит попытаться сузить задачу через уточняющие вопросы (какое решение планируется принять, какой горизонт интересует). Если это невозможно, начать с базового исследовательского анализа (EDA) — динамика ключевых метрик, аномалии, сегментация — и на основе найденного сформулировать 2–3 конкретные гипотезы для дальнейшего обсуждения с заказчиком, вместо того чтобы пытаться "покрыть всё".

**4. Сезонность vs тренд**
Тренд — устойчивое долгосрочное изменение метрики в одном направлении. Сезонность — регулярно повторяющиеся колебания, привязанные к календарю (день недели, месяц, праздники). Разделить их можно через декомпозицию временного ряда (например, метод STL: тренд + сезонность + остаток) или сравнение year-over-year по одинаковым периодам, чтобы исключить влияние сезонности при оценке тренда.

**5. Пример влияния анализа на решение**
Ответ индивидуальный — важно показать конкретную цепочку: какой был вопрос → какой анализ провели → какое решение приняли на основе этого → какой измеримый эффект получили.

**6. Приоритизация запросов**
Оценивать запросы по влиянию на бизнес и срочности (например, матрица важность/срочность), уточнять у заказчиков реальный дедлайн и цель запроса, по возможности группировать похожие запросы, прозрачно коммуницировать сроки и очередь всем заинтересованным сторонам, чтобы избежать ощущения "тишины".

## 6. Практическая задача

**1. Retention по когортам (месяц первой покупки)**
```sql
WITH first_purchase AS (
    SELECT user_id, DATE_TRUNC('month', MIN(order_date)) AS cohort_month
    FROM orders
    GROUP BY user_id
),
activity AS (
    SELECT o.user_id, fp.cohort_month,
           DATE_TRUNC('month', o.order_date) AS activity_month
    FROM orders o
    JOIN first_purchase fp ON fp.user_id = o.user_id
)
SELECT cohort_month,
       DATE_PART('month', AGE(activity_month, cohort_month)) AS month_number,
       COUNT(DISTINCT user_id) AS active_users
FROM activity
GROUP BY cohort_month, month_number
ORDER BY cohort_month, month_number;
```
Далее строится таблица когорт (cohort_month × month_number) с долей вернувшихся пользователей от размера когорты.

**2. Выявление аномальных дней трафика**
Подход: посчитать скользящее среднее и стандартное отклонение трафика (например, за последние 28 дней, чтобы учесть недельную сезонность), пометить дни, отклоняющиеся более чем на 2–3 сигмы, как аномальные; для каждой аномалии сопоставить с внешними событиями (маркетинговая кампания, технический сбой, праздник) и проверить, не совпадает ли аномалия с днём недели/сезонным паттерном, прежде чем считать её "настоящей" аномалией.

**3. Конверсия воронки**
```sql
WITH funnel AS (
    SELECT
        COUNT(DISTINCT CASE WHEN event = 'view' THEN user_id END) AS views,
        COUNT(DISTINCT CASE WHEN event = 'add_to_cart' THEN user_id END) AS carts,
        COUNT(DISTINCT CASE WHEN event = 'purchase' THEN user_id END) AS purchases
    FROM events
)
SELECT views, carts, purchases,
       carts * 1.0 / NULLIF(views, 0) AS view_to_cart_rate,
       purchases * 1.0 / NULLIF(carts, 0) AS cart_to_purchase_rate,
       purchases * 1.0 / NULLIF(views, 0) AS overall_conversion
FROM funnel;
```
Для более строгого расчёта стоит учитывать, что пользователь должен пройти шаги именно в правильной последовательности (например, через оконные функции с сортировкой по времени события на пользователя), а не просто иметь событие где-то в истории.
