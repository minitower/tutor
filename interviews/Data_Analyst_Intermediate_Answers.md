# Ответы: Data Analyst (Intermediate)

## 1. SQL (продвинутый уровень)

**1. RANK() vs DENSE_RANK() vs ROW_NUMBER()**
- `ROW_NUMBER()` — уникальный последовательный номер строки, даже при одинаковых значениях.
- `RANK()` — одинаковым значениям присваивает одинаковый ранг, но пропускает следующие номера (1, 1, 3).
- `DENSE_RANK()` — одинаковым значениям присваивает одинаковый ранг, без пропусков (1, 1, 2).
`DENSE_RANK()` нужен, например, когда считаем "топ-3 категории по продажам" и хотим включить все категории, разделившие 3-е место, не теряя место из-за пропуска номеров.

**2. Рекурсивный CTE**
```sql
WITH RECURSIVE org_chart AS (
    SELECT employee_id, manager_id, name, 1 AS level
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    SELECT e.employee_id, e.manager_id, e.name, oc.level + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.employee_id
)
SELECT * FROM org_chart;
```
Используется для обхода иерархических структур произвольной глубины: оргструктура, дерево категорий товаров, вложенные комментарии.

**3. Оптимизация медленного запроса**
Смотрю на execution plan: ищу full table scan там, где ожидается использование индекса, оцениваю порядок джойнов и оценку кардинальности (насколько верно СУБД предсказывает число строк на каждом шаге). Практические шаги: добавить индексы на поля джойна и фильтрации, отфильтровать данные как можно раньше (до джойнов), избегать `SELECT *`, разбить агрегацию на предагрегированные подзапросы/материализованные вьюхи, проверить, не приводит ли неявное приведение типов к отказу от индекса.

**4. UNION vs UNION ALL**
`UNION` убирает дубликаты, для чего СУБД выполняет дополнительную сортировку/дедупликацию — это дороже. `UNION ALL` просто объединяет результаты без проверки на дубликаты и работает быстрее. Если заранее известно, что множества не пересекаются или дубликаты допустимы/нужны, всегда предпочтительнее `UNION ALL`.

**5. Скользящее среднее**
```sql
SELECT day, revenue,
       AVG(revenue) OVER (
           ORDER BY day
           ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
       ) AS moving_avg_7d
FROM daily_revenue;
```

**6. Индексы**
Индекс — структура данных (обычно B-tree), ускоряющая поиск строк по значению колонки, за счёт избежания полного сканирования таблицы. Признак нехватки индекса — full table scan в плане выполнения на большой таблице при фильтрации/джойне по конкретному полю. Обратная сторона: каждый индекс замедляет `INSERT`/`UPDATE`/`DELETE`, так как его тоже нужно обновлять, и занимает дополнительное место — поэтому индексы не добавляют "про запас" на таблицы с интенсивной записью.

**7. Gaps and islands**
```sql
WITH flagged AS (
    SELECT user_id, activity_date,
           activity_date - (ROW_NUMBER() OVER (
               PARTITION BY user_id ORDER BY activity_date
           ))::int * INTERVAL '1 day' AS grp
    FROM user_activity
)
SELECT user_id, MIN(activity_date) AS period_start, MAX(activity_date) AS period_end
FROM flagged
GROUP BY user_id, grp
ORDER BY user_id, period_start;
```
Идея: вычесть из даты порядковый номер строки — внутри непрерывного периода это выражение остаётся константой, что позволяет сгруппировать строки в "острова".

## 2. Статистика и A/B-тестирование (углублённо)

**1. Ошибки I и II рода**
Ошибка первого рода (α) — отклонить верную нулевую гипотезу (ложноположительный результат, "увидели эффект, которого нет"). Ошибка второго рода (β) — не отклонить неверную нулевую гипотезу (ложноотрицательный, "пропустили реальный эффект"). Уровень значимости — это допустимая вероятность ошибки I рода, мощность теста (1 − β) — вероятность обнаружить реальный эффект, если он есть. Снижение α при фиксированной выборке увеличивает β, поэтому это всегда компромисс.

**2. Проблема множественных сравнений**
При проверке множества гипотез одновременно (например, эффект на 10 метриках сразу) вероятность получить хотя бы один ложноположительный результат растёт с числом тестов. Поправка Бонферрони делит порог значимости на число сравнений (консервативно, повышает риск ошибки II рода). Метод контроля FDR (Benjamini-Hochberg) менее консервативен и контролирует долю ложных срабатываний среди значимых результатов, что чаще предпочтительнее на практике.

**3. Значимый, но незначимый по эффекту результат**
Статистическая значимость при очень большой выборке может проявиться даже при пренебрежимо малом эффекте. В таком случае важно оценивать не только p-value, но и размер эффекта (effect size) и его практическую/бизнес-значимость — стоит ли внедрение риска и затрат ради, например, +0.1% к конверсии.

**4. Peeking problem**
Если многократно проверять результаты теста по мере накопления данных и останавливать его, как только видна значимость, реальная вероятность ложноположительного результата оказывается сильно выше заявленных 5%, так как накапливается эффект множественных проверок во времени. Решение — заранее фиксировать длительность/размер выборки (или использовать методы, специально спроектированные под последовательное тестирование, например sequential testing с поправкой на множественные проверки).

**5. Параметрические vs непараметрические тесты**
Параметрические тесты (t-тест) предполагают определённое распределение данных (обычно нормальное) и работают с параметрами этого распределения (среднее, дисперсия). Непараметрические (Манна-Уитни) не делают таких предположений и работают с рангами значений. U-критерий Манна-Уитни уместен, когда данные сильно скошены, есть выбросы, выборка маленькая, или метрика порядковая, а не непрерывная (например, оценки по шкале 1-5).

**6. Sample Ratio Mismatch (SRM)**
Ситуация, когда фактическое распределение пользователей между группами теста заметно отличается от заданного (например, ожидали 50/50, а получили 52/48 при большой выборке, что статистически значимо). Диагностируется хи-квадрат тестом на соответствие ожидаемым пропорциям. SRM — сигнал о баге в системе сплитования, различиях в трекинге между группами или проблемах с исключением ботов, и результаты такого теста нельзя доверять без исправления причины.

**7. Сетевые эффекты в экспериментах**
Если действия одного пользователя влияют на других (соцсети, маркетплейсы с двусторонним рынком), классическое A/B на уровне пользователя даёт смещённую оценку, потому что контрольная и тестовая группы не изолированы друг от друга. Решения: рандомизация на уровне кластеров (регион, город, группа пользователей, полностью изолированных друг от друга), geo-эксперименты, switchback-дизайн (переключение всей системы между вариантами по времени).

## 3. Работа с данными и Python/Pandas (углублённо)

**1. Данные, не помещающиеся в память**
Подходы: обработка чанками (`pd.read_csv(..., chunksize=...)`) с последовательной агрегацией; использование Dask или Polars, которые поддерживают ленивые вычисления и обработку данных больше объёма RAM; выгрузка тяжёлых агрегаций на уровень СУБД/DuckDB, где данные и не обязаны попадать в память Python целиком; при повторяющейся задаче — переход на колоночное хранилище (Parquet) вместо CSV для более эффективного чтения нужных колонок.

**2. .apply() vs векторизация vs .map()**
Векторизованные операции Pandas/NumPy выполняются в скомпилированном C-коде и на порядок быстрее построчных вызовов. `.apply()` построчно вызывает Python-функцию — гибко, но медленно на больших данных. `.map()` применяется к Series поэлементно (часто для замены значений по словарю) и по скорости ближе к векторизации, чем `.apply()`, но всё ещё уступает чистым векторным операциям. Правило: сначала искать векторизованное решение, `.apply()` — как последний вариант.

**3. Утечка данных (data leakage)**
Проверяю, не попадает ли в признаки/расчёт информация, которая на момент принятия решения физически ещё не могла быть известна (например, использование данных "после события" для предсказания "до события"), не пересекаются ли train/test по времени или по сущности (один и тот же пользователь в обеих выборках), не включена ли в фичи сама целевая переменная в скрытом виде (например, агрегат, посчитанный с учётом текущей строки).

**4. Проектирование витрины данных для отдела продаж**
Гранулярность — обычно "строка сделки" или "строка сделка × день" в зависимости от того, нужен ли анализ динамики. Ключевые таблицы: факт-таблица `sales_fact` (сделка, сумма, дата, ссылки на измерения), измерения (dimensions) `dim_customer`, `dim_product`, `dim_employee`, `dim_date`. Ключи — суррогатные ID измерений в факт-таблице (звёздная схема), что упрощает джойны и агрегации в BI-инструментах.

**5. SCD Type 2**
Slowly Changing Dimension — способ хранения истории изменений атрибутов сущности (например, статус клиента, регион) вместо перезаписи текущего значения. Type 2 добавляет новую строку при каждом изменении с полями `valid_from`, `valid_to` (или `is_current`), сохраняя старые значения нетронутыми:
```sql
UPDATE dim_customer SET valid_to = CURRENT_DATE, is_current = FALSE
WHERE customer_id = 123 AND is_current = TRUE;

INSERT INTO dim_customer (customer_id, status, valid_from, valid_to, is_current)
VALUES (123, 'premium', CURRENT_DATE, NULL, TRUE);
```
Это позволяет корректно считать метрики "по состоянию на дату X" задним числом.

## 4. Визуализация, дашборды и коммуникация (углублённо)

**1. Производительность дашборда при росте данных**
Использовать предагрегированные таблицы/материализованные представления вместо запроса к сырым данным на каждый рендер; extract (снапшот данных) вместо live-соединения там, где не требуется real-time; ограничивать дефолтный диапазон дат; избегать избыточной детализации на верхнем уровне дашборда, вынося глубокий разбор в drill-down.

**2. Несогласие стейкхолдера с выводами**
Пример подхода: не спорить "на словах", а вместе пройти по данным и методологии шаг за шагом, показать исходные цифры и логику расчёта, уточнить, не опирается ли стейкхолдер на неполную или устаревшую информацию, и при необходимости — предложить совместно определить, какая дополнительная проверка снимет разногласие.

**3. Баланс между точностью и скоростью ответа**
Явно обозначать уровень уверенности в промежуточном ответе ("предварительная оценка на неполных данных, уточню к пятнице"), давать быстрый ориентировочный ответ с чёткими оговорками о допущениях, если решение нужно "сейчас", и параллельно доводить более точный анализ, если это критично для итогового решения.

**4. Vanity metric**
Метрика, которая красиво растёт, но не отражает реальную ценность для пользователя или бизнес-результат — например, число регистраций без учёта активности после регистрации, число скачиваний приложения без учёта retention. Отличить можно, спросив: "если эта метрика вырастет вдвое, а всё остальное не изменится, станет ли бизнесу лучше?" Если ответ неочевиден — это, вероятно, vanity metric.

## 5. Бизнес-мышление и продвинутые кейсы

**1. Вовлечённость выросла, retention упал**
Стоит проверить: не привлекла ли фича "не тот" сегмент пользователей (например, через агрессивный онбординг, который повышает разовую активность, но не соответствует реальной потребности); не произошла ли каннибализация другой полезной функции; не изменилась ли одновременно другая часть продукта, влияющая на retention отдельно от фичи. Стоит сегментировать пользователей на "использовавших новую фичу" и "не использовавших" и сравнить retention внутри каждой группы отдельно.

**2. Оценка impact без A/B-теста**
Использовать квазиэкспериментальные методы: difference-in-differences (сравнение динамики метрики до/после у затронутой и незатронутой групп), интерполяцию тренда "что было бы без изменения" (counterfactual) на основе исторических данных, сравнение с похожим сегментом/регионом, который изменение не затронуло.

**3. Неоднозначное определение метрики**
Собрать всех заинтересованных стейкхолдеров, явно проговорить, для какого решения нужна метрика, предложить 2-3 варианта определения с конкретными числовыми расхождениями между ними на реальных данных, чтобы решение принималось осознанно, а не абстрактно, и зафиксировать финальное определение в общем глоссарии метрик, чтобы избежать повторного разногласия в будущем.

**4. Расхождение цифр между источниками**
Пошагово сверяю: одинаковый ли период и часовой пояс, одинаковая ли единица подсчёта (уникальные пользователи vs события), нет ли задержки/лага в одном из источников (например, биллинг обновляется раз в сутки), одинаковая ли логика включения/исключения (тестовые аккаунты, возвраты, отменённые заказы). Часто расхождение объясняется разным определением одного и того же на уровне ETL, а не ошибкой в данных.

**5. Точечное исследование vs долгосрочный мониторинг**
Если аномалия разовая и низкоимпактная — достаточно точечного разбора. Если похожие аномалии повторяются или имеют высокий потенциальный ущерб — стоит инвестировать в автоматический мониторинг (алерты по отклонению от скользящего среднего/сезонного baseline), чтобы не тратить ресурсы аналитика на ручной поиск каждый раз, и приоритизировать это по формуле "вероятность повторения × стоимость пропуска".

## 6. Практические задачи

**1. Concurrent users в момент времени**
```sql
WITH events AS (
    SELECT session_start AS ts, 1 AS delta FROM sessions
    UNION ALL
    SELECT session_end AS ts, -1 AS delta FROM sessions
)
SELECT ts,
       SUM(delta) OVER (ORDER BY ts ROWS UNBOUNDED PRECEDING) AS concurrent_users
FROM events
ORDER BY ts;
```
Каждое начало сессии добавляет +1, конец сессии — -1; накопительная сумма по времени даёт число одновременно активных пользователей в любой момент.

**2. MRR и churn rate с учётом апгрейдов/даунгрейдов**
```sql
WITH monthly_active AS (
    SELECT user_id, DATE_TRUNC('month', d) AS month, plan, plan_price
    FROM subscriptions s
    JOIN plan_prices p ON p.plan = s.plan
    CROSS JOIN generate_series(s.start_date, COALESCE(s.end_date, CURRENT_DATE), '1 month') AS d
)
SELECT month, SUM(plan_price) AS mrr
FROM monthly_active
GROUP BY month
ORDER BY month;
```
Churn rate за месяц = (число подписчиков, ушедших в этом месяце) / (число активных подписчиков на начало месяца). Апгрейды/даунгрейды учитываются автоматически, так как MRR считается по актуальной цене плана в каждом месяце, а не по цене на момент первой подписки.

**3. Когортный LTV по каналу привлечения**
```sql
WITH first_touch AS (
    SELECT user_id, acquisition_channel,
           DATE_TRUNC('month', MIN(order_date)) AS cohort_month
    FROM orders
    GROUP BY user_id, acquisition_channel
),
revenue_by_month AS (
    SELECT ft.user_id, ft.acquisition_channel, ft.cohort_month,
           DATE_TRUNC('month', o.order_date) AS activity_month,
           SUM(o.amount) AS revenue
    FROM orders o
    JOIN first_touch ft ON ft.user_id = o.user_id
    GROUP BY ft.user_id, ft.acquisition_channel, ft.cohort_month, DATE_TRUNC('month', o.order_date)
)
SELECT acquisition_channel, cohort_month,
       DATE_PART('month', AGE(activity_month, cohort_month)) AS month_number,
       SUM(revenue) / COUNT(DISTINCT user_id) AS ltv_per_user
FROM revenue_by_month
GROUP BY acquisition_channel, cohort_month, month_number
ORDER BY acquisition_channel, cohort_month, month_number;
```
Результат — кумулятивный LTV по месяцам жизни когорты, что позволяет сравнивать окупаемость разных каналов привлечения во времени.
