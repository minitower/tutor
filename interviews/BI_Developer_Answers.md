# Ответы: BI Developer

## 1. SQL и работа с базами данных

**1. INNER / LEFT / RIGHT / FULL OUTER JOIN**
- `INNER JOIN` — возвращает только строки, у которых есть совпадение в обеих таблицах. Пример: получить заказы только тех клиентов, которые есть в справочнике клиентов.
- `LEFT JOIN` — возвращает все строки левой таблицы и совпадающие строки правой; если совпадения нет — `NULL`. Пример: список всех клиентов и их заказов, включая тех, у кого заказов ещё не было.
- `RIGHT JOIN` — зеркало `LEFT JOIN`, на практике используется реже (обычно переписывают через `LEFT JOIN`, поменяв таблицы местами).
- `FULL OUTER JOIN` — все строки из обеих таблиц, с `NULL` там, где нет совпадения. Пример: сверка двух систем учёта, чтобы найти расхождения в обе стороны.

**2. Оконные функции**
Оконные функции выполняют расчёт по "окну" строк, связанных с текущей, но не схлопывают результат в одну строку (в отличие от `GROUP BY`).
```sql
-- Номер заказа клиента по дате
SELECT customer_id, order_id, order_date,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date) AS order_seq
FROM orders;

-- Ранг по сумме продаж внутри региона (с пропусками при равенстве)
SELECT region, sales_rep, total_sales,
       RANK() OVER (PARTITION BY region ORDER BY total_sales DESC) AS rnk
FROM sales_summary;

-- Сравнение с предыдущим заказом клиента
SELECT customer_id, order_date, amount,
       LAG(amount) OVER (PARTITION BY customer_id ORDER BY order_date) AS prev_amount
FROM orders;
```

**3. WHERE vs HAVING**
`WHERE` фильтрует строки до группировки и агрегации, агрегатные функции в нём использовать нельзя. `HAVING` фильтрует уже после `GROUP BY`, работает с агрегатами (например, `HAVING SUM(amount) > 1000`).

**4. Оптимизация медленного запроса**
Порядок действий: 1) посмотреть план выполнения (`EXPLAIN ANALYZE`), найти самые дорогие узлы; 2) проверить наличие индексов на полях джойнов и фильтров; 3) оценить кардинальность соединяемых таблиц — не идёт ли неявный декартов рост строк; 4) убрать лишние `SELECT *`, сузить набор колонок; 5) при необходимости — материализовать промежуточные результаты (временные таблицы, индексированные представления) или предагрегировать данные заранее (ETL-слой вместо расчёта на лету).

**5. CTE**
`WITH`-выражения (CTE) делают запрос читаемым, позволяют разбить сложную логику на именованные шаги и использовать рекурсию. От подзапроса отличаются в первую очередь читаемостью (CTE можно переиспользовать в запросе), от временной таблицы — тем, что CTE обычно не материализуется физически и живёт только в рамках одного запроса (поведение зависит от СУБД).

**6. Скользящее среднее с пропусками в датах**
Нужно сначала сгенерировать полный календарь дат (например, через `generate_series` или календарную таблицу), `LEFT JOIN` к нему фактические данные, заполнить пропуски нулями/предыдущим значением, и уже поверх этого считать `AVG(...) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)`.

**7. UNION vs UNION ALL**
`UNION` объединяет результаты и убирает дубликаты (требует дополнительной сортировки/хэширования — дороже). `UNION ALL` просто склеивает результаты без дедупликации — быстрее, и его стоит использовать по умолчанию, если заранее известно, что дублей нет или они не важны.

## 2. Моделирование данных и хранилища

**1. Звезда vs снежинка**
Star schema — факт-таблица напрямую связана с денормализованными таблицами измерений. Плюсы: проще, меньше джойнов, быстрее для BI-запросов. Snowflake schema — измерения дополнительно нормализованы в подтаблицы. Плюсы: меньше избыточности и легче поддерживать целостность справочников; минусы: больше джойнов, сложнее для конечных пользователей и медленнее для аналитических запросов.

**2. Факт-таблица и таблица измерений**
Факт-таблица хранит измеримые события/метрики (сумма продажи, количество) и внешние ключи на измерения. Таблица измерений хранит описательный контекст (клиент, продукт, дата, магазин). Пример: `fact_sales(date_id, product_id, store_id, amount, quantity)` + `dim_product`, `dim_store`, `dim_date`.

**3. Slowly Changing Dimensions (SCD)**
- **Type 0** — атрибут никогда не меняется (например, дата рождения).
- **Type 1** — перезаписываем старое значение новым, история теряется (например, исправление опечатки в имени).
- **Type 2** — при изменении создаётся новая строка с датами действия (valid_from/valid_to) и флагом текущей записи — история сохраняется полностью.
- **Type 3** — хранится текущее и одно предыдущее значение в отдельных колонках — ограниченная история.

**4. OLTP vs OLAP**
OLTP оптимизирован под множество коротких транзакций (вставка/обновление отдельных строк), сильно нормализован. OLAP оптимизирован под чтение больших объёмов и агрегацию, часто денормализован. Для BI используют отдельное хранилище, чтобы аналитические запросы не нагружали и не блокировали боевую базу, а также чтобы иметь историю и модель данных, удобную для отчётности, а не для работы приложения.

**5. Денормализация**
Намеренное добавление избыточности (например, дублирование названия категории прямо в факт-таблицу) ради упрощения запросов и повышения производительности чтения. Оправдана в BI/OLAP-слое, где важна скорость чтения, а не экономия места и не частота обновлений.

**6. Гранулярность факт-таблицы**
Определяется тем, что представляет собой одна строка — например, "одна позиция в чеке", а не "один чек" или "один день продаж по магазину". Гранулярность выбирают исходя из требований к детализации отчётности: чем ниже уровень (мельче grain), тем больше аналитической гибкости, но больше объём данных.

**7. Data Warehouse / Data Mart / Data Lake**
- **Data Warehouse** — централизованное, структурированное хранилище очищенных и смоделированных данных для всей компании.
- **Data Mart** — подмножество хранилища для конкретного отдела/домена (например, витрина для маркетинга).
- **Data Lake** — хранилище сырых данных любого формата (структурированных и нет) без обязательной схемы при записи, используется для более гибкой и объёмной аналитики/ML.

## 3. ETL / ELT процессы

**1. ETL vs ELT**
ETL — трансформация происходит до загрузки в целевое хранилище (на промежуточном сервере). ELT — сырые данные сначала загружаются в хранилище, а трансформация выполняется уже там средствами самого хранилища (актуально для облачных DWH типа Snowflake/BigQuery с большой вычислительной мощностью). ELT предпочтительнее при больших объёмах и когда хранилище достаточно мощное; ETL — когда нужно трансформировать/очистить данные до попадания в целевую систему (например, по требованиям безопасности).

**2. Обработка ошибок и логирование**
Логировать каждый запуск пайплайна (старт/финиш, число обработанных строк, ошибки), использовать retry с ограничением попыток для временных сбоев, отправлять данные с ошибками в отдельную "карантинную" таблицу/очередь вместо падения всего пайплайна, настраивать алерты (email/Slack) на критичные сбои, вести идемпотентность операций, чтобы повторный запуск не дублировал данные.

**3. Инкрементальная загрузка**
Загрузка только новых/изменённых данных с последнего запуска (по timestamp, инкрементальному ключу или CDC), а не полная перезаливка таблицы каждый раз. Нужна для экономии времени и ресурсов при больших объёмах данных.

**4. Инструменты**
Примеры: Apache Airflow (оркестрация), dbt (трансформации в стиле ELT с версионированием и тестами), SSIS/Azure Data Factory (в экосистеме Microsoft), Talend, Fivetran/Stitch (готовые коннекторы для экстракции). На собеседовании стоит рассказать о конкретном инструменте, с которым был реальный опыт, и объяснить решённые задачи.

**5. Качество данных**
Проверки на этапе загрузки: отсутствие дублей по ключу, отсутствие `NULL` в обязательных полях, соответствие типов и диапазонов значений (например, суммы не отрицательные), сверка контрольных сумм/количества строк источник-приёмник, проверка ссылочной целостности (foreign key существует в измерении).

**6. Дубликаты и опоздавшие данные**
Для дублей — дедупликация по бизнес-ключу с выбором последней версии записи (например, через `ROW_NUMBER() OVER (PARTITION BY key ORDER BY updated_at DESC)`). Для late-arriving data — использовать окно допустимого опоздания при инкрементальной загрузке (перезагружать не только "вчера", а последние N дней) либо помечать записи как "поздние" и пересчитывать зависимые агрегаты.

## 4. BI-инструменты и визуализация

**1. Опыт с инструментами**
Здесь важно рассказать реальный кейс: какую задачу решали, как строили модель данных, какие были сложности (производительность, требования заказчика) и какой результат получили.

**2. Calculated column vs measure (Power BI)**
Calculated column — вычисляется при обновлении данных, хранится физически в модели, занимает память, оперирует построчно. Measure — вычисляется "на лету" в момент визуализации в контексте текущих фильтров, не хранится, значительно эффективнее по памяти. Меры предпочтительны почти всегда, кроме случаев, когда результат нужен как атрибут для среза/группировки.

**3. DAX и контекст**
Row context — контекст текущей строки при вычислении вычисляемого столбца или в итерирующих функциях (`SUMX`, `FILTER`). Filter context — набор фильтров, действующих на измерение в момент вычисления меры (из среза, страницы, визуала). `CALCULATE` меняет filter context:
```dax
Sales YTD = CALCULATE(SUM(Sales[Amount]), DATESYTD('Date'[Date]))
Sales All Products = CALCULATE(SUM(Sales[Amount]), ALL(Product))
Top Sellers = FILTER(Products, [Total Sales] > 100000)
```

**4. Выбор визуализации**
- Динамика во времени → линейный график.
- Сравнение категорий → столбчатая диаграмма.
- Доли от целого (мало категорий) → круговая/донат, при многих категориях лучше горизонтальный bar.
- Распределение → гистограмма, box plot.
- Связь между переменными → scatter plot.
Главный принцип — выбирать тип, который меньше всего искажает восприятие и быстрее всего считывается зрителем.

**5. Best practices дашбордов**
Иерархия информации (главные KPI сверху), ограниченная цветовая палитра с акцентом на аномалиях, минимум "визуального шума" (лишние рамки, 3D-эффекты), интерактивность через срезы и drill-down вместо перегрузки одного экрана, единообразие форматов чисел и дат, оптимизация под целевое устройство (десктоп/мобильный).

**6. Производительность тяжёлых дашбордов**
Проверить объём данных, загружаемых в модель (агрегировать на уровне ETL, а не в BI-инструменте), уменьшить число визуалов на одной странице, заменить сложные вычисляемые меры на предрасчитанные столбцы там, где это уместно, использовать инкрементальное обновление модели вместо полной перезагрузки, проверить кардинальность связей и отказаться от связей "многие-ко-многим", где возможно.

**7. Row-Level Security (RLS)**
Механизм ограничения видимости строк данных в зависимости от того, кто смотрит отчёт (например, региональный менеджер видит только свой регион). Реализуется через роли с DAX-фильтрами (Power BI) или через таблицу соответствия "пользователь — доступные значения измерения", применяемую как динамический фильтр.

## 5. Бизнес-аналитика и коммуникация

**1. Сбор требований**
Начинать с вопроса "какое решение вы будете принимать на основе этого отчёта", а не "что вы хотите видеть". Уточнять источники данных, частоту обновления, целевую аудиторию, приоритетные метрики и разрезы, договариваться о макете/прототипе до начала разработки, чтобы избежать переделок.

**2. Расхождение данных с ожиданиями**
Пример подхода: сверить определения метрики (иногда расхождение — не ошибка, а разное понимание, что считается "продажей" — с НДС или без, по дате заказа или оплаты), проверить фильтры в отчёте, сверить агрегацию на исходном уровне против отчёта построчно, найти конкретный пример расхождения и трассировать его до источника.

**3. Выбор KPI по отделам**
Отталкиваться от целей отдела: продажи — выручка, конверсия, средний чек; маркетинг — CAC, ROI кампаний, трафик по каналам; финансы — маржинальность, cash flow, отклонение от бюджета. Важно обсуждать метрики с самим отделом, а не выбирать их только по данным.

**4. Проект, которым горжусь** — ответ индивидуальный, важно структурировать по схеме: проблема → что сделал → какой был измеримый результат (в цифрах, если возможно).

**5. Объяснение ограничений заказчику**
Говорить простым языком в терминах влияния на решения: "данные обновляются раз в сутки ночью, поэтому сегодняшние продажи вы увидите завтра утром" — не углубляясь в технические детали ETL, если это не нужно собеседнику.

## 6. Практическая задача

**1. Первая/последняя покупка и сумма по клиенту**
```sql
SELECT
    customer_id,
    MIN(order_date) AS first_order_date,
    MAX(order_date) AS last_order_date,
    SUM(amount) AS total_amount
FROM sales
GROUP BY customer_id;
```

**2. Схема звезды для денормализованных продаж по регионам**
- `fact_sales(date_id, region_id, product_id, amount, quantity)`
- `dim_date(date_id, date, month, quarter, year)`
- `dim_region(region_id, region_name, country)`
- `dim_product(product_id, product_name, category)`

**3. YoY прирост продаж**
DAX:
```dax
Sales PY = CALCULATE(SUM(Sales[Amount]), SAMEPERIODLASTYEAR('Date'[Date]))
YoY % = DIVIDE([Total Sales] - [Sales PY], [Sales PY])
```
SQL (упрощённо, через self-join по году):
```sql
SELECT curr.year, curr.total_sales,
       (curr.total_sales - prev.total_sales) * 1.0 / prev.total_sales AS yoy_growth
FROM yearly_sales curr
LEFT JOIN yearly_sales prev ON curr.year = prev.year + 1;
```
